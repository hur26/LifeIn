# 04 · 技术决策记录

**本文档最重要的部分是"被否决的方案"和"重新评估的触发条件"。**

本项目刻意没有引入 LangGraph、MCP、hook 机制、多 agent 等一批当前流行的 agent 技术。
这不是因为不了解,而是逐条评估后认为**当前阶段不匹配**。每条决策都写明了
将来什么信号出现时应该重新考虑 —— 请在改架构前先读对应条目。

选型标准只有一条:**适合项目才用,不为了用而用。**

## ADR-001 · 主入口选企业微信

**状态**:已确认(P0 生效)

**背景**
用户与朋友均在中国大陆,朋友为非技术背景。系统需要主动推送,且审批流程
要求消息能承载可点击的交互按钮并回调服务端。

**决策**
主入口使用**企业微信自建应用**。飞书作为备选方案保留。

**理由**
它是唯一同时满足三条硬需求的正规方案:无限制主动推送、交互式模板卡片 + 按钮回调、
消息可转投到微信中接收(朋友学习成本接近零)。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| Telegram | 大陆网络不可用,朋友不可能装 |
| 微信个人号(协议逆向) | 封号风险,**绝不能让朋友承担**,与托管他人数据的定位冲突 |
| 微信服务号 | 需企业主体 + 类目审核,个人做不了;订阅通知限制多,无交互按钮 |
| QQ 官方机器人 | 主动推送与私聊能力受政策限制 |
| 钉钉群机器人 | 只能推群,交互能力弱,无法承载审批 |
| 飞书 | API 体验明显更好,但**朋友是非技术背景**,装飞书的门槛高于企微转投微信 |
| 自建 App + 厂商推送 | 需接小米/华为/OPPO/vivo 四套通道,P3 前投入产出比极差 |
| 邮件 | 无交互按钮,不能承载审批;保留作兜底通道 |

**待验证**
企业微信"微信插件"的消息转投能力、以及模板卡片的按钮回调细节,
**动手前需实测确认**。平台开放政策变动频繁,以官方最新文档为准。

**重新评估的触发条件**
朋友群体变为技术背景为主 → 改飞书;或企微政策收紧导致转投微信失效 → 重新评估。

## ADR-002 · P0–P2 不引入 agent 编排框架

**状态**:已确认

**背景**
用户初期倾向自研编排层,后改为使用 LangGraph 等开源框架。

**决策**
**P0–P2 不引入任何 agent 编排框架**,直调外部 LLM API(OpenAI 兼容接口)。
**P3 引入状态机编排**(LangGraph 或同类)。

**理由**
P0–P2 的流程本质是"定时拉数据 → 调 LLM → 推送",是脚本级复杂度,
引入编排框架是纯负担 —— 多一层抽象、多一份文档、多一批 bug,换不来任何东西。

模型侧统一走 **OpenAI 兼容接口**,不绑定任何厂商:换模型只需改配置里的
`base_url` + `model`,不动业务代码。这条约束比"选哪家模型"重要 ——
厂商可能涨价、限流或下线,切换成本必须保持在改两行配置的量级。

真正需要框架的时刻是 **P3 的审批流程**:一个流程要**暂停数小时等用户点按钮,
然后从断点恢复**。这是长时间运行、可中断、可持久化的流程,
LangGraph 的 checkpoint / interrupt 机制正是为此设计的。那时引入才是赚的。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| 自研编排层 | 目标是"自己和朋友真的用",不是学习项目。会先花几个月重造轮子,而朋友一直等不到能用的东西 |
| P0 就上 LangGraph | 过度设计。P0 用不到它任何一个核心能力 |

**重新评估的触发条件**
提前进入 P3、或 P1/P2 出现需要长时间挂起的流程 → 提前引入。

## ADR-003 · P0 不引入 MCP

**状态**:已确认

**背景**
用户最初将 "MCP 与工具治理" 列为核心技术点。

**决策**
P0 的工具直接实现为普通函数,不包装成 MCP server。

**理由**
MCP 解决的问题是"同一套工具给**多个 client** 复用"。当前只有一个后端在调用,
包一层 MCP 是白加一层抽象,没有任何收益。

工具治理(分权、审计)本项目确实需要,但那是**治理层**的职责,
用工具注册表 + 统一调用网关实现即可,与 MCP 无关。不要把两件事捆在一起。

**重新评估的触发条件(这条很可能会触发)**
当你希望**在其他 MCP client 里也直接查自己的邮件、账单、记忆**时 ——
那一刻起就是"一套工具、两个消费方",MCP 立刻变得划算。
建议届时优先把 L1 只读工具封成 MCP server,写操作留在服务端。

## ADR-004 · 不做 hook 机制,用审批队列

**状态**:已确认

**背景**
用户最初将 "Hook 与可观测性" 列为核心技术点,设想用 hook 拦截高危操作。

**决策**
不实现通用 hook 机制。高危操作拦截由**分权网关 + 审批队列**直接实现。

**理由**
Hook 是给**第三方扩展**用的抽象。本项目没有第三方,所有代码都是自己写的。
在自己的代码里,"拦截 L3 操作"就是网关里的一个分支判断,
为它造一套注册/触发/优先级机制是纯粹的过度设计。

可观测性的真实需求是**审计日志 + 成本核算**,这两件事本项目做了
(见 [架构 §3.3](02-architecture.md#33-审计与成本)),只是不叫 hook。

**重新评估的触发条件**
项目开放为框架、或需要让朋友自己写扩展规则 —— 但这与
[产品定义 §8](01-product-spec.md#8-非目标明确不做的事) 的非目标冲突,基本不会发生。

## ADR-005 · 不做多 agent 协作

**状态**:已确认

**背景**
用户最初设想"并行竞争 + 评审择优"的多 agent 范式。

**决策**
使用**单 agent + 分领域工具集**。不做多 agent 协作,不做竞争择优。

**理由**
"并行竞争 + 评审择优"适用于**有客观验收标准、且值得花 N 倍 token** 的高价值任务
(如代码修复:测试跑没跑通是硬指标)。生活任务两条都不满足 ——
"帮我订个餐"没有客观优劣,也不值得跑五遍。

分领域拆 agent 的**真实理由**是上下文隔离和 prompt 专门化,不是"协作"。
等到单个 prompt 长到互相干扰、或上下文塞不下时再拆,那才是真实信号。

**重新评估的触发条件**
单 agent 的 system prompt 因领域过多而互相干扰,或上下文长度成为瓶颈 →
按领域拆分子 agent(仍然不做竞争择优)。

## ADR-006 · 存储用单一 PostgreSQL + pgvector

**状态**:已确认

**决策**
结构化数据、任务队列、记忆向量全部放在一个 PostgreSQL 实例,向量用 pgvector 扩展。

**理由**
单机自托管场景下,多引入一个组件就多一份运维负担和一个故障点。
在数据量达到百万级之前,pgvector 的性能完全够用,而事务一致性
(事件与其向量必须同时写入成功)反而是专用向量库的短板。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| 独立向量数据库 | 当前数据量下纯属增加运维复杂度,且跨库事务一致性难保证 |
| Redis / Celery 做队列 | P0–P3 的任务量用数据库表 + APScheduler 完全够;多用户后再评估 |

**重新评估的触发条件**
向量数据超过百万级且检索延迟成为瓶颈;或 P4 多用户后任务队列出现积压。

## ADR-007 · 朋友接入推迟到 P4

**状态**:已确认(硬约束)

**决策**
P0–P3 期间系统只有作者一个用户。朋友在 P4 且满足前置门槛后才接入。

**理由**
一旦有第二个用户,你就成了**别人的邮箱授权码和支付数据的保管人**,
这是法律责任而非仅技术责任。P0–P3 期间你需要随时重构、删库、改 schema 的自由,
有真实用户后这个自由就没了。

**同时**:多用户的三项技术预留(全表 `user_id`、凭据字段级加密、
数据访问不假设单用户)**必须从 P0 第一行代码就做**。现在成本几乎为零,
P4 再补是几周的痛苦重构。推迟的是**开放**,不是**准备**。

## ADR-008 · 账单归类用规则+LLM 混合

**状态**:已确认(P2 生效)

**决策**
账单归类采用两级策略:先查商户规则表命中则直接归类;未命中才调 LLM,
并将 LLM 的结果**写回规则表**作为后续规则。

**理由**
消费记录高度重复 —— 同样几十个商户占据绝大多数流水。
纯 LLM 归类既贵又不稳定(同一个商户不同月份可能归到不同类)。
规则表让成本随时间下降、结果随时间稳定,LLM 只处理长尾。

**与两阶段入账的关系**
实时通知里的商户名常常只是代收机构名("财付通""支付宝"),归类价值很低。
因此**归类跑两次**:实时入账时先给一个临时分类,月度账单回填真实商户后重新归类。
规则表只从**回填后的真实商户名**沉淀,不要用代收机构名污染规则表
(见 [ADR-012](#adr-012--账单采集以实时通知为主导出账单为辅))。

**监控指标**
LLM 调用占比。如果这个数字不随时间下降,说明规则没有正确沉淀,是 bug 而不是常态。

## ADR-009 · 凭据字段级加密从第一天做

**状态**:已确认(P0 生效,硬约束)

**决策**
所有 IMAP 授权码、企微 access_token 等凭据**存库前加密**,密钥走环境变量(P0–P3)
或 KMS(P4)。

**理由**
"先明文存,以后再加密"的问题是:等你想加密时,库里已经有真实凭据了,
备份里也有,而你不知道备份都散在哪。加密必须在第一条凭据入库之前就位。

P0 阶段成本极低(一个加密工具函数),P4 补做则要处理存量数据和历史备份。

## ADR-010 · 微信只做只读接入,走官方通知监听

**状态**:**已修订**(原决策为"完全不接入",2026-09 修订为"只读接入")

**背景**
原决策一刀切地否决了微信接入,理由是"只能靠协议逆向或客户端 hook"。
这个前提是错的:**读微信消息和 hook 微信客户端是两件不同的事**。
安卓的 `NotificationListenerService` 是系统级公开 API,能拿到通知的
应用包名、标题(群名/联系人)、正文,**既不修改也不注入微信客户端**。
而记账主通道([ADR-012](#adr-012--账单采集以实时通知为主导出账单为辅))
本来就要在手机上常驻这个监听器 —— 边际成本为零。

**决策**

**准许**:通过安卓官方通知监听读取微信通知(好友消息、群消息、支付通知),
用于账单识别、群消息摘要、日程与待办提取。

**禁止**(维持原否决,不放宽):

- 协议逆向 —— itchat / 网页版微信协议 / wechaty 等
- 客户端 hook —— Xposed、无障碍服务点击注入
- **任何形式的自动回复或代发微信消息**

**理由**
封号风险来自"写"和"伪装成客户端",不来自"读通知"。通知监听在微信侧
不产生任何异常行为特征,也不存在协议指纹。

自动发消息则是最容易被风控识别的行为,而且按本项目的三级分权,
代发消息本来就是标准的 **L3** —— 合规做法是 agent 生成草稿、推卡片、
人工点确认后才发出,那已经不叫"自动回复"了。既然要人点,
就没有必要为它承担 hook 微信客户端的风险。

**评估过的三个现成实现,都到不了目标**

| 项目 | 实际是什么 | 为什么不用 |
| --- | --- | --- |
| `node-webot/weixin-robot` | 微信**公众号**开放接口封装 | 只能回复关注公众号的人,回复不了个人好友 |
| `yangxuanxc/wechat_friends` | itchat,网页版微信协议 | 网页版个人号登录已基本关闭;且属协议逆向 |
| `itsMelo/WcAutoReply` | 安卓无障碍服务点击自动回复 | 客户端 hook,且 ROM 适配是无底洞 |

**这条通道的真实能力边界(必须写清,否则会高估)**

通知监听只能拿到**通知栏实际展示过的内容**,因此:

- 设了免打扰的群**拿不到**
- 长消息会被系统截断
- 撤回的消息、进入聊天前的历史消息**完全拿不到**
- 系统可能把多条折叠成"[3 条] 张三: ……",需要单独处理

所以这块能力的准确名字是"**在线期间的群消息摘要**",
不是"聊天记录分析"。产品文案和验收标准都必须按这个口径写。

**重新评估的触发条件**
微信开放个人号的官方消息接口(目前没有任何迹象)。
若将来愿意为自动回复承担封号风险,**也必须先把它归入 L3 审批流**,
而不是直接放开自动发送。

## ADR-011 · 数据源全面本地化

**状态**:已确认(P0 生效)

**背景**
原设计写的是 `IMAP / Gmail API` 和 `CalDAV / Google Calendar API`,
这是照搬国外方案的产物。作者实际用的是 QQ / 163 邮箱,日历也不在 Google。

**决策**

- **邮箱**:统一走标准 IMAP + 授权码(`imap.qq.com` / `imap.163.com`),
  不引入任何厂商 SDK。
- **日历**:走**企业微信日程 / 日历接口**,与主入口复用同一套自建应用凭据。

**理由**
IMAP 是国内邮箱的最小公分母,换邮箱只改配置。授权码不是账号登录密码,
泄露面更小且可单独吊销 —— 这一点对 P4 代管朋友凭据尤其重要。

日历选企微是因为**主入口已经是企微**:不多接一个平台、不多一套凭据、不多一次授权。
P1 的 L2 工具"改日历"直接走同一套接口写回,用户在手机企微上立刻看到结果。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| Gmail API / Google Calendar | 国内不可直连,且作者本来就不用 |
| iCloud CalDAV | 国内连接不稳定;小米/华为/OPPO 日历基本不开放 CalDAV |
| 飞书日历 | API 设计确实更好,但要多接一个平台、多一套凭据,还得同时用两个 App |

**实现注意(会卡住半天的坑)**

- 163 / 126 的 IMAP 在 `SELECT` 之前**必须先发 `ID` 命令**声明客户端身份,
  否则直接报 `Unsafe Login`。Python 的 `imaplib` 默认不允许在该状态发 `ID`,
  需要先把它注册为 AUTH 态可用命令。QQ 邮箱无此要求。
- 授权码会在用户修改账号密码后失效,采集端连续认证失败**必须告警**,
  不能静默停采(见 [R9](05-risks.md#r9--单点自托管可用性))。

**重新评估的触发条件**
需要读取邮件以外的 Google / Outlook 数据,或日历使用习惯迁出企微。

## ADR-012 · 账单采集以实时通知为主,导出账单为辅

**状态**:已确认(P2 生效)

**背景**
"能不能自动记账"决定 P2 的验收标准怎么写。最初的方案把月度导出当作主来源、
把交易短信当作可选增强,方向反了 —— 绝大多数消费当场就有一条通知,
而月度导出天然滞后最多 30 天。

**决策**

| 通道 | 角色 | 实时性 | 自动化程度 |
| --- | --- | --- | --- |
| 手机端转发(**短信 + App 通知**) | **主通道** | 秒级 | 全自动,需常驻安卓端 |
| 信用卡月度对账单邮件 | 金额权威源、对账 | 月度 | 完全自动 |
| 支付宝 / 微信账单导出 | 补全商户名与订单号 | 月度 | 半自动,每月手动触发 |

**明确不做**:模拟登录抓账单、客户端自动化。

**两阶段入账(核心设计)**

1. 实时通知到达 → **立即入账**,落金额、时间、卡号后四位、原始文本。
   此时商户名常常只是"财付通""支付宝"这类代收机构名,**不能直接用于归类**。
2. 月度账单到达 → 按 `(金额, 时间窗, 卡号后四位)` 匹配已有实时记录,
   **回填真实商户名、订单号并重新归类**;匹配不上的补为新记录,并计入覆盖率统计。

匹配必须有幂等键。**重复入账比漏记更糟** —— 漏记你会发现,重复不会。

**理由**
记账最难坚持的原因是反馈延迟。实时入账把反馈缩到秒级,这是月度导出无论如何
做不到的。更关键的是**预算超支预警只有在超支当天发出才有意义**,
下个月才知道自己上个月超了,这个功能等于没有。

**必须正视的两个缺口**

1. **覆盖率不是 100%。** 多家银行已提高短信提醒门槛,500 元以下的小额交易
   普遍不再免费发短信,改为 App 推送或微信服务号通知 —— 而日常生活消费
   恰恰大多落在这个区间。因此转发端**必须同时监听短信和 App 通知**,
   只做短信的方案覆盖率会随银行政策持续下滑。
2. **必须有一台常驻安卓设备。** iOS 没有等价方案,这是硬前提不是可选优化。
   只有 iOS 的话本条链路整体不成立,退回月度导出模式。

**覆盖率指标(P2 必须实现)**
月度账单到达后统计:其中有多少笔曾在实时通道出现过。这是通道健康度的**唯一客观指标**,
低于阈值说明转发规则漏了,要回去补规则,而不是接受现状。

**安全约束**
转发端能读到手机上的全部短信与通知,包含验证码。规则必须是发件人白名单 +
验证码内容强制丢弃,且**P4 绝不要求朋友安装转发端**。
详见 [R10](05-risks.md#r10--手机端采集器的越权读取)。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| 模拟登录抓账单 | 账号风险不可控,绝不能用于给朋友的服务,与 ADR-010 同理 |
| 只用月度导出 | 滞后最多 30 天,预算预警失去意义,记账反馈链路断掉 |
| 只监听短信、不监听 App 通知 | 小额交易的短信正在被银行取消,覆盖率会持续下滑 |
| 接第三方记账 App | 同样不开放个人 API,且等于把支付数据再交给一方 |

**重新评估的触发条件**
实时通道覆盖率长期低于阈值且补不上去;或支付宝 / 微信支付开放面向个人的
交易查询 API(目前没有任何迹象)。
