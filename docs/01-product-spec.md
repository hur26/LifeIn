# 01 · 产品定义

本文档记录已经确认的产品边界。**改动这里的任何一条,都意味着架构和计划要重新评估。**

---

## 1. 一句话定位

自托管的个人生活 agent —— 以邮箱 / 日历 / 账单 / 笔记为数据底座,企业微信为交互入口,
既能被问也能主动发现事情,所有"动外部世界"的操作都要经过人工审批。

---

## 2. 目标用户

| 优先级 | 用户 | 何时接入 |
| --- | --- | --- |
| 主 | 项目作者本人 | P0 |
| 次 | 作者的朋友(**非技术背景**) | P4,不早于此 |

**朋友放到 P4 是硬约束,不是排期偷懒。** 一旦有第二个用户,你就成了别人邮箱的 IMAP 授权码
和支付数据的保管人,这是法律责任而不只是技术责任。P0–P3 期间你可以随便重构、随便删库;
P4 之后不行。详见 [05 风险登记](05-risks.md#r1--代管他人凭据与支付数据)。

**明确不做**:面向陌生人的商业产品、面向开发者的开源框架。

---

## 3. 核心痛点(已确认,按优先级)

四条都是用户自述的真实高频困扰,不是设想出来的场景。

| # | 痛点 | 具体表现 | 首次交付 |
| --- | --- | --- | --- |
| 1 | **日程与待办** | 事情散在邮件、聊天、脑子里,记不住、排不出优先级 | P0 |
| 2 | **信息过载** | 邮件、资讯看不过来,想要自动筛选和每日摘要 | P0 |
| 3 | **财务与记账** | 钱花哪了不清楚,想要自动归类、预算预警、月度分析 | P2 |
| 4 | **生活安排执行** | 订票订餐、比价购物、预约这类"要跑腿"的事 | P3 |

排期理由:1 和 2 共用同一批数据源(邮箱 + 日历),放一起做边际成本最低,
且能最快验证"这东西你自己会不会每天看"这个核心问题。

---

## 4. 交互形态

### 主入口:企业微信自建应用

选它不是因为技术最好(飞书 API 体验明显更好),而是因为它是**唯一同时满足这三条**的正规方案:

- 能无限制主动推送(不像微信服务号受订阅通知和审核限制)
- 支持交互式模板卡片 + 按钮回调(**审批流程的硬需求**)
- 消息可以转投到微信里接收,非技术背景的朋友学习成本接近零

被否决的方案及理由见 [ADR-001](04-tech-decisions.md#adr-001--主入口选企业微信)。

### 其他入口

| 入口 | 阶段 | 说明 |
| --- | --- | --- |
| Web 控制台 | P3 | 审批历史、账单明细、记忆管理这类企微卡片装不下的内容 |
| 桌面客户端 | P3 | 作者自用,优先级低于 Web |
| 邮件 | P1 | 兜底通道,推送失败时降级 |
| 语音 | 不在规划内 | 链路长、延迟高,等前面都稳定了再说 |
| 自建 App | 不在规划内 | 需接小米/华为/OPPO/vivo 四套厂商推送通道,投入产出比极差 |

---

## 5. 主动性:双模式

**对话式(被动)**:用户在企微里提问或下指令,系统响应。

**事件驱动(主动)**:定时任务和事件订阅触发,系统主动推送。

主动是这个产品的价值主体,但**也是最容易毁掉它的东西**。误报多两次,用户就把通知关了,
之后再也不会打开。因此约束如下:

- 主动能力从**每天一条固定时间的摘要**起步,不做随机打断
- 任何新增的主动推送规则,先跑"影子模式"(只记录不推送)观察一周
- 每条主动推送都要能一键关闭该类规则
- 硬上限:非用户主动触发的推送,每天不超过 3 条

## 6. 数据源

### 第一期接入(已确认)

| 数据源 | 阶段 | 接入方式 | 备注 |
| --- | --- | --- | --- |
| 邮箱 | P0 | IMAP + 授权码(QQ / 163 / 126) | 账单、行程、待办的主要流入口 |
| 日历 | P0 | 企业微信日程 API | 与主入口复用同一套自建应用凭据 |
| 笔记 / 待办工具 | P1 | 官方 API | 具体选型待定,作记忆落地层 |
| 交易实时通知 | P2 | 安卓端转发短信 + App 通知 → webhook | **记账主通道**,刷卡当场入账 |
| 信用卡对账单 | P2 | 银行月度账单邮件(PDF,带密码) | 月度对账与金额校准,完全自动 |
| 账单与支付记录 | P2 | App 内手动导出 → 邮件送达 → 自动解析 | 月度补全真实商户名与订单号,每月手动触发两次导出 |

**记账以实时通知为主、月度账单为辅**,两阶段入账的设计与缺口见
[ADR-012](04-tech-decisions.md#adr-012--账单采集以实时通知为主导出账单为辅)。
硬前提:**需要一台常驻的安卓设备**,iOS 没有等价方案。

### 明确不接:微信聊天记录与公众号

信息密度最高、价值最大,但**无官方 API**,只能通过协议逆向或客户端 hook 获取。这意味着:

- 账号有被封禁风险
- 绝对不能用于给朋友的多用户服务(等于让朋友承担封号风险)
- 灰色地带,与"托管他人数据"的定位冲突

**这条不因为技术上能做到而重新讨论。**

## 7. 行动权限边界:三级分权

这是本项目的核心安全模型。每一个工具在注册时必须声明自己的等级。

| 等级 | 含义 | 示例 | 策略 |
| --- | --- | --- | --- |
| **L1** | 只读 | 查邮件、查日历、查账单、检索记忆 | 自动放行,记审计日志 |
| **L2** | 写自己的地盘 | 建待办、改日历、写笔记、归类账单 | 自动放行,**必须可回滚**,记审计日志 |
| **L3** | 写外部世界 | 代发消息、提交表单、预约 | **强制拦截进审批队列**,人工确认后执行 |

**L3 之外明确不做:代付款、代下单。** 国内主流平台没有可用的第三方代付 API,
绕过去只能靠模拟操作,风险不可控且无法向朋友交代。

---

## 8. 非目标(明确不做的事)

写在这里的每一条,都是在讨论中被明确否决过的。想做之前先读否决理由。

| 不做 | 理由 |
| --- | --- |
| 通用 agent 平台 / 开源框架 | 目标是自己和朋友真的用,不是给开发者用 |
| 多 agent 竞争择优 | 生活任务缺乏客观优劣标准,且不值得 N 倍 token([ADR-005](04-tech-decisions.md#adr-005--不做多-agent-协作)) |
| 本地模型 / 完全离线 | 本地模型能力撑不起复杂推理,而隐私可以靠自托管 + 加密解决 |
| 接入微信聊天记录 | 无官方 API,封号风险,不能给朋友用(见 §6) |
| 代付款 / 代下单 | 无可用 API,风险不可控(见 §7) |
| 语音入口 | 链路长、延迟高,不解决核心痛点 |
| 自建 App | 需接四套厂商推送通道,P3 前投入产出比极差 |
