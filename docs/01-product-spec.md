# 01 · 产品定义

本文档记录已经确认的产品边界。**改动这里的任何一条,都意味着架构和计划要重新评估。**

---

## 1. 一句话定位

自托管的个人生活 agent —— 以邮箱、日历、手机通知、账单、笔记为数据底座,
**企业微信负责推送与审批、安卓 App 负责采集与查看**,
既能被问也能主动发现事情,所有"动外部世界"的操作都要经过人工审批。

---

## 2. 目标用户

| 优先级 | 用户 | 何时接入 |
| --- | --- | --- |
| 主 | 项目作者本人 | P0 |
| 次 | 作者的朋友(**非技术背景**) | P4,不早于此 |

**朋友放到 P4 是硬约束,不是排期偷懒。** 一旦有第二个用户,你就成了别人邮箱的 IMAP 授权码
和支付数据的保管人,这是法律责任而不只是技术责任。P0–P3 期间你可以随便重构、随便删库;
P4 之后不行。详见 [05 风险登记](05-risks.md#r1--代管他人凭据与支付数据)。

**明确不做**:面向陌生人的商业产品、面向开发者的开源框架。

---

## 3. 核心痛点(已确认,按优先级)

四条都是用户自述的真实高频困扰,不是设想出来的场景。

| # | 痛点 | 具体表现 | 首次交付 |
| --- | --- | --- | --- |
| 1 | **日程与待办** | 事情散在邮件、聊天、脑子里,记不住、排不出优先级 | P0 摘要里体现 → **P1 自动提取入日历** |
| 2 | **信息过载** | 邮件、资讯看不过来,想要自动筛选和每日摘要 | P0 |
| 3 | **财务与记账** | 钱花哪了不清楚,想要自动归类、预算预警、月度分析 | P2 |
| 4 | **生活安排执行** | 订票订餐、比价购物、预约这类"要跑腿"的事 | P3 |

排期理由:1 和 2 共用同一批数据源(邮箱 + 日历),放一起做边际成本最低,
且能最快验证"这东西你自己会不会每天看"这个核心问题。

---

## 4. 交互形态

**两个客户端,按"推"和"拉"分工**,不是主次关系:

| | 安卓 App | 企业微信 |
| --- | --- | --- |
| 方向 | 用户主动打开去**看**和**操作** | 系统主动**推**给用户 |
| 承担 | 数据采集、账本浏览、报表、预算、待确认队列、拍照记账 | 每日摘要、主动提醒、**审批交互卡片**、对话式问答 |
| 关键限制 | **不接收任何推送** | 无 |

### 为什么 App 不做推送

自建 App 当初被否决,理由只有一条:**要接小米/华为/OPPO/vivo 四套厂商推送通道**,
投入产出比极差。而这条成本**只在 App 需要接收推送时才存在**。

本项目的 App 只做两件事 —— 读手机上的通知往外发、以及打开时向服务端拉数据。
它从不接收推送,因此**完全不需要厂商通道**,那条否决理由整个消失。
推送继续由企微承担,那是它唯一不可替代的能力。

详见 [ADR-014](04-tech-decisions.md#adr-014--客户端做完整-app-但不接收推送)。

### 为什么推送非企微不可

- 能无限制主动推送(不像微信服务号受订阅通知和审核限制)
- 支持交互式模板卡片 + 按钮回调(**审批流程的硬需求**)
- 消息可以转投到微信里接收,非技术背景的朋友学习成本接近零

被否决的方案见 [ADR-001](04-tech-decisions.md#adr-001--推送与审批入口选企业微信)。

### 能力降级矩阵

装了 App 才有完整能力。这不是可选项,而是**记账和群摘要的物理前提** ——
交易通知和微信消息只存在于手机上,服务端够不着。

| 用户情况 | 记账 | 群消息摘要 | 每日摘要 / 问答 / 审批 |
| --- | --- | --- | --- |
| 安卓 + 装 App | ✅ 实时入账 | ✅ | ✅ |
| 安卓 + 只用企微 | ⚠️ 退化为月度导出 | ❌ | ✅ |
| **iOS** | ⚠️ 只能月度导出 | ❌ | ✅ |

iOS 那一行**不是排期问题,是平台限制** —— iOS 没有通知监听的等价能力。
若将来做 iOS 版,也只能是"只看不采"的只读客户端。

### 其他入口

| 入口 | 阶段 | 说明 |
| --- | --- | --- |
| 邮件 | P1 | 兜底通道,推送失败时降级 |
| Web 控制台 | P4 | **从 P3 推迟** —— 移动端查看已由 App 覆盖,只剩数据导出与账号管理,那是 P4 的合规需要 |
| 桌面客户端 | 不在规划内 | 与 App 和 Web 三重重复 |
| 语音 | 不在规划内 | 链路长、延迟高,等前面都稳定了再说 |
| iOS App | 不在规划内 | 做不了通知监听,只能是只读客户端,价值有限 |

## 5. 主动性:双模式

**对话式(被动)**:用户在企微里提问或下指令,系统响应。

**事件驱动(主动)**:定时任务和事件订阅触发,系统主动推送。

主动是这个产品的价值主体,但**也是最容易毁掉它的东西**。误报多两次,用户就把通知关了,
之后再也不会打开。因此约束如下:

- 主动能力从**每天一条固定时间的摘要**起步,不做随机打断
- 任何新增的主动推送规则,先跑"影子模式"(只记录不推送)观察一周
- 每条主动推送都要能一键关闭该类规则
- 硬上限:非用户主动触发的推送,每天不超过 3 条

## 6. 数据源

### 第一期接入(已确认)

| 数据源 | 阶段 | 接入方式 | 备注 |
| --- | --- | --- | --- |
| 邮箱 | P0 | IMAP + 授权码(QQ / 163 / 126) | 账单、行程、待办的主要流入口 |
| 日历 | P0 | 企业微信日程 API | 与推送入口复用同一套自建应用凭据 |
| 微信 / 群消息通知 | P1 | 安卓官方通知监听 → webhook | **只读**,用于群消息摘要与日程提取 |
| 笔记 / 待办工具 | P1 | 官方 API | 具体选型待定,作记忆落地层 |
| 交易实时通知 | P2 | 安卓端转发短信 + App 通知 → webhook | **记账主通道**,刷卡当场入账 |
| 信用卡对账单 | P2 | 银行月度账单邮件(PDF,带密码) | 月度对账与金额校准,完全自动 |
| 账单与支付记录 | P2 | App 内手动导出 → 邮件送达 → 自动解析 | 月度补全真实商户名与订单号,每月手动触发两次导出 |

**采集与消费分两期**:安卓 App 在 P1 就装好并跑通通知监听链路,
但 P1 只消费微信/群消息;银行与支付类通知的白名单和记账链路在 P2 才打开。
先用一条低风险的链路验证采集器能不能稳定活着,再把账目压上去。

**记账以实时通知为主、月度账单为辅**,两阶段入账的设计与缺口见
[ADR-012](04-tech-decisions.md#adr-012--账单采集以实时通知为主导出账单为辅)。
硬前提:App 必须装在**日常使用的安卓主力机**上(备用机不行,原因见
[ADR-012](04-tech-decisions.md#adr-012--账单采集以实时通知为主导出账单为辅)),
iOS 没有等价方案。

### 微信:只读接入,不做自动回复

微信信息密度最高,但接入方式决定风险。**读通知和 hook 客户端是两件事**:

| 做什么 | 怎么做 | 结论 |
| --- | --- | --- |
| 读微信通知(好友消息、群消息、支付通知) | 安卓官方 `NotificationListenerService` | ✅ 做。不碰微信客户端,无协议指纹 |
| 协议逆向(itchat / 网页版协议) | 伪装成微信客户端 | ❌ 封号风险,绝不能给朋友用 |
| 客户端 hook(Xposed / 无障碍服务) | 注入或模拟点击微信 | ❌ 同上,且 ROM 适配是无底洞 |
| **自动回复好友、代发消息** | 必须靠上面两种之一 | ❌ 最易被风控识别;且它本来就是 L3,合规做法是草稿+审批,与"自动"矛盾 |

**能力边界要说清**:通知监听只能拿到通知栏实际展示过的内容 —— 免打扰的群拿不到、
长消息会截断、撤回和历史消息完全拿不到。所以这块能力叫"**在线期间的群消息摘要**",
不是"聊天记录分析"。详见 [ADR-010](04-tech-decisions.md#adr-010--微信只做只读接入走官方通知监听)。

## 7. 行动权限边界:三级分权

这是本项目的核心安全模型。每一个工具在注册时必须声明自己的等级。

| 等级 | 含义 | 示例 | 策略 |
| --- | --- | --- | --- |
| **L1** | 只读 | 查邮件、查日历、查账单、检索记忆 | 自动放行,记审计日志 |
| **L2** | 写自己的地盘 | 建待办、改日历、写笔记、归类账单 | 自动放行,**必须可回滚**,记审计日志 |
| **L3** | 写外部世界 | 代发消息、提交表单、预约 | **强制拦截进审批队列**,人工确认后执行 |

**L3 之外明确不做:代付款、代下单。** 国内主流平台没有可用的第三方代付 API,
绕过去只能靠模拟操作,风险不可控且无法向朋友交代。

---

## 8. 非目标(明确不做的事)

写在这里的每一条,都是在讨论中被明确否决过的。想做之前先读否决理由。

| 不做 | 理由 |
| --- | --- |
| 通用 agent 平台 / 开源框架 | 目标是自己和朋友真的用,不是给开发者用 |
| 多 agent 竞争择优 | 生活任务缺乏客观优劣标准,且不值得 N 倍 token([ADR-005](04-tech-decisions.md#adr-005--不做多-agent-协作)) |
| 本地模型 / 完全离线 | 本地模型能力撑不起复杂推理。**注意:自托管保护的是存储,保护不了推理** —— 内容仍会发给外部模型供应商,这是明确接受的代价,缓解见 [R12](05-risks.md#r12--外部-llm-供应商侧的数据暴露) |
| 微信自动回复 / 代发消息 | 必须 hook 微信客户端,封号风险且不能给朋友用;它本来就是 L3,合规做法是草稿+审批(见 §6) |
| 微信协议逆向 / 客户端 hook | 同上。只走官方通知监听读取(见 §6) |
| 代付款 / 代下单 | 无可用 API,风险不可控(见 §7) |
| 语音入口 | 链路长、延迟高,不解决核心痛点 |
| **接收推送的** App | 需接小米/华为/OPPO/vivo 四套厂商推送通道。注意:**采集与查看用的安卓 App 是做的**,它不接收推送因而无此成本(见 §4) |
