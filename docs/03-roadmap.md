# 03 · 开发计划

**分期原则:每一期结束后都必须是"能真的用起来"的状态。**
不接受"先搭三个月基础设施再说"。每期都有明确的验收标准和**退出条件**
(即"什么情况下应该停下来修前面,而不是继续往下做")。

工作量估计按**一人全职**计,业余投入请自行乘系数。

---

## 总览

| 期 | 主题 | 验收标准 | 估计 |
| --- | --- | --- | --- |
| **P0** | 邮箱+日历 → 每日摘要 | 你自己每天真的会打开它 | 2–3 周 |
| **P1** | 记忆层 + 主动触发 | 它开始"记得你",且提醒不烦人 | 3–4 周 |
| **P2** | 财务与账单 | 你不再手动记账 | 3–4 周 |
| **P3** | 审批执行 + Web 控制台 | 你敢让它代发一条真实消息 | 4–6 周 |
| **P4** | 多用户托管 | **朋友才在这一步进来** | 4–6 周 |

---

## P0 · 自己每天会打开它

**唯一目标**:验证两件事 —— 你自己会不会每天看,以及 LLM 摘要质量够不够。
这两个答案决定后面所有事情值不值得做。

### 范围

- 数据表 schema(含 `user_id` 与凭据加密字段,见 [架构 §6](02-architecture.md#6-为多用户预留p4-前必须做到))
- 工具注册表 + 分权网关 + 审计日志(**骨架必须在 P0 到位**,后面往里填)
- 邮箱采集(IMAP / Gmail API)、日历采集(CalDAV)
- 事件归一化写入 `raw_events`
- 每日摘要生成(直调 Claude API,不套框架)
- 企业微信自建应用 + 模板卡片推送
- 基础对话:在企微里提问,agent 用 L1 工具回答

### 不在范围内

L2/L3 工具、记忆抽取、向量检索、账单、Web 界面、任何朋友相关的东西。

### 验收标准

连续 14 天每天收到摘要,你主观判断"这条有用"的比例 **> 70%**。

### 退出条件(出现以下情况先停下来修,不要往 P1 走)

- 摘要质量差到你自己都不看 → 问题多半在**数据归一化**而不是 prompt,回去修归一化
- 邮箱/日历数据拉取不稳定 → 先解决可靠性,主动推送的信任建立在稳定之上
- 企微卡片推送有延迟或丢失 → 入口不可靠,后面全是空中楼阁

## P1 · 记忆层与主动触发

**目标**:让它开始"记得你",并且主动说话时不招人烦。

### 范围

- 实体抽取与别名归并(`entities` / `entity_aliases`)
- 事实库 `facts`,**强制携带 provenance**
- 笔记 / 待办工具接入(具体选型在本期确定)
- pgvector 向量索引,用于模糊召回
- 规则引擎 + 影子模式 + 频率闸门
- L2 工具首次上线(建待办、改日历),含回滚信息记录
- 邮件兜底推送通道

### 验收标准

- 能正确回答:"上次和 X 聊的是什么"、"我这周答应了谁什么事"
- 主动提醒**误报率 < 20%**(先跑一周影子模式统计,再决定是否转 active)
- 你没有关掉任何一类通知

### 退出条件

- 误报率降不到 20% 以下 → 收紧规则或退回影子模式,**不要靠调 prompt 硬压**
- 记忆里开始出现你不认可又说不清来源的条目 → provenance 链路有漏,先补

---

## P2 · 财务与账单

**目标**:你不再手动记账。

### 范围

- 支付宝 / 微信账单 CSV 导入与解析(格式不稳定,需容错)
- 银行短信 / 信用卡邮件解析
- 归类:**规则表 + LLM 混合** —— 高频商户走规则(便宜且稳定),
  新商户才问 LLM,结果写回规则表([ADR-008](04-tech-decisions.md#adr-008--账单归类用规则llm-混合))
- 预算设定与超支预警
- 月度分析报告(企微卡片 + 邮件长版)

### 验收标准

- 一个月账单自动归类准确率 **> 90%**
- 你连续一个月没有手动记账

### 退出条件

- 账单导出格式频繁变动导致解析经常挂 → 先做格式容错和失败告警,不要静默丢数据
- 归类准确率上不去 → 检查是不是规则表没有沉淀,而在反复问 LLM

---

## P3 · 审批执行与 Web 控制台

**目标**:你敢让它代你发一条真实消息。这是信任的分水岭。

### 范围

- L3 工具首次上线(代发消息、提交表单、预约)
- 审批队列:幂等键、超时过期、人类可读预览
- 企微交互卡片回调链路(签名校验、时效校验)
- **引入状态机编排**(LangGraph 或同类)—— 审批要求流程暂停数小时后从断点恢复,
  这才是引入框架的真实理由([ADR-002](04-tech-decisions.md#adr-002--p0p2-不引入-agent-编排框架))
- Web 控制台:审批历史、账单明细、记忆管理
- 桌面客户端(可选,优先级低于 Web)

### 验收标准

- 完成 20 次真实 L3 操作,**零重复执行、零越权**
- 审批卡片的预览文本你一眼能看懂在做什么,不需要点开细节

### 退出条件

- 出现任何一次越权或重复执行 → 停止 L3 上线,回去修网关和幂等
- 你自己不敢点"同意" → 预览做得不够清楚,或回滚机制不可信

---

## P4 · 多用户托管

**只有走到这里,朋友才进来。**

### 前置硬门槛(不满足则不开放)

- [ ] 完成一次安全审查,[05 风险登记](05-risks.md) 中所有 **高** 等级风险已有缓解措施
- [ ] 凭据加密从环境变量升级为 KMS 或等价方案
- [ ] 备份与恢复演练成功至少一次
- [ ] 写好隐私说明,明确告知朋友:你能看到什么、数据存在哪、如何删除

### 范围

- 用户体系与租户隔离(数据层强制 `user_id` 过滤,不靠应用层自觉)
- 凭据 KMS 管理
- 每用户配额与**成本上限**(主动扫描的开销随用户数线性增长)
- 企业微信多成员配置与"微信插件"接收链路验证
- 备份、恢复、数据导出与删除

### 验收标准

一位朋友连续使用两周,无数据事故、无越权、无成本失控。

---

## 开发节奏约定

- **一个可独立描述的改动 = 一次提交 = 一次推送。** 不攒批。
- 提交信息说清**为什么**这么改,不只是改了什么。三个月后你只会记得 why。
- 每期结束写一份复盘,把新学到的和被推翻的结论回写进
  [04 技术决策](04-tech-decisions.md)。
- 任何时候引入新依赖或新技术,先在 04 里补一条 ADR,写明**被否决的替代方案**
  和**将来重新评估的触发条件**。
