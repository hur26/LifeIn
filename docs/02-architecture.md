# 02 · 架构设计

本文档描述系统分层、数据模型和三个核心机制(记忆、审批、主动触发)。

**设计原则**:数据整合和长期记忆是本项目的重心,agent 编排不是。
架构上的复杂度预算优先花在"记住"和"刹车"上,而不是"怎么调度 agent"。

---

## 1. 分层总览

```
┌─────────────────────────────────────────────────────────┐
│ 接入层    企微(推送/审批)│ 安卓 App(采集/查看)│ 邮件兜底 │
├─────────────────────────────────────────────────────────┤
│ 触发层    定时调度 · 数据源轮询 · 规则扫描 · 用户消息      │
├─────────────────────────────────────────────────────────┤
│ 编排层    P0–P2: 按领域分工的 agent 集,同进程运行        │
│           P3+:  引入状态机以支持"暂停等审批"的长流程       │
├─────────────────────────────────────────────────────────┤
│ 治理层    工具分权网关 · 审批队列 · 审计日志 · 成本核算     │  ← 所有工具调用必经
├─────────────────────────────────────────────────────────┤
│ 能力层    邮箱 · 日历 · 笔记 · 通知 · 账单 · 检索 · 推送   │
├─────────────────────────────────────────────────────────┤
│ 记忆层    事件流(时序) + 实体库(结构化) + 事实库 + 向量索引 │
├─────────────────────────────────────────────────────────┤
│ 存储      PostgreSQL + pgvector(单库)                    │
└─────────────────────────────────────────────────────────┘
```

**治理层是强制通道。** 能力层的任何工具都不允许被编排层直接调用,
必须经过治理层的分权网关。这一条在代码结构上强制,不靠约定。

### 1.0 "在代码结构上强制"具体是什么

**这一段是补出来的。** 原来只有"工具注册表 + 统一调用入口"这半句,
而那两样都**不阻止任何人绕过去**:`from lifein.tools.transaction import record`
然后直接调,注册表拦不住,网关也不知道。铁律 4 那句"不靠约定"
在此之前恰恰只是约定。

三道,一道比一道早:

| 哪一道 | 什么时候发现 | 挡什么 |
| --- | --- | --- |
| **`@tool` 装饰器包一层运行时守卫** | 真调下去的那一刻 | 直接调用工具函数 —— 抛 `DirectCall`,不执行 |
| **导入检查**(`tests/test_layering.py`) | 跑测试时 | 编排层 import 能力层 —— 连写出来的机会都没有 |
| **代码评审** | 提交前 | 上面两道的边角 |

运行时那道靠一个 `ContextVar`:网关调工具之前把它设上,工具函数进门先看
那个值。**没有它的话"过网关"和"不过网关"在代码里长得一模一样** ——
两者都是 `func(args, ctx)`。

**有一处合法的例外:审批执行。** L3 的调用在进审批队列那一刻已经过了网关
(等级、白名单、入参、`trust` 全查过了),人点同意之后执行 job 直接调工具 ——
那时再过一次网关只会把它重新变成一条审批。所以
[`jobs/approval_execute.py`](../lifein/jobs/approval_execute.py) 显式开一次
那个上下文,而**"只有它和网关能开"由测试盯着**。

> **在 Python 里做不到"不可能绕过"**,只能做到"绕过需要显式地写出来,
> 而且写出来会被看见"。这三道要的就是后者 —— 一个想绕过的人必须
> import 一个名字叫"我在故意绕过网关"的东西。

## 2. 记忆层(本项目的重心)

生活助手的价值几乎全部来自"它记得你"。记忆分四层,职责严格分开。

### 2.1 事件流 · `raw_events`

所有数据源摄入的原始事件,**只追加不修改**。它是全系统的事实来源,
其他所有记忆都必须能追溯回这里。

| 字段 | 说明 |
| --- | --- |
| `id` | |
| `user_id` | **P0 只有一个用户也必须带**,见 §6 |
| `source` | `email` / `calendar` / `note` / `notification` / `transaction` |
| `external_id` | 源系统 ID,用于去重,与 source 组成唯一键 |
| `occurred_at` | 事件真实发生时间(非摄入时间) |
| `ingested_at` | |
| `raw` | 原始 payload(JSONB) |
| `normalized` | 归一化后的结构(JSONB) |

**归一化是这一层的核心脏活**:邮件、日历、账单格式完全不同,
要抽出统一的 `{标题, 时间, 参与方, 金额, 正文}` 骨架,上层才能统一处理。
这部分没有技术含量但决定成败。

### 2.2 实体库 · `entities` + `entity_aliases`

从事件流中抽取出的**长期存在的东西**:人、商户、地点、项目、订阅服务、周期性事务。

关键难点是**别名归并** —— "张三"、"张总"、"zhangsan@x.com" 是同一个人。
用 `entity_aliases` 表维护映射,新别名先低置信度写入,累积证据后提升。

### 2.3 事实库 · `facts`

用户的稳定偏好和属性:"不吃香菜"、"每周三晚上健身"、"房租每月 5 号扣"。

| 字段 | 说明 |
| --- | --- |
| `statement` | 事实本身 |
| `provenance` | **来源事件 id 数组 —— 必填** |
| `confidence` | 推断出的事实置信度 |
| `confirmed_by_user` | 用户是否确认过 |
| `valid_from` / `valid_until` | 事实会过期(换工作、搬家) |

**`provenance` 是硬约束。** 没有来源的记忆无法验证、无法纠错,时间一长就变成
一堆用户不认可又删不掉的噪音。任何写入 `facts` 的路径都必须带来源。

### 2.4 向量索引

对事件和实体的文本表示做 embedding,存在 pgvector,用于模糊召回。

**检索策略:结构化优先,向量兜底。** "上个月在星巴克花了多少" 应该走 SQL 聚合,
不是 RAG。向量检索只用于"我记得之前有个关于 X 的事"这类模糊查询。
一上来就把所有东西塞进向量库是常见错误,又贵又不准。

## 3. 治理层:分权与审批

### 3.1 工具注册与分权

每个工具在注册时**必须**声明等级(定义见 [产品定义 §7](01-product-spec.md#7-行动权限边界三级分权)):

| 等级 | 网关行为 |
| --- | --- |
| L1 只读 | 放行 + 审计 |
| L2 写自己地盘 | 放行 + 审计 + **记录回滚信息** |
| L3 写外部世界 | **拦截 → 审批队列** |

未声明等级的工具**默认按 L3 处理**(拒绝放行),避免新增工具时忘记标注造成越权。

### 3.2 审批流程

```
agent 请求调用 L3 工具
        ↓
分权网关拦截,不执行
        ↓
写入 approvals 表(pending),生成 idempotency_key 与人类可读预览
        ↓
推送企微交互卡片:【同意】【拒绝】【修改后同意】
        ↓
用户点击 → 企微回调 → 校验签名与时效 → 执行工具
        ↓
更新卡片为结果态 + 写审计日志
```

约束:

- **超时自动过期**,默认 24 小时,过期后不再可执行(防止用户几天后误点)
- **幂等**:执行前检查 `idempotency_key`,回调重复投递不会重复执行
- **预览必须是人话**:卡片上展示"给张三发消息:……",不是 JSON payload
- 审批记录**永久保留**,是出问题时唯一的追溯依据

### 3.3 审计与成本

`tool_calls` 表记录每一次调用:工具名、等级、入参摘要、结果、耗时、
以及**该次 agent 回合的 token 消耗与费用**。

成本核算不是锦上添花 —— 主动扫描意味着**每天固定烧钱且随用户数线性增长**,
不从第一天记账,P4 开放给朋友时你不知道自己在承担多少。

## 4. 触发层:主动性的实现

| 触发类型 | 说明 |
| --- | --- |
| 定时任务 | 每日摘要、周期性对账 |
| 数据源轮询 | 邮箱/日历增量拉取 |
| 外部推送入口 | 安卓 App 采集侧转发的通知(webhook)—— 唯一的 push 型数据源,见 [§8](#8-安卓-appp1-起) |
| 规则扫描 | 在事件流上匹配条件,命中则触发 agent |
| 用户消息 | 企微消息回调 |

两个必须内建的机制:

**影子模式**:每条主动规则有 `mode ∈ {shadow, active}`。shadow 只写
`push_log` 不真推送。新规则一律先 shadow 跑一周,人工看误报率再转 active。

**频率闸门**:非用户触发的推送每天硬上限 3 条(见
[产品定义 §5](01-product-spec.md#5-主动性双模式))。超限时合并或丢弃,
由 `push_log` 计数强制,不靠规则自觉。

## 5. P0 完整链路

这是第一期唯一要打通的路径,用它验证所有分层是否成立:

```
APScheduler 08:00 触发
    ↓
拉取昨日邮件(IMAP)+ 今日日历(企微日程 API)         [L1 工具,网关放行]
    ↓
归一化 → 写入 raw_events(按 source+external_id 去重)
    ↓
构造 prompt,直调外部 LLM API 生成摘要
    ↓
渲染企业微信 markdown 消息(模板卡片随审批在 P3,见 03)
    ↓
推送 → 写 push_log + tool_calls(含 token 成本)
```

P0 不涉及 L2/L3、不涉及记忆抽取、不涉及向量检索。
但**数据表结构、分权网关、审计日志从 P0 就到位**,后面几期是往里填东西,不是重搭。

## 6. 为多用户预留(P4 前必须做到)

朋友接入在 P4,但有三件事**必须从 P0 第一行代码就做**,否则 P4 时要大改:

1. **所有表带 `user_id`。** 哪怕 P0 只有一个用户,也不要省。事后加 user_id
   并回填、改所有查询,是最典型的痛苦重构。
2. **凭据字段级加密。** IMAP 授权码、企微 access_token 等凭据存库前加密,密钥走环境变量或 KMS。
   不要"先明文存,P4 再加密" —— 那时库里已经有真实凭据了。
3. **代码里不假设单用户。** 所有数据访问函数第一个参数是 `user_id`,
   不要写全局单例的当前用户。

这三条的成本在 P0 几乎为零,在 P4 会是几周的重构。

## 7. 编排层:agent 按领域分工

不是一个大 agent 配超长 prompt,也不是多个进程互相调用。**按领域拆 agent、
全部跑在同一个进程里** —— 拆的是职责和评测,不是部署单元。

| agent | 职责 | 首次出现 | 可用工具 |
| --- | --- | --- | --- |
| **摘要** | 把当日事件流写成一条推送 | P0 | L1 只读 |
| **问答** | 回答企微里的提问 | P0 | L1 只读 + 检索 |
| **记忆** | 实体抽取、别名归并、事实沉淀 | P1 | L1 + 写 `facts` / `entities` |
| **日程** | 从邮件与群消息提取日程待办 | P1 | L1 + L2 写日历 / 待办 |
| **记账** | 通知 → 结构化账单 + 防误判 + 归类 | P2 | L1 + L2 写账单 |
| **执行** | L3 操作的规划与审批预览生成 | P3 | 只能**请求** L3,不能执行 |

### 每个 agent 必须声明的五件事

这是 agent 的**契约**,缺一项不允许注册:

1. **输入类型** —— 它接受哪些事件或请求
2. **工具白名单** —— 网关按 `(agent, tool)` 双重校验,不只看工具等级。
   记账 agent 拿不到发消息的工具,哪怕那个工具是 L1
3. **输出 schema** —— 结构化,能被代码校验,不是自由文本
4. **失败行为** —— 拿不准时做什么。记账是"进待确认",日程是"不写日历"。
   **默认行为必须是不动作**,不是猜一个
5. **独立评测集** —— 至少 20 条真实样本 + 期望输出

第 5 条是这套划分的**真正目的**:改记账 agent 的 prompt 时,能立刻知道
有没有把摘要 agent 弄坏。一个大 prompt 做不到这件事。

### 为什么同进程

拆进程解决的是独立扩缩容和独立发布,P0–P2 都不需要;换来的是分布式追踪、
部署编排、版本兼容,全是负担。

而"方便测试和迭代维护"由**契约**保证,不由进程边界保证 ——
只要工具白名单和评测集是隔离的,改一个 agent 不会影响另一个,
这跟它们跑在几个进程里无关。

**什么时候拆进程**:某个 agent 需要独立扩缩容(记账在月底账单集中到达时
有可能)、发布节奏明显不同、或 P3 引入状态机后长流程需要独立 worker。

详见 [ADR-002](04-tech-decisions.md#adr-002--p0p2-不引入-agent-编排框架)
与 [ADR-013](04-tech-decisions.md#adr-013--agent-按领域分工同进程运行)。

**P3 才需要状态机**:审批流程要求"暂停几小时等人点按钮,然后从断点恢复",
这是长时间运行、可中断、可持久化的流程,那时才值得引入 LangGraph 这类框架。

## 8. 安卓 App(P1 起)

系统里唯一一个**跑在服务器之外**的组件,承担三件事:**采集**、**查看/操作**、
以及 P1 起新增的**执行**(把日程写进手机系统日历)。

它存在的根本原因是采集:交易通知和微信消息**只存在于手机上**,
服务端够不着,Web 也拿不到。P1 之后又多一条同样的理由:
**系统日历也只存在于手机上**,没有服务端接口
([ADR-020](04-tech-decisions.md#adr-020--待办与日程落在自己的-app企微退出主链路))。

**硬约束:App 不接收任何推送。** 不集成厂商推送 SDK,主动触达走消息通道
(微信,邮件兜底)。这条不是妥协而是成本边界 —— 一旦开始收推送,就要接四套
厂商通道并跟着各家政策维护,那正是自建 App 当初被否决的全部理由。见
[ADR-014](04-tech-decisions.md#adr-014--客户端做完整-app-但不接收推送)。

**桌面小组件不在这条禁令里。** 它是 `AppWidgetProvider` + `WorkManager`
**定时去拉**,没有任何一方向手机推送 —— 禁的是"接收推送",不是"主动刷新"。
但也正因为是拉的,它受各家省电策略限制:**小组件是"看一眼"的入口,
不是提醒机制**,真正的提醒仍然走消息通道。

技术选型:原生 Kotlin,不做 iOS,见
[ADR-015](04-tech-decisions.md#adr-015--app-用原生-kotlin只做安卓)。

### 8.1 采集侧:只做三件事,不做判断

```
安卓设备(常驻)
    │
    ├─ 短信监听 ──┐
    │             ├─→ 白名单过滤 → 验证码丢弃 → HTTPS POST ──→ 服务端 /ingest
    └─ 通知监听 ──┘
```

采集器**不解析、不归类、不判断**,只做过滤和转发。所有语义处理都在服务端 ——
手机端逻辑越薄,越不需要跟着业务改动重新发版,这一点在真机上迭代过就知道有多重要。

### 8.2 监听范围

| 来源 | 用途 | 阶段 |
| --- | --- | --- |
| 银行交易短信 | 记账主通道 | P2 |
| 支付宝 / 微信 / 云闪付 / 银行 App 通知 | 记账主通道 | P2 |
| 美团 / 京东 / 拼多多等订单通知 | 补全商户与品类 | P2 |
| 微信好友与群消息通知 | 群消息摘要、日程提取 | P1 |
| 手机系统日历(读) | 已有日程作为摘要素材,替代原来的企微日程 | P1 |

微信**只读、不写**,边界见
[ADR-010](04-tech-decisions.md#adr-010--微信只做只读接入走官方通知监听)。

### 8.3 采集侧的三条硬约束

1. **发件人 / 包名白名单,默认拒绝。** 不在白名单里的一律不转发。
   新增来源要显式加白,不做"先全转发、服务端再过滤"。
2. **验证码类内容在手机端就丢弃**,服务端入库前再过一次正则。
   双保险的理由见 [R10](05-risks.md#r10--手机端采集器的越权读取)。
3. **传输走 HTTPS + 独立密钥**,入口做来源校验与重放保护。
   绝不用明文邮件转发交易或聊天内容。

### 8.4 查看侧

App 打开时才向服务端拉数据,**不常驻、不推送**(小组件除外,它按 `WorkManager`
的周期去拉):

| 功能 | 说明 |
| --- | --- |
| **待办列表与桌面小组件** | P1 的主界面。待办的落地表在服务端,**App 是它的界面不是数据源** —— 换手机不丢(ADR-020) |
| 账本浏览、月度报表、预算与超支 | 列表和图表在 App 里看比消息卡片方便得多 |
| **待确认队列** | 防误判拦下来的账目在这里快速处理,是使用频率最高的界面 |
| 拍照记小票、手动补一笔 | 补现金与纸质票据这条长尾 |
| 记忆与实体浏览 | 查看、否定、纠正 `facts` 里的条目 |
| 采集器状态与白名单配置 | 心跳、掉线原因、白名单增删 |

查询接口与采集上报**使用不同凭据**:采集端只能写不能读,
手机丢失或 App 被逆向不等于账本被读走。见 [R11](05-risks.md#r11--app-直连服务端的认证面)。

### 8.5 执行侧:把日程写进系统日历(P1 起)

服务端的 L2 工具"建日程"写的是 `todos` 里的一行,**副作用真正发生在设备上**:
App 拉到未同步的条目 → 写入 `CalendarContract` → 把系统日历的 event id
回报给服务端。那个 id 就是回滚信息(06 §2.11)。

这带来一条别处没有的性质:**服务端只能保证"意图已记录",保证不了"设备已执行"。**
所以 `device_ref` 为空就是没落地,App 一联网就补,而且这个状态在 App 上看得见 ——
**看得见的延迟可以接受,静默丢失不行。**

### 8.6 已知能力边界

- **必须装在日常使用的安卓主力机上**,备用机不行:银行短信只到 SIM 卡所在设备,
  微信与支付宝个人号同一时间只能在一台手机登录。这也意味着**保活难度更高** ——
  主力机上你会频繁清后台,厂商 ROM 对后台进程也更激进
- iOS 无等价方案。iOS 用户只能用消息通道,记账退化为月度导出
  ([产品定义 §4 降级矩阵](01-product-spec.md#4-交互形态))
- 通知只能拿到系统实际展示过的内容:免打扰的群拿不到、长消息截断、
  撤回与历史消息拿不到、多条可能被折叠成"[3 条] ……"
- 安卓后台保活受厂商 ROM 限制。采集器必须**定期心跳上报**,
  服务端超过阈值没收到心跳就告警 —— **静默掉线是这条链路最可能的失效方式**,
  而且它失效时系统表现得一切正常,只是账目和提醒悄悄变少了

## 9. 扩展点:加新功能要动几个文件

"架构支持扩展"不能停在口号上。下面四个扩展点各自定义了一个接口,
**加一个新的 X,只应该改这一处**。如果实际改动超出了,说明抽象漏了,要回来修。

### 9.1 数据源适配器

```
interface SourceAdapter:
    source: str                       # 'email' / 'calendar' / 'notification' / ...
    fetch(since) -> list[RawEvent]    # 拉取型
    # 或 handle(payload) -> list[RawEvent]   # 推送型(采集器 webhook)
```

新增一个数据源 = 实现一个适配器 + 写一段归一化。**不改事件流、不改 agent、
不改推送**。归一化写不出来说明这个源还没想清楚,不要先接进来再说。

### 9.2 工具注册表

```
@tool(name=..., level=L1|L2|L3, schema=..., rollback=...)
```

声明即被网关接管,自动获得分权、审计、成本记录。
**未声明等级的工具默认按 L3 拒绝**,避免新增工具时忘记标注造成越权。

### 9.3 agent 注册表

```
@agent(name=..., inputs=..., tools=[...], output_schema=..., on_low_confidence=..., evalset=...)
```

即 §7 的五项契约。注册后自动获得审计、成本核算与评测入口。

### 9.4 推送通道

```
interface Channel:
    send(user_id, card) -> delivery_id
```

企微与邮件实现同一个接口。**安卓 App 不是推送通道** ——
它不接收推送([ADR-014](04-tech-decisions.md#adr-014--客户端做完整-app-但不接收推送))。
接口留出来是为了平台政策变动时能换成飞书或其他
([R6](05-risks.md#r6--平台政策变动)),不是为了现在就做多通道。
