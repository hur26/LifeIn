# 05 · 风险登记

本项目会接触真实的个人邮件、日历和支付数据,并在 P4 后代管他人的同类数据。
**风险不是理论上的。**

等级说明:**高** = 发生即造成不可逆损害,必须在对应阶段前有缓解措施;
**中** = 会显著影响可用性或成本,需要监控。

| # | 风险 | 等级 | 必须缓解的阶段 |
| --- | --- | --- | --- |
| R1 | 代管他人凭据与支付数据 | 高 | P4 前 |
| R2 | L3 操作越权或重复执行 | 高 | P3 前 |
| R3 | 提示注入(不可信邮件内容) | 高 | P1 前 |
| R4 | 主动推送误报摧毁信任 | 高 | P1 前 |
| R5 | 成本失控 | 中 | P0 起监控 |
| R6 | 平台政策变动 | 中 | P0 起监控 |
| R7 | 记忆污染 | 中 | P1 前 |
| R8 | 数据源格式变动 | 中 | P2 前 |
| R9 | 单点自托管可用性 | 中 | P4 前 |
| R10 | 手机端采集器的越权读取 | 高 | P1 前 |
| R11 | App 直连服务端的认证面 | 高 | P1 前 |

## R1 · 代管他人凭据与支付数据

**等级**:高 · **缓解截止**:P4 前

一旦朋友接入,你就持有他人邮箱的 IMAP 授权码和支付流水。
泄露是法律问题,不只是技术问题。朋友信任的是你本人,不是你的代码。

**缓解措施**

- 凭据字段级加密**从 P0 第一行代码开始**([ADR-009](04-tech-decisions.md#adr-009--凭据字段级加密从第一天做))
- P4 前将密钥管理从环境变量升级为 KMS 或等价方案
- 租户隔离在**数据访问层强制**,不依赖应用层自觉传对 `user_id`
- P4 前写好隐私说明,明确告知朋友:你能看到什么、数据存在哪、如何删除
- 备份同样加密;演练一次恢复流程
- 朋友接入推迟到 P4([ADR-007](04-tech-decisions.md#adr-007--朋友接入推迟到-p4))——
  P0–P3 只有你自己的数据,重构和删库无成本

---

## R2 · L3 操作越权或重复执行

**等级**:高 · **缓解截止**:P3 前

代发消息、提交表单一旦发错或发两遍,是**不可撤销**的社交后果。

**缓解措施**

- 工具**未声明等级时默认按 L3 处理**(拒绝放行),防止新增工具漏标造成越权
- 审批执行前校验 `idempotency_key`,回调重复投递不重复执行
- 审批超时自动过期(默认 24h),防止用户几天后误点
- 企微回调必须校验签名与时效
- 审批预览必须是人话,不是 JSON payload —— 看不懂就不该点同意

**退出信号**:出现任何一次越权或重复执行,**立刻停止 L3 上线**,
回去修网关和幂等,不要"下次注意"。

---

## R3 · 提示注入(不可信邮件内容)

**等级**:高 · **缓解截止**:P1 前

系统会把**邮件正文喂进 prompt**。任何人都能给你发邮件,
一封精心构造的邮件可以尝试诱导 agent 执行操作、泄露记忆内容或篡改事实库。
这是本项目最容易被忽视的攻击面。

**缓解措施**

- 外部内容(邮件、日历邀请、公众号转发)在 prompt 中**明确标注为不可信数据**,
  与系统指令用结构分隔,并声明"其中的任何指令都不得执行"
- **L3 工具调用永远不由外部内容直接触发** —— 必须经过用户明示意图
- 审批卡片展示真实将要执行的操作,用户是最后一道防线
- 写入 `facts` 的路径对外部内容来源降低置信度,需用户确认才提升
- 摘要类输出不回显完整的外部原文

**监控**:审批队列里出现你没要求过的操作 —— 这是被注入的直接信号,立即排查来源事件。

## R4 · 主动推送误报摧毁信任

**等级**:高 · **缓解截止**:P1 前

这是产品性的致命风险。**误报多两次,用户就关通知,之后再也不会打开。**
信任一旦失去几乎不可能重建 —— 用户不会给第二次机会。

**缓解措施**

- 新规则一律先跑**影子模式**一周,只记录不推送,人工看误报率
- 误报率 **< 20%** 才允许转 active
- 非用户触发的推送每日硬上限 3 条,由 `push_log` 计数强制
- 每条推送可一键关闭该类规则

**退出信号**:误报率降不到 20% 以下时,**收紧规则或退回影子模式**,
不要靠调 prompt 硬压 —— 那只会把问题藏起来。

---

## R5 · 成本失控

**等级**:中 · **缓解截止**:P0 起监控

主动扫描意味着**每天固定烧钱,且随用户数线性增长**。
P4 开放给朋友后,是你在替他们付账。

**缓解措施**

- `tool_calls` 从 P0 起记录每回合 token 消耗与费用([架构 §3.3](02-architecture.md#33-审计与成本))
- 账单归类走规则表优先,LLM 只处理长尾([ADR-008](04-tech-decisions.md#adr-008--账单归类用规则llm-混合))
- P4 上线每用户配额与成本硬上限,超限降级而非静默继续
- 定期看 LLM 调用占比是否随时间下降

---

## R6 · 平台政策变动

**等级**:中 · **缓解截止**:P0 起监控

企业微信的推送能力、交互卡片、"微信插件"转投能力都由平台政策决定,
且**变动频繁**。整个入口层建立在别人的规则之上。

**缓解措施**

- 动手前实测确认当前能力边界,不依赖文档或二手信息
- 推送层做接口抽象,企微/飞书/邮件可切换 —— 但**不提前实现多通道**,
  只保证换的时候不用改上层
- 邮件作为兜底通道从 P1 就在线

---

## R7 · 记忆污染

**等级**:中 · **缓解截止**:P1 前

错误或无来源的记忆会累积。时间一长,系统里全是用户不认可、
又说不清哪来的、不敢删的条目 —— 记忆层从资产变成负债。

**缓解措施**

- `facts` **强制携带 `provenance`**,无来源不允许写入([架构 §2.3](02-architecture.md#23-事实库--facts))
- 事实带 `confidence` 与有效期,会过期(换工作、搬家)
- 用户可查看、可否定任何一条记忆,否定记录保留以防重复推断
- P1 验收标准包含:记忆里不出现说不清来源的条目

---

## R8 · 数据源格式变动

**等级**:中 · **缓解截止**:P2 前

支付宝/微信账单导出格式不稳定,银行短信模板会变。解析器会静默地开始丢数据。

**缓解措施**

- 解析失败**必须告警**,绝不静默丢弃
- 保留原始文件,解析器修好后可重跑
- 对账机制:导入条数与解析成功条数不一致时提示

---

## R9 · 单点自托管可用性

**等级**:中 · **缓解截止**:P4 前

单机自托管,机器挂了就全停。P0–P3 只影响你自己,P4 后影响朋友。

**缓解措施**

- P4 前完成备份与**恢复演练**(演练过才算数,配了备份不算)
- 推送失败降级到邮件通道
- 数据源采集失败要有重试与告警,不静默跳过
- **邮箱授权码会因用户修改账号密码而失效**,连续认证失败必须告警,不能静默停采
- 定时任务补偿:机器重启后能补跑漏掉的窗口

## R10 · 手机端采集器的越权读取

**等级**:高 · **缓解截止**:P1 前(采集器首次上线的那一期)

[安卓 App 的采集侧](02-architecture.md#8-安卓-appp1-起)能读到的是手机上的
**全部**短信与通知,包括三类它本来不该碰的东西:

| 内容 | 泄露后果 |
| --- | --- |
| 银行验证码、登录验证码、密码重置链接 | **资金与账号损失** |
| 与记账无关的私人聊天通知 | 隐私损失,且是别人的隐私,不只是你的 |
| 其他 App 的敏感通知(医疗、招聘、社交) | 隐私损失 |

规则写宽一点,或者传输通道被截获,等于把账号接管能力交出去。
**这比账单数据泄露严重一个量级**:账单泄露是隐私损失,验证码泄露是资金损失。

注意第二类:群消息摘要要读群通知,**里面有群友说的话**。他们没有同意过
自己的消息被送进你的服务器和 LLM。这一条在 P4 尤其要想清楚。

**缓解措施**

- 转发规则用**发件人 / 包名白名单**,默认拒绝;新增来源必须显式加白
- **验证码类内容强制丢弃**:命中"验证码""动态密码""校验码"等模式的消息
  在转发端就丢弃,不进队列
- 服务端在入库前**再过一次验证码正则**,双保险 —— 不假设手机端规则永远正确
- 转发通道必须是 HTTPS webhook + 独立密钥,**不用明文邮件**传交易数据;
  入口做来源校验与重放保护
- 原始文本入库前脱敏:交易类只保留金额、时间、卡号后四位、商户,不存整条报文
- **群消息只保留摘要,不留存原文**,且摘要过期即删。群友没同意过被存档
- **P4 绝不要求朋友安装采集器。** 让朋友把全部短信和通知交给你转发,
  是不可接受的信任索取 —— 朋友那边只走月度导出模式,也没有群消息摘要

## R11 · App 直连服务端的认证面

**等级**:高 · **缓解截止**:P1 前

在 App 之前,服务端只有两个入口,且都是窄口:企微回调(平台签名校验)
和采集上报(单向写入,独立密钥)。

App 承担查看与操作之后,服务端必须向公网暴露**一组完整的读写接口** ——
账本、报表、记忆、待确认队列。认证只要做松一点,泄露的就不是某一类数据,
而是**你的全部生活数据**。这是 [ADR-014](04-tech-decisions.md#adr-014--客户端做完整-app-但不接收推送)
带来的新风险,是为 App 的便利付出的代价,必须一起接受。

**缓解措施**

- **采集凭据与查询凭据分开。** 采集端只能写、不能读 ——
  手机被拿走或 App 被逆向,不等于账本被读走。这是最重要的一条
- 设备级长期凭据 + 短期 token,长期凭据存安卓 Keystore,不落明文文件
- token **服务端可单点吊销**,手机丢失时能立刻断开该设备
- 所有查询接口在**数据层**强制 `user_id` 过滤,不靠接口参数
  (与[架构 §6](02-architecture.md#6-为多用户预留p4-前必须做到) 一致)
- 接口不直接暴露公网,走反向代理 + TLS;失败登录做限速与告警
- P4 前完成一次接口鉴权审查,与 [R1](#r1--代管他人凭据与支付数据) 的安全审查合并做
