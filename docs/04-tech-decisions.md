# 04 · 技术决策记录

**本文档最重要的部分是"被否决的方案"和"重新评估的触发条件"。**

本项目刻意没有引入 LangGraph、MCP、hook 机制、多 agent 等一批当前流行的 agent 技术。
这不是因为不了解,而是逐条评估后认为**当前阶段不匹配**。每条决策都写明了
将来什么信号出现时应该重新考虑 —— 请在改架构前先读对应条目。

选型标准只有一条:**适合项目才用,不为了用而用。**

## ADR-001 · 推送与审批入口选企业微信

**状态**:已确认(P0 生效)

**背景**
用户与朋友均在中国大陆,朋友为非技术背景。系统需要主动推送,且审批流程
要求消息能承载可点击的交互按钮并回调服务端。

**决策**
**推送与审批**入口使用企业微信自建应用。飞书作为备选方案保留。

范围说明:本 ADR 只决定"系统怎么主动找到用户"。用户主动查看和操作走安卓 App,
两者是分工不是主次,见 [ADR-014](#adr-014--客户端做完整-app-但不接收推送)。

**理由**
它是唯一同时满足三条硬需求的正规方案:无限制主动推送、交互式模板卡片 + 按钮回调、
消息可转投到微信中接收(朋友学习成本接近零)。

**它不是零成本的:装 pdfplumber 会顺带装进 Pillow 和 pypdfium2**,
而后者是编译扩展。所以上面否决 PyMuPDF 时,"编译扩展"这条理由不成立 ——
**否决它的是 AGPL 那一条,只有那一条**。三个包都有现成的 wheel,
装的时候不用编译,但换 Python 大版本时要确认有对应的轮子。

`pypdfium2` 只有 `page.to_image()` 会用到,而我们不渲染图片,
只取表格 —— 它是装上了不跑的那种依赖,不是运行时的第二个 PDF 引擎。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| Telegram | 大陆网络不可用,朋友不可能装 |
| 微信个人号(协议逆向) | 封号风险,**绝不能让朋友承担**,与托管他人数据的定位冲突 |
| 微信服务号 | 需企业主体 + 类目审核,个人做不了;订阅通知限制多,无交互按钮 |
| QQ 官方机器人 | 主动推送与私聊能力受政策限制 |
| 钉钉群机器人 | 只能推群,交互能力弱,无法承载审批 |
| 飞书 | API 体验明显更好,但**朋友是非技术背景**,装飞书的门槛高于企微转投微信 |
| 自建 App + 厂商推送 | 需接小米/华为/OPPO/vivo 四套通道,投入产出比极差。**注意这条只否决"接收推送"**,不否决 App 本身 —— 见 ADR-014 |
| 邮件 | 无交互按钮,不能承载审批;保留作兜底通道 |

**待验证**
企业微信"微信插件"的消息转投能力、以及模板卡片的按钮回调细节,
**动手前需实测确认**。平台开放政策变动频繁,以官方最新文档为准。

**重新评估的触发条件**
朋友群体变为技术背景为主 → 改飞书;或企微政策收紧导致转投微信失效 → 重新评估。

## ADR-002 · P0–P2 不引入 agent 编排框架

**状态**:已确认

**背景**
用户初期倾向自研编排层,后改为使用 LangGraph 等开源框架。

**决策**
**P0–P2 不引入任何 agent 编排框架**,直调外部 LLM API(OpenAI 兼容接口)。
~~**P3 引入状态机编排**(LangGraph 或同类)。~~
**P3 也不引入** —— 见 [ADR-024](#adr-024--p3-的审批编排不引-langgraph用-approvals-表--已有网关),
那是按下面"重新评估的触发条件"重算之后的结论。

注意"不引入编排框架"**不等于"只有一个 agent"**:agent 按领域分工,
但全部跑在同一进程内、用普通函数调用串起来,见
[ADR-013](#adr-013--agent-按领域分工同进程运行)。

**理由**
P0–P2 的流程本质是"定时拉数据 → 调 LLM → 推送",是脚本级复杂度,
引入编排框架是纯负担 —— 多一层抽象、多一份文档、多一批 bug,换不来任何东西。

模型侧统一走 **OpenAI 兼容接口**,不绑定任何厂商:换模型只需改配置里的
`base_url` + `model`,不动业务代码。这条约束比"选哪家模型"重要 ——
厂商可能涨价、限流或下线,切换成本必须保持在改两行配置的量级。

真正需要框架的时刻是 **P3 的审批流程**:一个流程要**暂停数小时等用户点按钮,
然后从断点恢复**。这是长时间运行、可中断、可持久化的流程,
LangGraph 的 checkpoint / interrupt 机制正是为此设计的。那时引入才是赚的。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| 自研编排层 | 目标是"自己和朋友真的用",不是学习项目。会先花几个月重造轮子,而朋友一直等不到能用的东西 |
| P0 就上 LangGraph | 过度设计。P0 用不到它任何一个核心能力 |

**重新评估的触发条件**
提前进入 P3、或 P1/P2 出现需要长时间挂起的流程 → 提前引入。
注意:agent 数量变多**不是**引入框架的理由 —— 那是模块划分问题,不是编排问题。

## ADR-003 · P0 不引入 MCP

**状态**:已确认

**背景**
用户最初将 "MCP 与工具治理" 列为核心技术点。

**决策**
P0 的工具直接实现为普通函数,不包装成 MCP server。

**理由**
MCP 解决的问题是"同一套工具给**多个 client** 复用"。当前只有一个后端在调用,
包一层 MCP 是白加一层抽象,没有任何收益。

工具治理(分权、审计)本项目确实需要,但那是**治理层**的职责,
用工具注册表 + 统一调用网关实现即可,与 MCP 无关。不要把两件事捆在一起。

**重新评估的触发条件(这条很可能会触发)**
当你希望**在其他 MCP client 里也直接查自己的邮件、账单、记忆**时 ——
那一刻起就是"一套工具、两个消费方",MCP 立刻变得划算。
建议届时优先把 L1 只读工具封成 MCP server,写操作留在服务端。

## ADR-004 · 不做 hook 机制,用审批队列

**状态**:已确认

**背景**
用户最初将 "Hook 与可观测性" 列为核心技术点,设想用 hook 拦截高危操作。

**决策**
不实现通用 hook 机制。高危操作拦截由**分权网关 + 审批队列**直接实现。

**理由**
Hook 是给**第三方扩展**用的抽象。本项目没有第三方,所有代码都是自己写的。
在自己的代码里,"拦截 L3 操作"就是网关里的一个分支判断,
为它造一套注册/触发/优先级机制是纯粹的过度设计。

可观测性的真实需求是**审计日志 + 成本核算**,这两件事本项目做了
(见 [架构 §3.3](02-architecture.md#33-审计与成本)),只是不叫 hook。

**重新评估的触发条件**
项目开放为框架、或需要让朋友自己写扩展规则 —— 但这与
[产品定义 §8](01-product-spec.md#8-非目标明确不做的事) 的非目标冲突,基本不会发生。

## ADR-005 · 不做多 agent 协作

**状态**:已确认

**背景**
用户最初设想"并行竞争 + 评审择优"的多 agent 范式。

**决策**
使用**单 agent + 分领域工具集**。不做多 agent 协作,不做竞争择优。

**理由**
"并行竞争 + 评审择优"适用于**有客观验收标准、且值得花 N 倍 token** 的高价值任务
(如代码修复:测试跑没跑通是硬指标)。生活任务两条都不满足 ——
"帮我订个餐"没有客观优劣,也不值得跑五遍。

分领域拆 agent 的**真实理由**是上下文隔离和 prompt 专门化,不是"协作"。
等到单个 prompt 长到互相干扰、或上下文塞不下时再拆,那才是真实信号。

**重新评估的触发条件**
单 agent 的 system prompt 因领域过多而互相干扰,或上下文长度成为瓶颈 →
按领域拆分子 agent(仍然不做竞争择优)。

## ADR-006 · 存储用单一 PostgreSQL + pgvector

**状态**:已确认

**决策**
结构化数据、任务队列、记忆向量全部放在一个 PostgreSQL 实例,向量用 pgvector 扩展。

**理由**
单机自托管场景下,多引入一个组件就多一份运维负担和一个故障点。
在数据量达到百万级之前,pgvector 的性能完全够用,而事务一致性
(事件与其向量必须同时写入成功)反而是专用向量库的短板。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| 独立向量数据库 | 当前数据量下纯属增加运维复杂度,且跨库事务一致性难保证 |
| Redis / Celery 做队列 | P0–P3 的任务量用数据库表 + APScheduler 完全够;多用户后再评估 |

**重新评估的触发条件**
向量数据超过百万级且检索延迟成为瓶颈;或 P4 多用户后任务队列出现积压。

## ADR-007 · 朋友接入推迟到 P4

**状态**:已确认(硬约束)

**决策**
P0–P3 期间系统只有作者一个用户。朋友在 P4 且满足前置门槛后才接入。

**理由**
一旦有第二个用户,你就成了**别人的邮箱授权码和支付数据的保管人**,
这是法律责任而非仅技术责任。P0–P3 期间你需要随时重构、删库、改 schema 的自由,
有真实用户后这个自由就没了。

**同时**:多用户的三项技术预留(全表 `user_id`、凭据字段级加密、
数据访问不假设单用户)**必须从 P0 第一行代码就做**。现在成本几乎为零,
P4 再补是几周的痛苦重构。推迟的是**开放**,不是**准备**。

## ADR-008 · 账单归类用规则+LLM 混合

**状态**:已确认(P2 生效)

**决策**
账单归类采用两级策略:先查商户规则表命中则直接归类;未命中才调 LLM,
并将 LLM 的结果**写回规则表**作为后续规则。

**理由**
消费记录高度重复 —— 同样几十个商户占据绝大多数流水。
纯 LLM 归类既贵又不稳定(同一个商户不同月份可能归到不同类)。
规则表让成本随时间下降、结果随时间稳定,LLM 只处理长尾。

**与两阶段入账的关系**
实时通知里的商户名常常只是代收机构名("财付通""支付宝"),归类价值很低。
因此**归类跑两次**:实时入账时先给一个临时分类,月度账单回填真实商户后重新归类。
规则表只从**回填后的真实商户名**沉淀,不要用代收机构名污染规则表
(见 [ADR-012](#adr-012--账单采集以实时通知为主导出账单为辅))。

**监控指标**
LLM 调用占比。如果这个数字不随时间下降,说明规则没有正确沉淀,是 bug 而不是常态。

## ADR-009 · 凭据字段级加密从第一天做

**状态**:已确认(P0 生效,硬约束)

**决策**
所有 IMAP 授权码、企微 access_token 等凭据**存库前加密**,密钥走环境变量(P0–P3)
或 KMS(P4)。

**理由**
"先明文存,以后再加密"的问题是:等你想加密时,库里已经有真实凭据了,
备份里也有,而你不知道备份都散在哪。加密必须在第一条凭据入库之前就位。

P0 阶段成本极低(一个加密工具函数),P4 补做则要处理存量数据和历史备份。

## ADR-010 · 微信只做只读接入,走官方通知监听

**状态**:**已修订**(原决策为"完全不接入",2026-09 修订为"只读接入")

**背景**
原决策一刀切地否决了微信接入,理由是"只能靠协议逆向或客户端 hook"。
这个前提是错的:**读微信消息和 hook 微信客户端是两件不同的事**。
安卓的 `NotificationListenerService` 是系统级公开 API,能拿到通知的
应用包名、标题(群名/联系人)、正文,**既不修改也不注入微信客户端**。
而记账主通道([ADR-012](#adr-012--账单采集以实时通知为主导出账单为辅))
本来就要在手机上常驻这个监听器 —— 边际成本为零。

**决策**

**准许**:通过安卓官方通知监听读取微信通知(好友消息、群消息、支付通知),
用于账单识别、群消息摘要、日程与待办提取。

**禁止**(维持原否决,不放宽):

- 协议逆向 —— itchat / 网页版微信协议 / wechaty 等
- 客户端 hook —— Xposed、无障碍服务点击注入
- **任何形式的自动回复或代发微信消息**

**理由**
封号风险来自"写"和"伪装成客户端",不来自"读通知"。通知监听在微信侧
不产生任何异常行为特征,也不存在协议指纹。

自动发消息则是最容易被风控识别的行为,而且按本项目的三级分权,
代发消息本来就是标准的 **L3** —— 合规做法是 agent 生成草稿、推卡片、
人工点确认后才发出,那已经不叫"自动回复"了。既然要人点,
就没有必要为它承担 hook 微信客户端的风险。

**评估过的三个现成实现,都到不了目标**

| 项目 | 实际是什么 | 为什么不用 |
| --- | --- | --- |
| `node-webot/weixin-robot` | 微信**公众号**开放接口封装 | 只能回复关注公众号的人,回复不了个人好友 |
| `yangxuanxc/wechat_friends` | itchat,网页版微信协议 | 网页版个人号登录已基本关闭;且属协议逆向 |
| `itsMelo/WcAutoReply` | 安卓无障碍服务点击自动回复 | 客户端 hook,且 ROM 适配是无底洞 |

**这条通道的真实能力边界(必须写清,否则会高估)**

通知监听只能拿到**通知栏实际展示过的内容**,因此:

- 设了免打扰的群**拿不到**
- 长消息会被系统截断
- 撤回的消息、进入聊天前的历史消息**完全拿不到**
- 系统可能把多条折叠成"[3 条] 张三: ……",需要单独处理

所以这块能力的准确名字是"**在线期间的群消息摘要**",
不是"聊天记录分析"。产品文案和验收标准都必须按这个口径写。

**重新评估的触发条件**
微信开放个人号的官方消息接口。
若将来愿意为自动回复承担封号风险,**也必须先把它归入 L3 审批流**,
而不是直接放开自动发送。

### 2026-09 复评:触发条件已发生,但本条结论不变

上面那句"目前没有任何迹象"过时了 —— 腾讯开放了 **iLink Bot API**
(`ilinkai.weixin.qq.com`,npm 上有官方 scope 的
`@tencent-weixin/openclaw-weixin-cli`)。已由作者实测可用,收发正常。

**它确实推翻了一件事**:这份文档里到处写着"微信只能靠协议逆向或客户端 hook",
这个前提现在不成立了。凡是基于"封号风险"做的推理都要重新检查。

**但它没有推翻本条的禁止清单**,原因是 iLink 给的东西和这条 ADR 管的东西
不是一回事:

| | 本条 ADR 想要的 | iLink 实际给的 |
| --- | --- | --- |
| 身份 | 你的个人号 | **一个独立 bot 身份**(`xxx@im.bot`) |
| 好友消息 | 读到好友发给**你**的消息 | ❌ 好友发给你的号,不经过 bot |
| 群消息 | 读群聊做摘要 | ❌ 对多数 bot 账号类型**根本不投递群事件** |
| 自动回复好友 | —— | ❌ 同上,拿不到好友消息就无从回复 |

所以:**群消息摘要与日程提取仍然只能走安卓通知监听**,一个字都不用改;
**自动回复好友仍然做不到** —— 现在不是"不敢做",是"做不了"。

iLink 真正改变的是**另一件事**:系统怎么找到用户。那属于
[ADR-001](#adr-001--推送与审批入口选企业微信) 的范围,处理见
[ADR-018](#adr-018--微信推送走-ilink-bot-api企微降为兜底与审批入口)。

## ADR-011 · 数据源全面本地化

**状态**:已确认(P0 生效)

**背景**
原设计写的是 `IMAP / Gmail API` 和 `CalDAV / Google Calendar API`,
这是照搬国外方案的产物。作者实际用的是 QQ / 163 邮箱,日历也不在 Google。

**决策**

- **邮箱**:统一走标准 IMAP + 授权码(`imap.qq.com` / `imap.163.com`),
  不引入任何厂商 SDK。
- **日历**:走**企业微信日程 / 日历接口**,与主入口复用同一套自建应用凭据。

**理由**
IMAP 是国内邮箱的最小公分母,换邮箱只改配置。授权码不是账号登录密码,
泄露面更小且可单独吊销 —— 这一点对 P4 代管朋友凭据尤其重要。

日历选企微是因为**主入口已经是企微**:不多接一个平台、不多一套凭据、不多一次授权。
P1 的 L2 工具"改日历"直接走同一套接口写回,用户在手机企微上立刻看到结果。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| Gmail API / Google Calendar | 国内不可直连,且作者本来就不用 |
| iCloud CalDAV | 国内连接不稳定;小米/华为/OPPO 日历基本不开放 CalDAV |
| 飞书日历 | API 设计确实更好,但要多接一个平台、多一套凭据,还得同时用两个 App |

**实现注意(会卡住半天的坑)**

- 163 / 126 的 IMAP 在 `SELECT` 之前**必须先发 `ID` 命令**声明客户端身份,
  否则直接报 `Unsafe Login`。Python 的 `imaplib` 默认不允许在该状态发 `ID`,
  需要先把它注册为 AUTH 态可用命令。QQ 邮箱无此要求。
- 授权码会在用户修改账号密码后失效,采集端连续认证失败**必须告警**,
  不能静默停采(见 [R9](05-risks.md#r9--单点自托管可用性))。

**重新评估的触发条件**
需要读取邮件以外的 Google / Outlook 数据,或日历使用习惯迁出企微。

## ADR-012 · 账单采集以实时通知为主,导出账单为辅

**状态**:已确认(P2 生效)

**背景**
"能不能自动记账"决定 P2 的验收标准怎么写。最初的方案把月度导出当作主来源、
把交易短信当作可选增强,方向反了 —— 绝大多数消费当场就有一条通知,
而月度导出天然滞后最多 30 天。

**决策**

| 通道 | 角色 | 实时性 | 自动化程度 |
| --- | --- | --- | --- |
| 手机端转发(**短信 + App 通知**) | **主通道** | 秒级 | 全自动,需常驻安卓端 |
| 信用卡月度对账单邮件 | 金额权威源、对账 | 月度 | 完全自动 |
| 支付宝 / 微信账单导出 | 补全商户名与订单号 | 月度 | 半自动,每月手动触发 |

**明确不做**:模拟登录抓账单、客户端自动化。

**两阶段入账(核心设计)**

1. 实时通知到达 → **立即入账**,落金额、时间、卡号后四位、原始文本。
   此时商户名常常只是"财付通""支付宝"这类代收机构名,**不能直接用于归类**。
2. 月度账单到达 → 按 `(金额, 时间窗, 卡号后四位)` 匹配已有实时记录,
   **回填真实商户名、订单号并重新归类**;匹配不上的补为新记录,并计入覆盖率统计。

匹配必须有幂等键。**重复入账比漏记更糟** —— 漏记你会发现,重复不会。

**理由**
记账最难坚持的原因是反馈延迟。实时入账把反馈缩到秒级,这是月度导出无论如何
做不到的。更关键的是**预算超支预警只有在超支当天发出才有意义**,
下个月才知道自己上个月超了,这个功能等于没有。

**多层防误判(借鉴 AutoBookKeepingBeta 的实战经验)**

这是最容易被低估的部分。**错记一笔比漏记一笔糟得多** —— 漏记你会补,
错记会让你不再信任这个账本,而不信任的账本等于没有。四层校验按成本从低到高:

| 层 | 位置 | 做什么 |
| --- | --- | --- |
| 1 源头过滤 | 手机端 | 包名 / 发件人白名单,不在白名单的通知根本不上报 |
| 2 去重窗口 | 服务端 | 同一 `(来源, 金额, 商户)` 在 5 分钟内只入账一次 —— 支付宝、微信、银行会为同一笔交易各发一条通知 |
| 3 LLM 结构化 + 判定 | 服务端 | 除了抽字段,**必须同时判定这是不是一笔真实支出** |
| 4 结果校验 | 服务端 | **不信 LLM 的输出**,用代码复核 |

第 3 层要显式区分的类型,漏掉哪个就会错记哪个:

`真实支出` / `待支付提醒` / `还款提醒` / `信用卡还款` / `转账` / `退款` /
`到账收入` / `营销文案`。**只有第一类入账**;信用卡还款计入会造成双重记账
(消费时已记过一次)。

第 4 层的具体规则:金额必须能在原文里逐字找到;时间必须落在合理窗口内;
分类必须在枚举集合内;置信度低于阈值直接拒绝。

**任何一层不通过,一律进"待确认"队列,不入账也不丢弃。**
宁可让你多点一下,不可以偷偷记错。

**两个缺口,要分人看**

1. **覆盖率对作者本人不是问题,对 P4 的朋友是。**
   作者未开通"小额免短信",所有银行卡消费均有短信,微信与支付宝消费另有
   App 通知,双通道覆盖。但这是**个人账户配置**,不是系统能保证的前提 ——
   多家银行已在提高短信提醒门槛,500 元以下小额交易普遍不再免费发短信。
   因此 P4 给朋友用时,不能假设对方也有全额短信,必须先测覆盖率再开通道。
2. **必须是日常使用的安卓主力机,不能是备用机。** 两条物理限制:
   银行短信只到 **SIM 卡所在的设备**;微信与支付宝个人号**同一时间只能在
   一台手机登录**,备用机登录就等于主力机被踢下线。
   这条把保活从"注意一下"变成核心风险 —— 主力机上你会频繁清后台。
   iOS 没有等价方案,只有 iOS 的话本条链路整体不成立,退回月度导出模式。

**为什么这仍然不是"完全自动"**

数据源确实接近全覆盖:所有银行卡消费有短信,微信支付宝消费有 App 通知。
但"通知能收到"和"账记对了"之间还隔着三个缺口,它们都不是数据源问题:

| 缺口 | 性质 | 缓解 |
| --- | --- | --- |
| **采集器静默掉线** | 最大威胁。停掉时系统表现一切正常,摘要照发报表照出,只是账目悄悄变少,到月底对账才发现少了两周 | 心跳告警,P1 必做 |
| **解析不确定** | 通知被折叠成"[3 条]"、不含金额、新商户格式没见过 → 进待确认 | 随规则表沉淀下降,但降不到 0 |
| **现金支付** | 根本没有通知 | 拍小票或手动补一笔 |

第二条是**刻意的设计**,不是缺陷:四层防误判存在的意义就是
"宁可让你点一下,不可以偷偷记错"。把不确定的东西自动记进去,
才是真正毁掉账本的做法。

因此本 ADR 承诺的是:**"逐笔录入"这件事消失**,剩下的操作从
"打开 App 输入一笔账"变成"在待确认队列里点个确认或改个分类"。
这是量级上的质变,但不是零操作。P2 的目标写作"你不再**逐笔**记账",
措辞是准的。

**覆盖率指标(P2 必须实现)**
月度账单到达后统计:其中有多少笔曾在实时通道出现过。这是通道健康度的**唯一客观指标**,
低于阈值说明转发规则漏了,要回去补规则,而不是接受现状。

**安全约束**
转发端能读到手机上的全部短信与通知,包含验证码。规则必须是发件人白名单 +
验证码内容强制丢弃,且**P4 绝不要求朋友安装转发端**。
详见 [R10](05-risks.md#r10--手机端采集器的越权读取)。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| 模拟登录抓账单 | 账号风险不可控,绝不能用于给朋友的服务,与 ADR-010 同理 |
| 只用月度导出 | 滞后最多 30 天,预算预警失去意义,记账反馈链路断掉 |
| 只监听短信、不监听 App 通知 | 小额交易的短信正在被银行取消,覆盖率会持续下滑 |
| 接第三方记账 App | 同样不开放个人 API,且等于把支付数据再交给一方 |

**参考项目的功能对齐**

`AutoBookKeepingBeta` 和 `LiteNote` 里哪些采纳、哪些不采纳:

| 功能 | 处理 | 说明 |
| --- | --- | --- |
| 通知账单识别(支付宝/微信/云闪付/银行/美团/京东) | **采纳** | 即本 ADR 的主通道 |
| 多层 AI 防误判 | **采纳** | 见上,这是最有价值的借鉴 |
| 账单增删改 + 按时间/类别/关键字组合查询 | **采纳** | 在企微里对话式完成,属 L2 工具 |
| 自定义分类、预算与超支预警、月度报表 | **采纳** | 已在 P2 范围内 |
| 拍照识别小票 / 发票 | **采纳,但降到 P2 末** | 补的是没有电子通知的现金与纸质票据,是长尾 |
| 语音记账 | **不做** | 见[产品定义 §4](01-product-spec.md#4-交互形态),语音入口不在规划内 |
| 云端同步 / 换机迁移 | **不适用** | 本项目数据本来就在自己的服务端,不存在这个问题 |
| 个人 / 家庭账本切换 | **推迟到 P4** | 本质是多用户与共享,与朋友接入是同一件事 |
| 桌面小组件 | **已改判为做** | 写这条时还没有自己的 App。[ADR-014](#adr-014--客户端做完整-app-但不接收推送) 之后有了,[ADR-020](#adr-020--待办与日程落在自己的-app企微退出主链路) 把待办小组件排进 P1 —— 它是"看一眼"的入口,定时拉不接推送 |
| 快捷开关、全局公告 | **不做** | 那些是独立 App 的形态,与本项目的边界无关([产品定义 §8](01-product-spec.md#8-非目标明确不做的事)) |

**重新评估的触发条件**
实时通道覆盖率长期低于阈值且补不上去;或支付宝 / 微信支付开放面向个人的
交易查询 API(目前没有任何迹象)。

## ADR-013 · agent 按领域分工,同进程运行

**状态**:已确认(P0 起按此结构组织代码)

**背景**
需求是"细化分工,多个 agent 分别负责一部分,方便后续测试和迭代维护"。

这与 [ADR-005](#adr-005--不做多-agent-协作) **不冲突**。ADR-005 否决的是
**竞争择优**(N 个 agent 做同一件事再挑最好的),而它的重评触发条件原文写着:
"单 agent 的 prompt 因领域过多互相干扰时,按领域拆分(仍不做竞争择优)"。
本 ADR 就是在执行那条触发条件,只是**提前执行** —— 领域边界现在已经看得清了,
等 prompt 真的互相干扰了再拆,要付重构的代价。

**决策**
按领域划分 agent,每个 agent 声明完整契约;**P0–P2 全部跑在同一进程内**,
不引入进程间通信,不引入编排框架。划分见
[架构 §7](02-architecture.md#7-编排层agent-按领域分工)。

**每个 agent 的契约(缺一项不允许注册)**

| 项 | 为什么必须有 |
| --- | --- |
| 输入类型 | 说清它管什么,避免职责漂移 |
| **工具白名单** | 网关按 `(agent, tool)` 双重校验,不只看等级。记账 agent 拿不到发消息的工具,哪怕那是 L1 |
| 输出 schema | 结构化才能被代码校验,自由文本没法测 |
| **失败行为** | 拿不准时做什么。**默认必须是不动作**,不是猜一个 |
| **独立评测集** | ≥ 20 条真实样本 + 期望输出 |

**理由**
最后一条是这套划分的真正目的。改记账 agent 的 prompt 时,你需要立刻知道
有没有把摘要 agent 弄坏 —— **一个大 prompt 做不到这件事**,它的每次修改都是
全局的,而且没有任何办法分别评测。

工具白名单那条是安全收益:三级分权管的是"这个工具危不危险",
agent 白名单管的是"这个角色该不该碰它"。两者是不同维度,叠加才严密。

**为什么不拆进程**
拆进程解决的是独立扩缩容和独立发布,P0–P2 一个都不需要;
换来的是分布式追踪、部署编排、版本兼容,全是负担。

而"方便测试和迭代维护"是由**契约**保证的,不是由进程边界保证的。
只要工具白名单和评测集隔离,改一个 agent 不会波及另一个 ——
这与它们跑在几个进程里无关。这是本条决策里最容易被直觉误导的地方。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| 一个大 agent + 超长 prompt | 领域互相干扰,改记账会让摘要变差,且无法分别评测 |
| P0 就拆多进程 / 多服务 | 过度设计。单机自托管,拆进程只增加运维面,不带来任何当前需要的能力 |
| 多 agent 竞争择优 | 见 ADR-005,生活任务没有客观优劣标准,不值得 N 倍 token |
| 按数据源划分 agent(邮件 agent、账单 agent……) | 划错了维度。同一个数据源要服务多个目的,按目的划分才不会重复 |

**重新评估的触发条件(拆进程的时机)**
某个 agent 需要独立扩缩容(记账在月底账单集中到达时有可能);
发布节奏明显不同于其他;或 P3 引入状态机后,长流程需要独立 worker。

## ADR-014 · 客户端做完整 App 但不接收推送

**状态**:已确认(P1 起)

**背景**
文档里曾同时存在两条互相矛盾的话:非目标表写着"不做自建 App",而 P1 又要求
在手机上装一个安卓采集器。**采集器本身就是一个安卓 App**,矛盾是真实存在的。

追下去发现,ADR-001 否决自建 App 的理由只有一条:
**要接小米 / 华为 / OPPO / vivo 四套厂商推送通道**。而这条成本
**只在 App 需要接收推送时才产生**。采集器只读系统通知、只往外发 HTTP 请求,
从不接收推送 —— 那条否决理由对它完全不适用。

既然 App 是必装的(记账和群摘要的物理前提),把能力局限在后台采集就是浪费:
账本、报表、预算这类内容在 App 里看本来就比在企微卡片里翻方便得多。

**决策**

安卓 App 承担**采集 + 完整的查看与操作**:

- 短信与通知监听、白名单过滤、心跳上报(采集)
- 账本浏览、月度报表、预算与超支查看
- 待确认队列处理、拍照记小票、手动补一笔
- 记忆与实体浏览、采集器状态与白名单配置

**唯一的硬约束:App 不接收任何推送。** 不集成任何厂商推送 SDK,
不申请通知权限用于自身推送。所有主动触达一律走企微。

**理由**
这条约束不是妥协,是**成本边界的守卫**。一旦 App 开始接收推送,
就要接四套厂商通道、处理各家的到达率与保活策略、跟着各家政策变动维护 ——
那正是 ADR-001 当初否决它的全部原因。把它明确写成硬约束,
是为了防止将来"顺手加个推送"把这笔成本重新引进来。

分工的另一半也成立:企微的推送能力、交互卡片按钮回调、以及转投微信让
非技术背景的朋友零学习成本接收,是 App **无论如何都替代不了**的。

**连带影响**

| 影响 | 处理 |
| --- | --- |
| Web 控制台与 App 大量重复 | **从 P3 推迟到 P4**,只保留数据导出与账号管理(P4 的合规需要) |
| 桌面客户端 | **移出规划**,与 App、Web 三重重复 |
| App 要直连服务端 API | 新增认证面,见 [R11](05-risks.md#r11--app-直连服务端的认证面) |
| 工作量上升 | P1 与 P2 各增加约 2 周,见[开发计划](03-roadmap.md) |

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| 纯后台采集器,只有配置页 | 待确认队列和拍照记账绕到企微里做,体验别扭;而 App 反正要装,不用白不用 |
| App 也做推送,取代企微 | 要接四套厂商通道,ADR-001 的否决理由原样回来;且朋友那边失去转投微信的零门槛 |
| 用 Web 应用代替 App | Web 拿不到系统通知,采集这件事做不了 —— 这是 App 存在的根本原因 |

**重新评估的触发条件**
企微推送出现不可接受的延迟或政策收紧([R6](05-risks.md#r6--平台政策变动))
且邮件兜底也不够用时 —— 那时才重新计算接厂商推送通道的账。

## ADR-015 · App 用原生 Kotlin,只做安卓

**状态**:已确认(P1 生效)

**决策**
安卓 App 用原生 Kotlin 编写,**不使用 Flutter / React Native 等跨端框架**,
**不做 iOS 版**。

**理由**
App 的核心能力全部是原生系统 API:`NotificationListenerService`、短信监听、
前台服务保活、厂商 ROM 的自启动白名单适配。跨端框架在这些地方只能通过
platform channel 转发到原生代码 —— 等于既写了原生,又多维护一层桥。

跨端框架的唯一价值是复用到 iOS,而**iOS 做不了通知监听**,
这条链路在 iOS 上根本不成立(见[产品定义 §4 降级矩阵](01-product-spec.md#4-交互形态))。
价值为零的收益,不值得付出一层抽象。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| Flutter / React Native | 核心是原生 API,跨端只增加一层桥;唯一价值(复用到 iOS)不成立 |
| iOS 版 App | 系统不提供通知监听等价能力,只能做成"只看不采"的只读客户端,价值有限 |
| 混合方案(原生采集 + WebView 展示) | 可以考虑,但离线可用性和列表性能会明显变差,先用原生做,不行再退 |

**重新评估的触发条件**
苹果开放通知读取权限(几乎不可能);或 App 的展示部分复杂到自研成本超过
引入框架的成本 —— 那时也只换展示层,采集层保持原生。

## ADR-016 · 服务端用 Python + FastAPI

**状态**:已确认(P0 生效)

**背景**
这是从第一天就在用的选型,但一直只写在 README 的技术栈表里,
**没有决策记录** —— 没写为什么选它,也没写否决过什么。本条补上。

**决策**

| 层 | 选型 |
| --- | --- |
| 语言 | Python 3.11+ |
| Web 框架 | FastAPI —— 接企微回调、采集上报 webhook、App 查询 API |
| 调度 | APScheduler,**进程内**,不引入消息队列 |
| 数据访问 | 简单 CRUD 用 SQLAlchemy,分析类查询**直接写 SQL** |
| 客户端 | 安卓原生 Kotlin,见 [ADR-015](#adr-015--app-用原生-kotlin只做安卓) |

**理由**

本项目的重心是**数据归一化**和**调 LLM**,不是高并发。从一个用户到几个朋友,
QPS 是个位数,**性能从头到尾都不是约束** —— 用性能给语言选型排序在这里是错的。

真正的约束是胶水库的厚度。要接的东西全是脏活:IMAP、PDF 解析(带密码)、
CSV 容错解析、通知文本抽取、OpenAI 兼容 SDK、pgvector 客户端。
Python 在这些上面全有成熟库,换任何语言都要自己再写一遍。

FastAPI 的 Pydantic 模型正好承担 [ADR-013](#adr-013--agent-按领域分工同进程运行)
契约里的**输出 schema 校验**,不用额外引入校验库 —— 这是它比其他 Python 框架多出的一分。

APScheduler 进程内跑,与 ADR-013"同进程"的取向一致。定时任务补偿
([R9](05-risks.md#r9--单点自托管可用性))靠数据库记录上次执行窗口实现,
**不依赖调度器自身的持久化** —— 这样换调度器时不会丢补偿能力。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| Go / Rust | 性能不是本项目的约束,而上面那批胶水库要重写一遍。归一化这种反复试错的脏活,Python 迭代快得多 |
| Node.js / TypeScript | 生态可用,但邮件、PDF、CSV 解析这块明显不如 Python 厚;且 App 已经是 Kotlin,再多一门语言对单人项目是负担 |
| Django | 自带的 ORM / Admin / 模板对本项目没用,异步支持也不如 FastAPI 自然 |
| Celery + Redis 做调度 | P0–P2 单机单进程,引入消息队列是纯运维负担。真需要时再换,APScheduler → Celery 的迁移面很小 |
| ORM 重度使用 | 记忆层会有大量 JSONB 与向量操作,ORM 在这里帮倒忙。约定分工:CRUD 用 ORM,分析查询写 SQL |

**重新评估的触发条件**
P4 用户数增长到定时扫描无法在单进程内跑完 —— 那时**先拆 worker 进程,仍不换语言**。
语言层面基本不会重评:瓶颈永远在 LLM 侧,不在服务端。

## ADR-017 · P0 依赖清单逐条定性

**状态**:已确认(P0 生效)

**背景**
[AGENTS.md §3](../AGENTS.md#3-写代码时) 规定"不许引入新依赖而不补 ADR"。
[ADR-016](#adr-016--服务端用-python--fastapi) 已经定了框架层(FastAPI /
SQLAlchemy / Alembic / APScheduler / PostgreSQL),但真正装进 `pyproject.toml`
的还有几个它没覆盖的。与其为每个库单写一条,不如在这里一次性交代清楚。

**决策**

| 依赖 | 用途 | 定性 |
| --- | --- | --- |
| `fastapi` / `uvicorn` / `pydantic` | Web 与 schema 校验 | ADR-016 已定 |
| `sqlalchemy` / `alembic` | CRUD 与迁移 | ADR-016 已定 |
| `apscheduler` | 进程内调度 | ADR-016 已定 |
| `psycopg[binary]` | PostgreSQL 驱动 | psycopg3,官方现行版本 |
| `pgvector` | 向量列的 SQLAlchemy 类型 | pgvector 扩展的官方 Python 绑定 |
| `pydantic-settings` | 环境变量加载与**启动期校验** | 见下 |
| `httpx` | 调 OpenAI 兼容接口与企微 API | 见下 |
| `cryptography` | 凭据字段级加密([ADR-009](#adr-009--凭据字段级加密从第一天做)) | 见下 |
| `qrcode` | 在终端画 iLink 登录二维码([ADR-018](#adr-018--微信推送走-ilink-bot-api企微降为兜底与审批入口)) | 见下 |

**三个需要说明的**

`pydantic-settings` 的价值不是"读环境变量" —— 那 `os.environ` 就够了 ——
而是**缺配置在进程启动时就报错**,而不是等到当晚八点推摘要时才发现
`WECOM_SECRET` 是空的。自托管单机没有值班的人,失败必须尽量早。

`httpx` **不装任何厂商 SDK**。OpenAI 兼容接口在本项目只用到
`POST /chat/completions` 和 `POST /embeddings` 两个端点,一层 SDK 换来的
是它对特定厂商响应格式的假设。装 `openai` 包会让"换厂商只改两行环境变量"
([07 §2.3](07-config.md#23-外部模型))这句话在遇到不完全兼容的国内供应商时失效。
企微 API 本来就没有可用 SDK,两处复用同一个 HTTP 客户端还省一个连接池。

`cryptography` 提供 AES-256-GCM。选它不是选算法而是选**不自己拼装密码学** ——
它是 Python 生态里唯一有专职维护和安全响应流程的底层库。

`qrcode` 只用它的**字符画输出**,不装 Pillow。服务器上没有浏览器,
登录链接是打不开的 —— 对自托管来说终端能画出二维码不是锦上添花。
代码里做了 try/import 兜底:装不上就退回打印链接,不让登录整个失败。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| `openai` SDK | 绑定厂商响应格式假设,与"不绑厂商"冲突(见上) |
| `requests` | 同步阻塞;FastAPI 全异步,混用要多一层线程池 |
| `pycryptodome` | 能用,但安全响应不如 `cryptography`,且后者已是多数库的传递依赖 |
| `python-dotenv` 裸用 | 只加载不校验,拿不到"启动即失败"这个价值 |
| `passlib` / `bcrypt` | P0 没有用户口令。凭据是**对称加密后取回原文**,不是哈希 |

**重新评估的触发条件**
出现第二个 LLM 供应商且两家响应格式差异大到需要各写一套解析 —— 那时把差异
收敛进一个 provider 适配层,**仍然不装厂商 SDK**。

## ADR-018 · 微信推送走 iLink Bot API,企微降为兜底与审批入口

**状态**:已确认(P0 生效)

**背景**
[ADR-001](#adr-001--推送与审批入口选企业微信) 选企微,是因为当时"能主动推送
到微信"的正规方案只有企微转投。代价是**用户回话必须切到企业微信 App** ——
收在微信、回在企微,这个割裂一直是这个方案最难受的地方。

2026-09 腾讯开放了 **iLink Bot API**:扫码得到一个 bot 身份,
私聊收发都在微信里,长轮询,**不需要公网回调**。作者已实测可用。

**决策**

| 用途 | 走哪 |
| --- | --- |
| **每日摘要、提醒等主动推送** | **微信(iLink)**,企微作为降级 |
| 问答对话 | 企微(见下面"暂不做入站"的理由) |
| **L3 审批卡片**(P3) | **企微** —— 按钮回调是硬需求 |
| 群消息摘要、日程提取 | 安卓通知监听,不变([ADR-010](#adr-010--微信只做只读接入走官方通知监听)) |

新增一个 `WeixinChannel` 实现既有的 `Channel` 接口
([架构 §9.4](02-architecture.md#94-推送通道)),推送时优先微信、失败降级企微。
**这正是那个接口当初留下来的用途**,不是临时加的口子。

**理由**

体验上的差别是实打实的:摘要落在微信里,和落在一个你一天不一定打开一次的
App 里,不是一回事 —— 而 P0 的验收标准就是"你自己会不会每天看"。

不需要公网回调这一点被低估了:它意味着**跑通完整体验不再需要服务器、域名和
证书**,一台常开的机器就够。对自托管项目这是门槛上的实质变化。

**为什么企微不撤掉**

1. **iLink 太新。** 2026-03 才有,腾讯改它或关它都不需要跟谁商量。
   把唯一的触达通道压在一个半年新的接口上,是 [R6](05-risks.md#r6--平台政策变动)
   明确要防的事
2. **审批按钮。** P3 的 L3 审批要交互式卡片 + 按钮回调,iLink 支不支持未知,
   而企微确定支持 —— ADR-001 当初选它就是为这个
3. **朋友(P4)。** 企微转投微信对非技术背景的人是零门槛;iLink 要每人扫码
   连一个 bot,门槛更高。这条到 P4 再定

**入站(问答)也做,但要单独扫一个 bot**

iLink 收消息是长轮询同一个 bot 会话。**两个客户端同时拉会互相抢消息** ——
社区里专门有项目在解决"让两个 agent 共用一个微信账号",说明这是真问题。

解法不是不做,是**给 LifeIn 单独扫一个 bot**(`login-weixin`)。
一个微信号可以连多个 bot 身份,各自的会话互不干扰。

出站不存在这个冲突,任何时候都能发。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| 用 iLink 完全取代企微 | 单一通道压在半年新的接口上;且 P3 审批按钮没有替代 |
| 继续只用企微 | 收在微信回在企微的割裂是真实痛点,而解法已经存在,没有理由不用 |
| 客户端 hook / 协议逆向 | 有官方接口了,承担封号风险毫无必要([ADR-010](#adr-010--微信只做只读接入走官方通知监听)) |
| 复用已有客户端的 bot 会话做入站 | 两个客户端长轮询同一个会话会抢消息。单独扫一个才是解法 |
| 不做扫码登录、只支持手工导入凭据 | 会话过期后每次都要去别的客户端捞一遍 token,而扫码登录本身不复杂 |

**重新评估的触发条件**

- iLink 支持交互式卡片与按钮回调 → 审批也可以搬过来,企微可能整个撤掉
- iLink 连续不可用或被关闭 → 降级路径自动生效,同时把它从主通道降回备用
- iLink 的会话有效期短到需要频繁重扫 → 那时要考虑自动续期或退回企微

## ADR-019 · embedding 复用同一个 OpenAI 兼容端点,不引第二个供应商

**状态**:已确认(P1 生效)

**背景**

P1 的记忆层要"模糊召回":问"上次那个报销的事"时,字面搜不到"报销单已通过"
这条事实。[06 §2.4](06-data-model.md#24-向量索引) 已经把 `embeddings` 表和
`VECTOR(1024)` 定死了,[07 §2.3](07-config.md#23-外部模型) 也留了
`EMBEDDING_MODEL` / `EMBEDDING_DIM` 两个配置项 —— **但没有一条记录说明向量从哪来**。
本条补上。

**决策**

向量从**已经在用的那个 OpenAI 兼容端点**取,调 `POST /embeddings`,
和 `chat/completions` 共用 base_url、api key、httpx 客户端与重试逻辑。

- `EMBEDDING_MODEL` 留空 = **整个向量召回不启用**,字面检索照常工作。
  记忆层不因为没配这一项而不可用
- `embeddings.model` 列记下当时用的模型名。换模型时旧向量筛得出来,
  **不做在线混用** —— 两个模型的向量之间比距离,得到的数是无意义的
- 维度不匹配当场拒绝写入:`VECTOR(1024)` 是建表时定死的,
  拿一个 1536 维的模型直接写会被库拒掉,但报错发生在半夜的抽取任务里。
  在客户端先比一次,错误信息里说得清是哪个模型

**理由**

**这是"少一个供应商"而不是"省事"。** 每多一个外部服务就多一份密钥、
一份可用性、一份数据出境([R12](05-risks.md#r12--外部-llm-供应商侧的数据暴露))。
embedding 的输入是事实原文和事件标题 —— 和已经发给同一家的 prompt 是同一批
数据,发给第二家等于把同样的内容再泄一次给一个新的对象。

**召回质量不是这一期的约束。** P1 的量级是一个人几千条事实,任何一个
主流 embedding 模型都够用。真正决定回答质量的是抽取抽得准不准
(第 3 片)和事实有没有溯源(铁律 5),不是向量模型排行榜上的零点几分。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| 本地跑 embedding 模型(bge-m3 等) | 要装 `torch` + `sentence-transformers`,几个 G 的依赖和一份显存/CPU 预算,只为省几分钱的调用费。**自托管的边界是数据不外流,而这批数据本来就已经发给同一家了** |
| 换一家专做 embedding 的供应商 | 多一份密钥、多一个可用性、多一处数据出境,换来的是这一期用不上的质量差 |
| 独立向量数据库(Qdrant / Milvus) | [ADR-006](#adr-006--存储用单一-postgresql--pgvector) 已经否决过。几千条向量用 pgvector 的 HNSW 绰绰有余,而多一个存储就多一份备份与一致性负担 |
| 不做向量,靠字面 + 实体检索硬撑 | 实体检索解决"和谁",解决不了"那个报销的事"。P1 验收要求答得出后者 |
| 事件正文也全量向量化 | 成本随邮件量线性涨,而问答真正要召回的是**结论**不是原文。先只向量化 `facts`,事件靠实体检索够不够,跑一期看数据 |

**重新评估的触发条件**

- 召回明显不准(问对了人却召不回相关事实)→ 先查抽取质量,再考虑换模型或
  把事件正文也纳入向量化
- 事实条数过万、HNSW 查询超过 200ms → 那时调索引参数,仍然不换存储
- 出现"数据一个字节都不能出境"的要求 → 那时才值得把本地模型的成本吃下来,
  但那同时意味着 `chat/completions` 也得本地化,是一次整体决策而不是只换 embedding

## ADR-020 · 待办与日程落在自己的 App,企微退出主链路

**状态**:已确认(P1 生效)

**背景**

[03](03-roadmap.md) 写着"笔记 / 待办工具接入(具体选型在本期确定)",
默认的读法是接一个第三方待办工具。但那句话是在
[ADR-014](#adr-014--客户端做完整-app-但不接收推送) 之前写的 ——
**那时还没决定要做一个完整的客户端。**

现在的事实是:推送与问答已经走微信
([ADR-018](#adr-018--微信推送走-ilink-bot-api企微降为兜底与审批入口)),
企微只剩"兜底通道"和"日历数据源"两个角色,而 P1 本来就要出一个安卓 App。
**在已经有客户端的情况下再接一个第三方待办工具,是多接一个平台。**

**决策**

1. **待办与日程的落地表在服务端**(`todos`,见
   [06 §2.11](06-data-model.md#211-todos--待办与待写入的日程)),
   **App 是它的界面,不是另一个数据源**。换手机、重装 App 都不丢
2. **App 提供桌面小组件**,展示今天的待办与日程
3. **日程写回改成落到系统日历**(安卓 `CalendarContract`),由 App 执行。
   服务端的 L2 工具写的是 `todos` 里 `kind=schedule` 的一行;
   App 写入系统日历后**回报那条事件的 id**,那个 id 就是回滚信息
4. **企微退出主链路**:不再是推送入口、不再是日历数据源。
   代码留着休眠 —— 配置留空即不启用(ADR-018 已经把它整组降为可选),
   删掉会同时失去唯一的兜底通道

**小组件不违反铁律 10。** 那条铁律禁的是**接收推送**:不集成厂商推送 SDK、
不让第三方推送服务成为触达链路的一环。小组件是反过来的 ——
`AppWidgetProvider` + `WorkManager` **定时去拉**,没有任何一方向手机推送。
[ADR-014](#adr-014--客户端做完整-app-但不接收推送) 原样成立。

**理由**

**已经有客户端了。** 为待办再接滴答清单或 Notion,换来的是更好的移动端体验,
代价是多一个平台、多一套凭据,以及把"你答应了谁什么事"逐条发给第三方 ——
那恰恰是整个系统里最私人的一类内容([R12](05-risks.md#r12--外部-llm-供应商侧的数据暴露))。

**系统日历是安卓上真正的公共层。** 小米、华为、三星的日历应用都建在
`CalendarContract` 上,写进去在哪个日历 App 里都看得见,而且**不要求你装企微**。
[ADR-011](#adr-011--数据源全面本地化) 当初选企微日程的理由是"主入口已经是企微" ——
那个前提没了,结论跟着变。

回滚照旧成立:删掉那条系统日历事件,和删掉一条企微日程一样干净。

**代价(必须说清)**

- **L2 的副作用第一次发生在服务端之外。** 服务端只能保证"意图已记录",
  保证不了"设备已执行"。所以 `todos` 要有 `device_ref` 与 `synced_at`:
  没回报就是没落地,App 一联网就补。**"写了没写进去"要能被查出来,
  不能只表现为日历里少一条**
- 手机长时间不在线时日程进不了日历。这是**看得见的延迟**(App 上有状态),
  不是静默丢失 —— 后者才是不可接受的
- 小组件的刷新受各家省电策略限制。所以它是"看一眼"的入口,
  **不是提醒机制**:真正的提醒仍然走消息通道

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| 滴答清单 / Notion 等第三方待办 | 已经有客户端了。多一个平台、多一套凭据,还要把最私人的内容逐条送出境 |
| 继续用企微日程与企微待办 | 推送和问答都已经不走企微,只为日历维护一套凭据不划算,还要求你一直装着它 |
| 服务端直接写系统日历 | 做不到。系统日历在设备上,没有服务端接口 —— 这不是取舍,是事实 |
| 待办只存在 App 本地 | 服务端抽出来的待办就送不进去了,换手机也没了。**App 是界面不是数据源** |
| 给 App 加厂商推送 SDK 让待办实时更新 | [ADR-014](#adr-014--客户端做完整-app-但不接收推送) 与铁律 10,不改。小组件定时拉已经够用 |
| 小组件直连数据库 | 凭据要放进手机,而 [R11](05-risks.md#r11--app-直连服务端的认证面) 要求采集与查询凭据分开签发、可单点吊销 |

**重新评估的触发条件**

- 安卓后台限制严到小组件一天刷不了几次 → 那时用消息通道推一条"待办有变",
  **仍然不接推送 SDK**
- 系统日历写入频繁失败(设备长期离线)→ 退回"日程也发一条消息,你自己加"
- 出现第二个用户且他不用安卓 → 那是 [ADR-015](#adr-015--app-用原生-kotlin只做安卓) 的重评触发条件,不是这条

## ADR-021 · 安卓端依赖清单逐条定性

**状态**:已确认(P1 第 11 片生效)

**背景**

[ADR-015](#adr-015--app-用原生-kotlin只做安卓) 定了"原生 Kotlin、不做 iOS",
但没说用哪些库。[AGENTS.md §3](../AGENTS.md#3-写代码时) 要求
"不许引入新依赖而不补 ADR",而 App 一开工要装的东西比服务端那次还多。
与其为每个库单写一条,不如照
[ADR-017](#adr-017--p0-依赖清单逐条定性) 的做法一次性交代清楚。

判据和服务端那次一样:**适合项目才用,不为了用而用**;
以及一条 App 特有的 —— **手机上多一个依赖,就多一处要跟着 ROM 和
Play 服务变的东西**,而这个 App 要在一台被频繁清后台的主力机上活着。

**决策**

| 依赖 | 用途 | 定性 |
| --- | --- | --- |
| Kotlin / AGP / Gradle | 构建 | ADR-015 已定 |
| **Jetpack Compose**(BOM) | 界面:待办列表、待确认队列、状态页 | 新增。三个列表页,XML + Adapter 那套要写三倍代码 |
| **RemoteViews**(不是 Glance) | 桌面小组件 | 系统自带,零依赖 |
| **WorkManager** | 定时拉、心跳、上报重试 | 新增。[ADR-020](#adr-020--待办与日程落在自己的-app企微退出主链路) 已经点名它 |
| **Room** + KSP | 上报队列、日历幂等表、离线缓存 | 新增 |
| **OkHttp** | HTTP | 新增。签名要对**发出去的字节**签 |
| **kotlinx.serialization** | JSON | 新增。Kotlin 官方,无反射 |
| **kotlinx.coroutines** | 后台入口全在用 | 新增。写明版本而不是靠 ktx 传递进来 —— 传递依赖的版本会跟着别的库跳 |
| **Android Keystore**(系统 API) | 长期凭据落地 | 零依赖,见下 |
| **CalendarContract**(系统 API) | 写系统日历 | ADR-020 的落点 |
| `NotificationListenerService`(系统 API) | 采集 | [ADR-010](#adr-010--微信只做只读接入走官方通知监听) 的落点 |

`minSdk = 26`(Android 8.0)。理由不是"覆盖率"——是
`NotificationListenerService` 在 8.0 之后才有稳定的重连与前台服务行为,
而[ADR-012](#adr-012--账单采集以实时通知为主导出账单为辅) 的硬前提是
"装在日常使用的主力机上",那种机器不会停在 7.x。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **Retrofit** | 签名要对**实际发出去的字节**算(06 §6.2),而 Retrofit 把序列化藏在转换器后面,拿到那串字节要绕一圈。十个端点不值得多一层 |
| **Glance**(Compose 写小组件) | 小组件只有几行文字,RemoteViews 够用;Glance 还在往稳定爬,而小组件坏了的表现是"桌面上一片空白" |
| **androidx.security-crypto**(EncryptedSharedPreferences) | 长期停在 alpha 且已不再推荐。直接用 Keystore 生成一把 AES/GCM 密钥自己加解密,是六十行代码、零依赖,而且和服务端 `crypto.py` 的做法一致 |
| **明文 SharedPreferences 存密钥** | [R11](05-risks.md#r11--app-直连服务端的认证面) 要求长期凭据存 Keystore。root 过的手机上明文 prefs 是白送的 |
| ~~**应用内扫码**(CameraX + ML Kit / ZXing)~~ | ~~为一次性的配码动作引两套重依赖,还要一个相机权限~~ **已改判,见下面那节** |
| **深链接配码**(`lifein://enroll?...`) | **任何 App 都能注册同一个 scheme**,一次性凭据会被截走。配码改成粘贴:用系统相机扫出文字,粘进配置页 |
| **厂商推送 SDK**(小米/华为/OPPO/vivo) | [铁律 10](../AGENTS.md#1-铁律) 与 ADR-014,不改。小组件是定时去拉,不在此列 |
| **Firebase / Crashlytics / 友盟** | 会把设备标识与使用数据送到第三方,而这个 App 读的是你的全部通知 —— 与 [R12](05-risks.md#r12--外部-llm-供应商侧的数据暴露) 的取向正相反。崩溃看 logcat,单人项目够了 |
| **Flutter / React Native** | ADR-015 已否决,不重开 |
| **后台常驻的自研保活**(互相唤醒、1 像素 Activity 那类) | 各家 ROM 会针对性地封,而封的方式每个大版本都变 |
| **给采集器加一个前台服务** | `NotificationListenerService` 是系统绑定的,被杀了系统会重新绑;为它再挂一个常驻通知,换来的保活收益说不清,代价是每天都在你的通知栏里占一行。**靠系统重绑 + 心跳告警**:掉线了要能被发现,比"想尽办法不掉线"更可靠(架构 §8.6)。厂商的自启动白名单仍然要手动加,那是部署步骤不是代码 |

**两件事顺带定死**

**验证码正则在两端各存一份**,不共用配置。共用的那一刻,
[铁律 11](../AGENTS.md#1-铁律) 的"双重丢弃"就退化成一道 ——
手机端那道的全部价值正在于它和服务端那道**独立失效**(07 §4)。

**白名单从服务端拉,但拉不到时用内置的那份**(P1 只有微信)。
拉不到就全放行是绝对不行的:那等于把默认拒绝反过来
([R10](05-risks.md#r10--手机端采集器的越权读取))。

### 2026-09 改判:应用内扫码要做

**原来的否决理由站不住。** 当时算的是"一次性动作不值得引依赖",漏了两件事:

1. **粘贴那条路要求人先在服务器上跑命令、再把一串 JSON 弄进手机。**
   自己用尚可,而 [03 的 P4](03-roadmap.md#p4--多用户托管) 里朋友是
   **非技术背景**([产品定义 §2](01-product-spec.md#2-目标用户))—— 让他复制粘贴
   一段带两把 base64 密钥的 JSON,这条路实际上是走不通的
2. **相机权限"难解释"这条,解法不是不做,是按需申请。** 在用户点"扫码"
   那一刻才要权限,并且**粘贴那条路一直留着** —— 不给相机权限也配得上

**改判后的决策**

| 项 | 选择 |
| --- | --- |
| 扫码库 | `com.journeyapps:zxing-android-embedded` |
| 权限 | `CAMERA`,**点扫码时才申请**;拒绝了就回到粘贴 |
| 粘贴 | **保留**,不是降级路径而是并列的一条 |

**为什么是 ZXing 而不是 ML Kit**:ML Kit 的免捆绑版依赖 Google Play 服务,
而这个 App 的目标机型是**国内的安卓主力机**([ADR-012](#adr-012--账单采集以实时通知为主导出账单为辅) 的硬前提),
那上面 Play 服务不一定有 —— 表现会是"扫码页打开就报错",而且只在真机上出现。
捆绑版能绕开这条,但体积明显更大。ZXing 是纯 Java、不依赖 Play 服务,
在国内环境里是更稳的一边。

**仍然否决的**:`lifein://` 深链接配码。任何 App 都能注册同一个 scheme,
一次性凭据会被截走 —— 这条和扫码是两件事,没有跟着改。

**P4 要再改一次(现在就写下来)**

今天的二维码里是**明文的两把密钥**,而它是从你自己的屏幕上扫走的,
一次性、当场用掉,可以接受。但 P4 把配码发给朋友时,那张图会走微信 ——
**等于把密钥发在聊天里**。那时要改成"二维码里只放一次性换取码,
App 拿它去换真凭据",而换取码几分钟就过期。

同一批要补的还有:**朋友不该需要碰服务器**。签发配码这件事得挪进
[P4 的 Web 控制台](03-roadmap.md#p4--多用户托管) —— 03 把它放在 P4 的理由
本来就是"账号与授权管理",配码正是其中一项。

**重新评估的触发条件**

- Glance 稳定且小组件要展示更复杂的东西 → 那时再换,采集侧不动
- 需要在 App 里手动补一笔并拍小票(P2)→ 那时才引相机相关依赖,
  与配码扫码是两件事,不要因为"反正都要相机"提前引进来
- 多设备(第二台手机)→ 配码流程要重做,那时再考虑一次性配码链接
  的安全形态,仍然不用 scheme 深链接


### 2026-09 补充:小票识别放在手机上

[06 §6.12](06-data-model.md#612-手动补一笔与拍照记小票-appledger) 把这件事
挂在"P2 收尾时定"。现在定了:**在手机上识别,照片不上传。**

**决定它的是一条,不是权衡的结果:照片里有的东西比一笔账多得多。**
一张餐厅小票的照片里可能有同行的人、邻桌、你的手、店里的装修 ——
而记账要的只有金额、时间、商户。
[R10](05-risks.md#r10--手机端采集器的越权读取) 对交易类的口径是
"只保留金额、时间、卡号后四位、商户",而**不上传是兑现那句话最彻底的方式**:
服务端从来没收到过的东西,不需要承诺"不留"。

| 项 | 选择 |
| --- | --- |
| 识别库 | `com.google.mlkit:text-recognition-chinese`(**打包版**,不是 Play 服务版) |
| 权限 | `CAMERA`,**点"拍小票"时才申请**;拒绝了仍然能手填 |
| 上传什么 | 只有识别出来的字段。**照片不出手机,识别完就丢** |
| 落到哪 | `pending_confirmations`,不直接入账 |

**打包版而不是 Play 服务版**,和 ADR-021 那句"手机上多一个依赖,就多一处要跟着
ROM 和 Play 服务变的东西"是同一条:Play 服务版体积小,但它在没有 Play 服务的
国内 ROM 上会静默降级成"识别不出来",而那和"这张小票拍糊了"长得一模一样。
代价是 APK 大约多 20 MB —— **这个代价是明知道并且接受的**。

**识别结果一律进待确认。** 小票上的数字里,"实付"和"原价"、桌号和金额长得
一样近;而 [03 那条"误记率 = 0"](03-roadmap.md#验收标准-2)不区分错误来自模型
还是来自 OCR。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **服务端识别 / 视觉模型读图** | 照片要真的上传一次。§6.12 写着"原图不留",而**最彻底的"不留"是没收到过** —— 一旦收到,那句承诺就要靠代码每次都做对 |
| **Play 服务版 ML Kit** | 见上面那段。体积换来的是"在一部分手机上安静地不工作" |
| **Tesseract** | 中文准确率不够,而**认错一个小数点就是一笔错账**;训练数据文件也不小 |
| **不做,只留手填** | 手填一笔要点七八下,而现金消费本来就是最容易懒得记的那种。P2 的验收标准写着"手动操作只剩两类",拍一张照比填七个字段更接近那句话 |

**重新评估的触发条件**

- 识别出来的金额经常要改 → 那时的问题不在库,在**取哪一行**:小票上金额有好几个
  (小计、优惠、实付),先把挑选规则写清楚再考虑换库
- APK 体积成为问题 → 换 Play 服务版,并接受"部分手机上不工作",
  那时要在界面上说清楚而不是静默失败
- 需要读发票(不只小票)→ 发票有固定版式和二维码,**那条路根本不该走 OCR**

## ADR-022 · 服务端搬到云服务器,用已备案域名的子域名

**状态**:已确认(P1 收尾生效)。**迁移尚未执行** —— 执行步骤见
[08 §6](08-deployment.md#6-搬到云服务器p1-收尾)。

**背景**

P1 的安卓 App 要一个手机够得着的入口,而这件事在原来的部署形态下过不去:

- 家里那台机器**没有公网入口**。日志里入站请求全部来自 `127.0.0.1`,
  企微回调一次都没有被打进来过 —— [ADR-001](#adr-001--推送与审批入口选企业微信)
  留的那个"审批与问答入口"其实一直是虚的,只是没人注意,因为
  [ADR-018](#adr-018--微信推送走-ilink-bot-api企微降为兜底与审批入口)
  之后推送和问答都走微信 iLink 的**长轮询**(出站),不需要公网
- 安卓从 9 起默认拒绝明文流量,而 App 的查询接口带的是 bearer token
  ——明文过网等于把账本交出去([R11](05-risks.md#r11--app-直连服务端的认证面))
- 那台机器**会关机、会睡眠**。而这个系统最危险的失效方式是
  [安静地停跑](05-risks.md#r9--单点自托管可用性):它停了没有任何外部表现,
  只是提醒和摘要悄悄不来了。`scripts/run-lifein.cmd` 里那套
  "开机自启、崩了重启"正是在跟这条打架 —— 打不赢,因为机器关了脚本也不在

**决策**

**P1 收尾起,服务端整体跑在云服务器上**:FastAPI + PostgreSQL + 调度器
同一台,对外只开一个已备案域名的**子域名**(备案是按域名的,子域名跟着走)。
家里那台不再跑常驻服务。

TLS 由反向代理终结(Caddy 或 nginx + Let's Encrypt),FastAPI 仍然只监听
`127.0.0.1`([07 §2.1](07-config.md#21-基础) 那条不变)。

**理由**

三件事同时被解决,而它们本来是三个不同的问题:App 有了稳定入口、
可用性不再取决于一台桌面机开没开、企微回调那条一直虚着的路补上了(P3 要用)。

**备案已经有了**——国内这条链路上最贵、最慢的一步已经付过,复用它的边际成本
接近零。这也是"为什么是现在"的答案:换个时间点,这个决策要多花两周等备案。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **继续放家里 + 内网明文 HTTP** | bearer token 明文过网,同一个 WiFi 下截到就能读你的待办与记忆(R11)。要开 `usesCleartextTraffic` 才跑得起来,那是把一条防线换成"反正是内网"这个假设 |
| **家里 + 自签证书** | 要改 App 的 `network_security_config` 去信任自定义 CA 并重新发版;以后每次换证书还得再动 App。**App 改一次要重新发版**,这条在 [AGENTS §9](../AGENTS.md#9-当前状态) 里就是排期的依据 |
| **家里 + Tailscale 组网** | 真能用,`*.ts.net` 是公共 CA 签的真 HTTPS。但它只解决"够得着",没解决"机器会关机"那一半 —— 而那一半是 R9。**留作退路**,见重评触发条件 |
| **云上只做入口(frp/nginx 转发回家),数据留家里** | 数据不出门确实更好,但整条链路最脆的一环仍然是家里那台机器,而它正是要解决的问题。多一条会断的隧道,换来的是把故障点从一个变成三个 |
| **和另一个项目挤同一台服务器** | 那台跑着已经全流程走通的东西。混部会让两套系统的故障、依赖、升级互相牵连,而这套系统的定位是"每天稳定跑" |
| **上 Docker Compose 编排** | 单机单进程 + 一个 PostgreSQL,systemd 两个单元就够。引入编排只增加一层要维护的东西,与 [ADR-016](#adr-016--服务端用-python--fastapi) 拒绝消息队列是同一条理由 |

**代价(必须说清,这条比运维代价重要)**

**"自托管"的含义变了。** 从今天起,你的邮件正文、事实库、待办躺在**租来的
机器**上。[R1](05-risks.md#r1--代管他人凭据与支付数据) 与
[R12](05-risks.md#r12--外部-llm-供应商侧的数据暴露) 的口径要跟着改 ——
产品定义里"自托管"那句话原本的意思是"数据在你自己的硬盘上",现在不是了。

具体多出来的三件事:

1. **云厂商是新的信任方**。磁盘快照、控制台权限、工单里的运维人员都是新的暴露面
2. **主密钥的处境更尴尬**。`MASTER_KEY` 仍然只在 `.env` 里,而 `.env` 会跟着
   磁盘快照一起被复制。[03 的 P4 门槛](03-roadmap.md#前置硬门槛不满足则不开放)
   里那条"凭据加密从环境变量升级为 KMS"从"以后再说"变成**更该早点做**
3. **P4 的算盘要重算**。那时库里是朋友的邮件,而朋友同意的是把数据交给你,
   不是交给你租的服务器 —— 这条要写进 P4 的隐私说明

**迁移当天最容易翻车的一条**:`MASTER_KEY` 与 `MASTER_KEY_VERSION` 不跟着搬,
`credentials` 里所有凭据**全部解不开**(信封的 AAD 绑了 `user_id` 与 `kind`,
密钥不对就是 `DecryptError`,不是"读出乱码")。表面症状是"迁完了但采不到邮件"。

**重新评估的触发条件**

- 云服务器到期、涨价、或线路不可用 → 退回家里 + Tailscale
  (那条路一直留着,而且不需要域名和备案)
- **P4 朋友接入** → 那时数据里有别人的东西,"放不放云上"要按 R1 重新算一遍,
  不能沿用今天这个答案
- 数据量或成本涨到单机撑不住 → 先拆 worker 进程,仍然不换语言
  ([ADR-016](#adr-016--服务端用-python--fastapi) 那条不变)

## ADR-023 · 对账单解析:PDF 用 pdfplumber,压缩包先用标准库

**状态**:已确认(P2 第 7、8 片生效)

**背景**

[ADR-012](#adr-012--账单采集以实时通知为主导出账单为辅) 的两阶段入账里,
第二阶段要读两种东西:**信用卡月度对账单 PDF**(带打开密码)和
**支付宝 / 微信的账单导出**(带密码的压缩包 + CSV)。
[AGENTS.md §3](../AGENTS.md#3-写代码时) 要求不许引入新依赖而不补 ADR。

判据和前两次一样(ADR-017、ADR-021):**适合项目才用**。
这里还多一条 —— **这两个格式我一年只见十二次**,
所以库出问题时我不会有大量样本去调试,
那意味着**能不能看清它为什么解错**比"解析率高几个百分点"更重要。

**决策**

| 依赖 | 用途 | 定性 |
| --- | --- | --- |
| **pdfplumber** | 信用卡对账单 PDF:解密 + **按表格取单元格** | 新增。它自己会带来 `pdfminer.six`、`Pillow`、`pypdfium2` |
| `zipfile`(标准库) | 支付宝 / 微信导出的压缩包 | 零依赖 |
| `csv` + `codecs`(标准库) | 导出的 CSV,多半是 GBK | 零依赖 |
| `cryptography` | PDF 的 AES 解密后端 | **已经在依赖里**(ADR-009 的凭据加密用它) |

对账单是一张表,而我们要的是"第 3 列的金额配第 5 列的商户"。
`pdfplumber.extract_table()` 直接给行列,**取错了能一眼看出是哪一格**。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **pypdf 单独用** | 它能解密,但只给一整段文本。对账单是表格,拉平成文本之后列就没了 —— 要靠正则从一行里猜哪个数字是金额哪个是余额,而那正是[第 2 片](../AGENTS.md#p2-的实施顺序)在交易短信上已经踩过的坑。**这里本来有列,不该主动扔掉** |
| **PyMuPDF (fitz)** | 解析质量最好,但 AGPL —— 这个项目自己用没问题,而 [03 的 P4](03-roadmap.md#p4--多用户托管) 是给朋友托管,那时"分发"的边界要请人看,而我不想为一个一年跑十二次的功能引一次法务判断 |
| **camelot / tabula-py** | 表格提取更强,但 tabula 要装 JVM。为一个月度任务在服务器上装 Java,而这台机器的定位是"能被 systemd 拉起来的单进程"(ADR-016) |
| **LLM 直接读 PDF 文本** | 金额绝不过模型([铁律 9](../AGENTS.md#1-铁律))。而且对账单一次几百行,是模型最容易漏行、串行的形状——**漏一行的表现是账本少一笔,而漏记不会有人提醒你** |
| **pyzipper**(AES 压缩包) | **暂时不引**,见下 |
| **自己写 PDF 解析** | 不是这个项目要解决的问题 |

**压缩包先用标准库,是一个赌**

标准库的 `zipfile` 只认传统的 ZipCrypto,不认 WinZip AES。
支付宝和微信的导出**目前**是前者,所以标准库够用;哪天不够用了,
症状是明确的(`RuntimeError: Bad password` 或 `NotImplementedError: AES`),
那时再引 `pyzipper` 一行就够。

**先不引**的理由不是"能省一个依赖",是**在没见过失败之前,
我没法判断该引哪一个** —— 而引错了的代价是它会一直在依赖表里躺着。

**重新评估的触发条件**

- **拿到真实对账单后 pdfplumber 取不出表**(扫描件、图片型 PDF)→
  那时的选择不是换库,是**换通道**:这一家的账单改用支付宝/微信导出那一路。
  OCR 不在考虑范围,金额靠 OCR 认是拿准确率换方便
- 压缩包报 AES 相关的错 → 引 `pyzipper`,补一条到 ADR-017 的清单里
- pdfplumber 停止维护,或跟不上 Python 版本 → 退回 pypdf + 正则,
  并接受"从一行文本里认金额"的那些坑
- **P4 之前**:朋友的对账单格式各不相同,而这一片是按我自己那两三家银行写的。
  那时要么让朋友只用支付宝/微信导出那一路,要么按银行做适配 ——
  [03 的 P4 门槛](03-roadmap.md#前置硬门槛不满足则不开放)里没写这条,是个缺口

## ADR-024 · P3 的审批编排不引 LangGraph,用 `approvals` 表 + 已有网关

**状态**:已确认(P3 生效)。**它推翻了
[ADR-002](#adr-002--p0p2-不引入-agent-编排框架) 里"P3 引入状态机编排"那一句。**

**背景**

ADR-002 写着 P0–P2 不引框架,**P3 引入**,理由是:

> 真正需要框架的时刻是 P3 的审批流程:一个流程要**暂停数小时等用户点按钮,
> 然后从断点恢复**。这是长时间运行、可中断、可持久化的流程,
> LangGraph 的 checkpoint / interrupt 机制正是为此设计的。

那句话是在 P0 之前写的,当时手上还没有代码。现在到了 P3,该按 ADR-002 自己那条
"重新评估的触发条件"重新算一遍 —— 而算下来结论反了。

**决策**

**不引入 LangGraph 或同类。** 审批的暂停与恢复用 `approvals` 表
([06 §2.8](06-data-model.md#28-approvals-与-pending_confirmations-的区别))
加已有的[网关](../lifein/governance/gateway.py)实现。

**理由:那个"断点"只有一个,而且已经建好了**

写 ADR-002 时想象的是一张图:若干节点、若干分支、中间任意一处可以挂起。
真到 P3,L3 那三件事(代发消息、提交表单、预约)的形状是同一条直线:

```
agent 提出        → 网关拦下(已经有了:_handle_l3)
                  → 写一条 approvals(要做的这一片)
   ⏸ 等人点按钮   ← 断点。**整个流程只有这一个**
                  → 回调核验签名与时效(要做的这一片)
                  → 执行,记 tool_calls(网关已经有了)
```

**这条流程的"状态"是一行数据,不是一个 Python 对象。** 它有五个字段:
哪个工具、什么参数、谁提的、什么时候过期、现在是什么状态。
LangGraph 的 checkpointer 解决的是"把任意 Python 状态序列化出去再恢复回来",
而我们根本没有任意状态要存 —— 存了反而多一份和 `approvals` 表不一致的可能。

**而且这个形状在这个项目里已经跑了一期。** `pending_confirmations`(P1)
就是"agent 提出 → 挂起 → 人点一下 → 写入",从 2026-09 起每天都在用。
**同一个形状用两次,比引一个框架去做第二次更可靠** ——
第二次会长得和第一次一样,而看代码的人不用学两套。

**还有一条不那么技术的理由:审批是这个系统里最危险的一条路。**
它是唯一会动外部世界的路径,而 03 给它的验收标准是"零重复执行、零越权"。
把它放进一个我还不熟悉其失效方式的框架里,意味着网关那几条不变量
(L3 必须 `user_input`、每次调用留审计、L2 必须带回滚)都要在框架内部
重新建立一遍 —— 而**重建一条安全不变量的成本,远高于它看起来的样子**。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **LangGraph** | 见上。它的 checkpoint / interrupt 是为"图上任意点挂起"设计的,而我们只有一个挂起点,状态是一行表 |
| **Temporal / Airflow 之类的工作流引擎** | 量级完全不对。它们要独立的服务进程,而 [ADR-016](#adr-016--服务端用-python--fastapi) 定的是"能被 systemd 拉起来的单进程" |
| **把审批状态放进内存 + 定期落盘** | 进程重启就丢。而这条流程的暂停时长是**小时到天**,重启是必然事件 |
| **复用 `pending_confirmations` 那张表** | 差一点就选了它。否决的理由是 06 §2.8 已经写清两者拦的不是同一件事:一个拦"要动外部世界",一个拦"agent 对自己没把握"。**合表会让那条 `CHECK`(L3 只能由 user_input 触发)没法只作用在该作用的那一半上** |

**重新评估的触发条件**

- **L3 流程出现第二个挂起点**(比如"预约失败 → 换个时段再问一次你"),
  或者出现真正的分支 → 那时状态就不是一行表了,重新算
- **要在一次审批里串起多个 agent 的往返** → 那是编排问题,不是状态问题
- P4 的 Web 控制台需要展示"流程走到哪一步" → 先看 `approvals` 加两个字段
  够不够;不够再说
- **出现任何一次重复执行**(03 的退出条件)→ 先查幂等键,不要先怪没有框架

## ADR-025 · 代发消息由一次「只看你这句话」的模型调用提出

**状态**:已确认(P3 补上,2026-09)。

**背景**

P3 的整条 L3 链路建完之后有一个洞:**没有任何 agent 会往 `approvals` 里放东西。**

`message.send` 注册了(L3、有预览),网关会把 L3 转成审批,回调能把 `pending`
改成 `approved`,执行 job 会去做 —— 但没有一个 agent 的白名单里有它,
所以生产里这条链路**一次都不会被触发**。
它是一段编译得过、测试也绿、而永远不会运行的代码。

而 [03 的 P3 范围](03-roadmap.md#p3--审批执行)写的是
"L3 工具首次上线(**代发消息**、提交表单、预约)",验收标准是
"完成 20 次真实 L3 操作" —— 20 次真实操作需要有人能发起。

**问题不在"给谁加白名单",在铁律 8**

唯一自然的发起点是问答:你在企微里说"帮我给老王发一条,今晚饭局我去不了了"。
所以该给 `qa` 加 `message.send`。

但 `qa` 这个 agent 的输入里**装满了外部内容** —— 检索回来的邮件、群消息、
从它们推断出的事实。而 [铁律 8](../AGENTS.md#1-铁律) 是
"**L3 永远不由外部内容触发**"。

网关那道 `ctx.trust is not USER_INPUT` 挡不住这一种:问句确实是你打的,
所以 `trust` 确实是 `user_input`。而一封写着"请帮我转告所有人……"的邮件
被检索回来之后,模型完全可能把它当成要执行的事,而那张审批卡片会长得
非常像你自己要的东西。

**决策**

**代发消息的提议由一次单独的模型调用产生,那次调用只看你自己打的那句话,
一个外部素材块都不带。**

```python
plan_action(question, llm=...)      # blocks=[]，user_instruction=question
```

和 `plan_recall` 是同一个形状 —— 那一步同样只看问句(因为"从中文问句里认出
人名"没有可靠的规则写法)。**同一个形状用两次,比为第二次发明一套新的更可靠。**

于是铁律 8 在这条路上是**结构性成立的**,不是靠模型自觉:
提议阶段的上下文里根本没有外部内容,注入进不来。回答阶段照旧带全部素材,
但那次调用的输出里没有"要做什么"这个字段。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **让回答那次调用顺便输出一个 action** | 少一次调用、省一点钱,但**外部素材和"要做什么"进了同一个上下文** —— 这正是要避免的那件事。省下的是几分钱,赌上的是铁律 8 |
| **加一层"这个提议是不是来自外部内容"的检测** | 检测器同样是模型,同样可以被绕过。**用一个可能出错的东西去守另一个可能出错的东西,不是防线** |
| **要求提议里的正文必须逐字出现在问句里** | 挡得住注入,但也挡死了正常用法:"帮我回一下老王说我晚点到"里,真正要发出去的话本来就要模型来组织 |
| **不做这条路,让 L3 停留在"有接口没调用方"** | 那等于 P3 没做完。而更糟的是**一段没有调用方的代码看起来是做完了的** —— 下一个人不会去查它有没有被调用过 |
| **给 `qa` 直接加白名单、不改任何输出结构** | 白名单只决定"能不能调",不决定"什么时候调"。不改输出结构的话,agent 没有任何途径表达"我想发一条消息" |

**代价**

- 每次问答**可能**多一次模型调用。只在问句看起来像"让我去做一件事"时才发生 ——
  `plan_action` 的 prompt 明确要求"是提问就返回空"
- 提议阶段看不到检索结果,所以它写不出"根据你上周那封邮件……"这种内容。
  **这是有意的**:要发出去的话应该来自你的指令,不是来自系统翻到的东西

**重新评估的触发条件**

- **出现第二个 L3 工具**(提交表单、预约)→ `plan_action` 的输出要从
  "一条消息"扩成"一个动作",那时重新看这个形状还合不合适
- **有人报告"它把我邮件里的话当成指令了"** → 说明这条隔离漏了,先查
  是不是哪里把素材塞进了提议那次调用
- **两次调用的成本占比明显上升** → 先看是不是 `plan_action` 被无差别地
  调用了(它应该只在像指令的问句上触发),而不是先去合并调用

## ADR-026 · 企业微信整个退出,消息面只剩 iLink 与邮件

**状态**:已确认(2026-09-10)。**它推翻了
[ADR-001](#adr-001--推送与审批入口选企业微信) 的主体**,并把
[ADR-018](#adr-018--微信推送走-ilink-bot-api企微降为兜底与审批入口)
那句"企微降为兜底与审批入口"收窄成"企微不在了"。

**背景**

ADR-018 已经把主推送搬到了 iLink,但给企微留了三条理由。到今天(P4 代码全部
落地)这三条要按 ADR-018 自己那条"重新评估的触发条件"重算一遍 ——
**而算下来三条全不成立**:

| ADR-018 留企微的理由 | 今天的事实 |
| --- | --- |
| "iLink 才半年新,唯一通道不能压在上面([R6](05-risks.md#r6--平台政策变动))" | **兜底从来就不是企微,是邮件。** 企微要配"企业可信 IP",而那需要公网域名 —— [07 §2.4](07-config.md#24-企业微信整组可选) 自己写着"对一台家里的机器,这是过不去的坎"。它**一天都没被真正配起来过** |
| "审批按钮 iLink 支不支持未知" | 审批用文字做完了(`同意 12`),而那个形状**在每条通道上都成立**。企微的按钮回调**从来没有被实现过** —— `wecom_callback.py` 只解析 `Content`,没有 `EventKey` 分支 |
| "朋友(P4)那边企微转投微信仍是零门槛" | P4 的朋友装的是 App + 用微信,整条路上不碰企微 |

**一条从来没配上、而且配不上的降级通道不是保险。** 它是三个文件的维护负担,
外加一份会让人误以为"还有兜底"的文档 —— 而后者比没有兜底更危险:
真出事的那天,你会先花二十分钟去查那条根本不存在的退路。

**决策**

**企业微信整个退出。** 消息面只剩两条:

```
主通道   微信(iLink Bot API)——  推送、问答、审批回复,收发都在微信里
兜底     邮件              ——  推送失败时降级;它不依赖任何一家平台的政策
```

`WECOM_*` 那一组配置、`channels/wecom*.py`、`sources/calendar_source.py`
以及对应的测试一并移除。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **留着代码,只是默认不启用**(现状) | 这正是现状,而现状的问题就是它:一份**看起来有、实际上不可能有**的兜底。留着的代价不是磁盘,是每次读这份文档的人都要重新判断一次"企微到底算不算数" |
| **保留企微专门做 L3 审批按钮** | 按钮回调至今没实现,而文字回复已经跑通并且更通用。为一个没做的功能保留一整条通道,是拿"将来可能需要"换"现在一直要维护" |
| **换成别的兜底通道**(短信、Telegram……) | 短信要资质和钱;Telegram 在国内不可用。**邮件已经在跑,而且是唯一不依赖平台政策的一条** |
| **连邮件也撤掉,只留 iLink** | 那才是真的把全部压在一个半年新的接口上。R6 说的是"平台政策变动",而 iLink 是腾讯说了算的 |

**这次改动带走的唯一真东西:日历输入**

`WecomCalendarAdapter` 读的是企微日程 —— **别人拉你进的会议**。
企微走了它也走了,而这是本次唯一实质损失(推送、问答、审批三样 iLink 全都
已经在做)。

它也**从来没有跑起来过**(要 `WECOM_CALENDAR_ID` 和一个能用的企微应用),
所以撤掉不改变今天的行为。但它挡着的那个需求是真的,替代方案也是现成的:

> **从手机的系统日历读。** App 已经声明了 `READ_CALENDAR`(它本来就要写日历,
> 见 [ADR-020](#adr-020--待办与日程落在自己的-app企微退出主链路)),
> 而**读系统日历覆盖的是所有日历** —— 企微的、飞书的、iOS 同步过来的、
> 手动建的。比只读企微那一个严格更好。

**已经补上了**(2026-09-10,紧接着这次改动):契约在
[06 §6.14](06-data-model.md#614-日历采集-post-ingestcalendar),
归一化在 `sources/device_calendar.py`,设备侧在 `calendar/CalendarReader.kt`
与 `work/CalendarCollectWorker.kt`。

那一片里最要紧的一条是**回环**:App 会把提取出来的日程写进系统日历
(ADR-020),而现在它又读同一个日历 —— 不排除的话一条日程会指数级繁殖,
每一轮都长得像真的。挡它的是 `calendar_links` 那张本地表。

**重新评估的触发条件**

- **iLink 的接口变了或者账号被限**(R6 真的发生)→ 那时要答的不是
  "把企微加回来",是"还有没有第三条能主动触达的路" ——
  而邮件那一条在,不是零
- **出现一个只有企业微信才能做到的需求**(比如要给一个组织里的多个人推)
  → 那时重新评估。**但先问一句:那个需求是不是可以用别的形状满足**
- **iLink 支持了交互式卡片与按钮回调** → 审批的预览可以做得更好,
  但那是锦上添花:文字"同意 12"已经满足 03 的验收标准

## ADR-027 · 审批用文字回复,不做交互卡片

**状态**:已确认(2026-09-10,补记一个 P3 就做了、但一直没写下来的判断)。
它把 [ADR-001](#adr-001--推送与审批入口选企业微信) 那条"交互式模板卡片 +
按钮回调是硬需求"正式撤掉。

**背景**

[03 的 P3 范围](03-roadmap.md#p3--审批执行)写的是"企微交互卡片回调链路
(签名校验、时效校验)",而做出来的是**回一句"同意 12"** ——
`wecom_callback.py` 只解析 `Content`,一个 `EventKey` 分支都没有。
**那个按钮回调从来没有被实现过**,而理由只写在 `jobs/approval_reply.py`
的模块注释里:

> 回一句"同意 12"在**每一条通道上都成立** —— 微信、企微、甚至邮件回信。

那句话是对的,但它是一句代码注释,不是一次记录在案的决策。而
[AGENTS §4](../AGENTS.md#4-文档没写的怎么办) 要求推翻已记录的决策要写 ADR。

**今天这不再是一道选择题**

两件事把它变成了唯一解:

1. [ADR-026](#adr-026--企业微信整个退出消息面只剩-ilink-与邮件) 之后企微没了
2. **iLink 根本没有交互卡片。** 协议的 `item_type` 只有五个:
   文本(1)、图片(2)、语音(3)、文件(4)、视频(5)。
   用户能做的只有发文本或媒体 —— 协议里**不存在**"点一下产生一个结构化
   事件"这种东西

**决策**

**审批走文字。** 卡片推过去,人回一句 `同意 12` 或 `拒绝 12`。

**为什么它够用,而不只是"只能这样"**

03 给 P3 的验收标准是两条,而第二条**用文字反而更容易满足**:

| 验收标准 | 文字方案 |
| --- | --- |
| 20 次真实 L3 操作,零重复执行、零越权 | 和交互形式无关。挡住它们的是幂等键、状态机认领和那条 `CHECK`([ADR-024](#adr-024--p3-的审批编排不引-langgraph用-approvals-表--已有网关)) |
| **预览文本你一眼能看懂在做什么,不需要点开细节** | 文字消息**没有"点开细节"这个概念** —— 预览就是全部。而卡片天然会诱使人把内容折进详情页里 |

**代价,一条都不藏**

- **打错数字会批错那一条。** "同意 12" 打成 "同意 21" 会同意另一条审批 ——
  **这是这个方案最真实的风险**,不是一个可以忽略的边角。两道挡它:

  1. 确认卡片**把内容原样回显**("替你发一条消息:今晚饭局我去不了了")。
     打错的那一刻他就看得见
  2. `approved` 也能被拒绝,**只要执行还没认领**
     ([06 §2.8](06-data-model.md#28-两个队列不许合并)那条 `approved → rejected`)。
     看得见还要停得下来 —— 写这份 ADR 时才发现第 2 条原来没有:
     `rejected` 只能从 `pending` 来,于是他只会收到一句"已经同意过了,正在做"

  认领之后仍然撤不回来,而那时如实说"正在做,已经撤不回来了" ——
  "以为撤回了、其实发出去了"比"撤不回来"糟得多
- 多打几个字。审批是一天几次的事,不是几十次 —— 但如果哪天变成几十次,
  这笔账要重算(见下面的触发条件)
- 没有"点下去"那一瞬的反馈,所以执行前后各回一条消息补上

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **为审批单独保留企业微信** | ADR-026 刚算过这笔账:一条配不上的通道不是保险。而这里是为一个**从没实现过**的功能保留一整条通道 |
| **在 App 里做审批界面** | **差一点选了它** —— App 有界面,按钮真做得出来。否决的理由是:L3 的触发点是一条消息(你在微信里说"帮我回复老王"),让人为了点一个按钮切到另一个 App,和 [ADR-018](#adr-018--微信推送走-ilink-bot-api企微降为兜底与审批入口) 当初要消灭的"收在微信、回在企微"是**同一种割裂**。而且 App 不收推送([铁律 10](../AGENTS.md#1-铁律)),他根本不知道有东西等着他点 |
| **消息里放一个链接,点开跳 Web 控制台批** | 控制台的一次性链接十五分钟过期,而审批可以等 24 小时。要么让链接活得更久(削弱 [§2.14](06-data-model.md#214-console_links--控制台的一次性链接) 那条设计),要么他点开时已经过期 —— 而"点开发现过期"比打四个字烦得多 |
| **把数字换成短语**("同意刚才那条") | 队列里有两条时"刚才那条"是歧义的,而**歧义在 L3 上的代价是发错消息**。数字难看,但它指得准 |

**重新评估的触发条件**

- **iLink 支持了交互卡片与按钮** → 那时值得重做,但先问一句:
  03 那条"一眼能看懂"现在过不过得了?卡片很容易把内容折进详情页
- **出现一次"批错了那条"而且没能撤回来** → 那说明回显加撤回这两道不够,
  要重新算。而**先做的仍然不该是上按钮** —— 按钮防不住手滑,
  它防的是"看不懂在批什么",而那件事文字已经做得更好
- **L3 从一天几次变成几十次** → 打字的代价变了,这笔账要重算

## ADR-028 · 账目的增删改只在 App 里,对话式只读

**状态**:已确认(2026-09-10,补记一个 P2 就做了、但一直没写下来的判断)。

**背景**

[03 的 P2 范围](03-roadmap.md#p2--财务与账单)有一行:

> 账单增删改与组合查询(按时间 / 类别 / 关键字),**在企微里对话式完成**

做出来的是**一半**:查(`ledger.query` / `ledger.spending`,都是 L1 只读)
在对话里;增删改只在 App 里(`POST` / `PATCH` / `DELETE
/app/ledger/transactions`)。`qa` 这个 agent 的白名单里没有任何写账工具。

理由写在 `agents/qa.py` 的注释里:

> 对话式的改账要多一次点头,走待确认那条路,因为"把昨天星巴克那笔改成餐饮"
> 多了一次可能理解错的机会

同样是一句代码注释,不是一次记录在案的决策。

**决策**

**对话式只读。改账在 App 里做。**

**三条理由,第二条是决定性的**

1. **理解错的代价不对称。** 账本上错一笔会让**每一个统计数字**都不可信,
   而 03 给 P2 的退出条件是"出现错记就停下来补防误判层"。
   查错了顶多答得不对,改错了要靠人自己发现
2. **对话里指代不准。** 改账要指定**哪一笔**,而"昨天那笔""刚才星巴克那笔"
   在同额同商户时是歧义的 —— 便利店连买两次同价的东西是真实存在的
   ([06 §2.6](06-data-model.md#26-去重与对账的三个层次) 为这件事专门放弃了
   唯一约束)。消歧要来回问两轮,而**那时候不如打开 App 点一下**
3. **App 那条路已经存在,而且更好。** 账本列表里点进去改,
   你看得见改之前和改之后 —— 对话里只看得见你说的那句话

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **走待确认队列**(agent 提出改动,人点头确认) | **差一点选了它**,而且机制全都现成:`pending_confirmations` 加上 `txn.record` 的确认路径刚做完([06 §6.7](06-data-model.md#67-待确认队列-apppending))。否决的理由是它把"点一下就改完"变成了三步 —— 说一句话、收到一条待确认、去 App 点确认 —— 而**终点还是 App** |
| **给 `qa` 一个 L2 的改账工具** | L2 要可回滚,而改账的回滚就是"改回去",做得到。真正拦住它的是上面第 1、2 条,不是等级 |
| **只做删除、不做修改** | 删比改更危险,不是更安全。而"删掉再手动补一笔"恰好是金额抠错时**推荐**的做法([06 §6.7](06-data-model.md#67-待确认队列-apppending)),那条路已经有了 |
| **照 03 原样做全套** | 那一行是 P2 开工前写的,而它假设的交互面是企微的对话。今天回头看,它把"能在对话里做"当成了"应该在对话里做" |

**重新评估的触发条件**

- **App 里改账的路径被证明太长。** 最可能的场景是"看到摘要里那笔错了",
  而那一刻手边只有微信 —— 那时要考虑的是"从摘要里直接改",
  不是"在对话里改"
- **记账准确率高到几乎不需要改** → 这条就不重要了
- **出现不装 App 的用户**([产品定义 §4 降级矩阵](01-product-spec.md#4-交互形态))
  → 他本来就没有账本界面,那一档的账本能力要整个重新算,不只是改账这一件

## ADR-029 · 控制台分成用户层与运营层,运营层加一个口令认证面

**状态**:已确认(2026-09-10)。**它推翻了"不再加认证面"那条判断的一半** ——
推翻的部分和保留的部分都写在下面。

**背景**

[03 的 P4](03-roadmap.md#p4--多用户托管) 给 Web 划的范围是三样:

> **Web 控制台**(从 P3 推迟至此):数据导出、账号与授权管理、隐私说明页 ——
> 移动端查看已由 App 覆盖,**Web 只剩这些 P4 的合规必需项**

那句"只剩"当时是对的,而它回答的是**"用户在 Web 上要做什么"**。
做完之后露出来的是另一个问题:**运营者在 Web 上什么都做不了。**

"哪台设备掉线了""这个月模型花了多少""哪个窗口一直在失败""这个朋友的账号
体检过没有" —— 一条都不在界面上。它们全在 `python -m lifein.admin` 的
三十多条子命令里,而那三十多条的入口是 SSH。

**用一把能改一切的钥匙,去做每天都要做一次的只读动作** —— 这是这条要修的东西。

**决策**

控制台分两层,一个按钮在两层之间切。

| | 用户层 | 运营层 |
| --- | --- | --- |
| 谁 | 账号本人(含朋友) | 白杨 |
| 进门 | App 里点"在浏览器打开",一次性链接。**不登录** | 口令登录 |
| 范围 | 03 那三样 + 自己的采集开关与白名单 | **只做 App 上没有、也不该有的事**:跨用户总览、用户开停、设备吊销、任务与配额、密钥轮换状态 |
| 会话 | `lifein_console` cookie,`Path=/console`,跟着那条链接一起过期 | `lifein_admin` cookie,`Path=/admin`,HMAC 签名,两小时 |

**"账本、待办、记忆不进 Web"那条没变。** 用户层的总览上只有数字(几条待确认、
本月支出、几条待办),点它跳去 App。**一个数字不会长出第二套确认逻辑,
而一份可编辑的账本列表会。**

**为什么这次接受一个认证面**

原来那句否决的话是:

> **多一个认证面就多一处会被攻破的地方**,而凭据面已经够多([R11](05-risks.md#r11--app-直连服务端的认证面))

**那句话现在仍然成立,但它比的是另一件事。** 它当时比的是"给用户加登录"
vs "一次性链接",而一次性链接**由 App 签发** —— 运营者要管的恰恰是那两样
它给不出来的东西:还没装上 App 的人的账号,和跨全部人的总览。

真正的比较对象不是"零个认证面",是 **SSH**。SSH 是这台机器上最强的一把凭据,
而它现在被用来干"看一眼有没有掉线"这种事。一个只读为主、能被单独吊销、
Path 限死在 `/admin` 的口令,比那个小。

增量被三件事压住:

1. **口令不进库。** 存的是 `scrypt` 派生值,放在环境变量里,和 `MASTER_KEY`
   同一处 —— 库被拖走时它不跟着走,而这份口令看得到全部人的数据
2. **会话是无状态的 HMAC 签名**,用主密钥派生的一把子密钥签。不建表、
   不留会话记录,过期就是过期
3. **失败有闸门**。连续失败之后这个进程在一段时间内不再受理登录

**每一次跨用户读取都写审计日志。** [09 §4](09-privacy.md) 承诺的是
"白杨在技术上读得到全部",而**读得到不等于读过之后没有痕迹** ——
那一行日志是这句承诺和"随便看"之间唯一的区别。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **继续只用 CLI + SSH** | 见上:用能改一切的钥匙做只读的事。而且它有一个更安静的代价 —— **要开 SSH 才能看的东西,会变成没人看的东西**,而"哪个窗口一直在失败"正是那种一旦没人看就会静静烂掉的 |
| **给运营者也发一条一次性链接**(CLI 里 print 一个 URL) | **差一点选了它**,零新增凭据面,形状和现有的完全一致。否决理由是它把"每天看一眼"变成"每天先开一次 SSH" —— 那正是要修的那件事,只是换了个位置 |
| **口令哈希存 `users` 表** | 哈希跟着库走。而这一份口令的权限范围是**全部人的全部数据**,它不该和它保护的东西躺在同一个地方(和"导出文件里不放凭据"是同一条) |
| **用户名 + 口令** | 运营者只有一个,用户名不增加任何保护 —— 它只增加一格要填的东西。**运营者超过一个人的那天要换掉这条**,见下面的触发条件 |
| **OIDC / 反代认证**(Authelia、oauth2-proxy 之类) | 这几条里唯一在安全上更强的。否决理由是运维量:多跑一个进程、多一份配置、多一处会在半夜过期的证书,而 [ADR-016](#adr-016--服务端用-python--fastapi) 定的是"能被 systemd 拉起来的单进程"。**留在触发条件里** |
| **复用 App 的 Bearer token** | 浏览器打开一个链接时带不了 `Authorization` 头 —— 这正是控制台一开始就有一次性链接的原因 |
| **把运营能力做进 App** | App 装在手机上,而运维要看的是表格和时间线。更硬的理由是 [R11](05-risks.md#r11--app-直连服务端的认证面):**一把丢了就能看全部人数据的凭据,不该放在会丢的东西上** |

**重新评估的触发条件**

- **运营者超过一个人。** 一份共用口令那时就不够了 —— 要的是每人一份、
  能单点吊销、日志里分得出是谁。那一步直接上 OIDC,不要自己做一张用户名口令表
- **控制台上出现批量写操作**(比如"给所有人重跑某个窗口")。那是 L3 的形状,
  要过[审批队列](#adr-024--p3-的审批编排不引-langgraph用-approvals-表--已有网关),不是加一个按钮
- **口令泄露过一次。** 不要换一个新口令了事 —— 换成 OIDC,把这一面交出去
- **朋友开始要在 Web 上处理待确认。** 那说明 App 那条路在某种场景下不通
  (最可能是"手机在充电,人在电脑前"),那时要重新算"账本、待办、记忆不进 Web"
  这一条,而不是偷偷加一个页面

## ADR-030 · 库版本落后由进程自己发现,并在空闲时段自己补上

**状态**:已确认(2026-09-10,一次真实事故之后)。

**背景**

2026-09-10,同一封告警把邮箱刷了 **85 次**:「审批执行异常 —— column
"started_at" does not exist」。查下来审批那条链路一行代码都没错 ——
**真库停在 `0007`,而代码已经在 `0014`**。0008–0014 是 09-08 与 09-09
提交的,而部署那一步漏了 `alembic upgrade head`。

要紧的不是漏了一条命令,是**漏掉之后没有任何一处发现它**:

- 进程在当天 09:23 重启过。**重启没发现。** 启动只校验环境变量
  ([config.py](../lifein/config.py) 那句"失败必须尽量早"),不看库
- 缺的那一列第一次被读到,是在审批 job 里。于是"部署少跑了一条命令"
  这件事,以「审批执行异常」的形状每三分钟报一次
- 同一个根因还伪装成了另一条:「月度报告异常 —— column "attempts"
  does not exist」。**一个原因,两个看起来无关的症状**

[08 §1.6](08-deployment.md#16-装) 与 [§6.2](08-deployment.md#62-把代码和配置搬上去)
把 `alembic upgrade head` 写成人工步骤 —— 而这次证明了那句"写在文档里"
和"它会被执行"之间的距离。

**决策**

**库版本这件事从"人记得做"改成"进程自己负责"。** 四条:

1. **启动即校验。** `python -m lifein` 在装配之前比一次:库里的
   `alembic_version` 对代码里的 head
2. **落后就升。** `SCHEMA_AUTO_UPGRADE`(默认 `true`)开着时,启动期直接
   升到 head 再继续跑。**关掉时启动直接失败**,并在退出信息里写清差几个版本
3. **空闲时段再核对一次。** 每天 `SCHEMA_CHECK_AT`(默认 `04:00`)做一遍
   同样的判断,落后就升
4. **只向前,不向后。** 库上的 revision 代码不认识时(库比代码新,或者
   来自另一条分支)**永远不动它**,只告警

**每一次真的升级都告警一次 —— 成功也告警。** 一次无人值守的结构变更
不该只留在日志里。

**理由:它跑的不是"任意迁移",是这次部署自己带来的那些**

"让服务进程自动改库结构"听起来比它实际的样子危险。
`migrations/versions/*.py` 和 `lifein/` 是**同一个 git 提交的产物** ——
自动升级做的事情不是引入新变更,是**把你已经做过的那次部署做完**。
真正的新变更早在 `git pull` 那一刻就到这台机器上了,自动升级只是让库
跟上它。

**而"升到一半"这个最可怕的状态在 Postgres 上不存在。** DDL 在事务里,
alembic 每个版本一个事务,失败整条回滚 —— 这也是 alembic 启动时那句
`Will assume transactional DDL` 的含义。所以自动升级的失败形态是
"没升,并且告诉你没升",不是"升坏了"。

**为什么启动期也升,不是只在凌晨那一次**

落后的库不会让进程起不来,它让进程**部分不可用** —— 而这次的表现是每三
分钟一封告警。等到凌晨四点,意味着这一整天都在发那封信。

**为什么关掉自动升级等于启动失败,而不是"启动之后告警一下"**

告警需要有人看。而"库版本落后"恰恰发生在**没人在看**的时候 ——
这次那 85 封信里,没有一封在两小时内被处理。
`systemd` 的 `Restart=always` 会让它每 30 秒重试一次、每次写一行日志,
**那是这台机器上最响的一种失败方式**,比一封会进垃圾箱的邮件响得多。

**为什么空闲时段还要再来一次**

因为 `migrations/versions/*.py` 是 **alembic 在运行时从磁盘读的**。
一次 `git pull` 不重启进程,磁盘上的 head 就已经前进了 ——
那种漂移只有重启才会暴露,而这个进程可能几周不重启
(`Restart=always` 只在它崩的时候重启它)。

那一次升级会把库升到**比正在跑的代码更新**的位置。这不是新问题 ——
不升的话库就落后于磁盘上的代码,两头都是漂移 —— 但它值得说出来,
所以那条告警里带一句"进程还在旧代码上,重启它"。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **维持现状:部署文档里写一行 `alembic upgrade head`** | 就是现在的做法,而它这次没被执行。**能被漏掉的步骤迟早会被漏掉** —— 尤其是家里那台 Windows 上"手动重启一下"那条路,它根本没有部署脚本。**这一行不删**,自动升级是它的兜底,不是它的替代 |
| **只告警,不自动升级** | 那正是这次事故的形状:告警发了 85 次,而它要的动作是一条命令。**一个只能靠人执行的修复,和没有修复的区别只在于你会不会内疚** |
| **启动时无条件 `upgrade head`,不做判断** | 分不出"落后"和"库上的版本代码不认识"。后者自动升级等于拿一条不该跑的迁移链去动一个不属于这份代码的库 —— 恢复演练用的 `lifein_drill` 就是这种库 |
| **不用 alembic,在 ORM 层 `create_all()` 把缺的表建出来** | [db.py](../lifein/db.py) 写着"**永远不要调用**":[06](06-data-model.md) 里那几条 CHECK 约束(facts 必须有 provenance、L3 只能由 user_input 触发)是安全机制,而 `create_all` 绕过它们。**用它补一张表,补出来的是一张没有安全约束的同名表** |
| **用 `alembic check`(autogenerate 差异)判断** | [env.py](../migrations/env.py) 不设 `target_metadata`,本项目的 DDL 全部手写。autogenerate 认不得手写的 CHECK,它给出的"差异"是要**删掉**它们 |
| **升级前自动跑一次备份** | 差一点选了它。否决理由是它把服务进程绑到 shell 脚本上:[`backup.sh`](../scripts/backup.sh) 是 bash + `pg_dump`,而家里那台是 Windows。而且它挡不住真正剩下的那种风险 —— 事务性 DDL 已经覆盖了"升到一半",剩下的是"升成功但那条迁移本身写错了",**那种情况需要人来判断要不要回滚,而不是需要一份自动备份** |
| **迁移放进单独的 init 容器 / 启动前置单元** | 量级不对。[ADR-016](#adr-016--服务端用-python--fastapi) 定的是"能被 systemd 拉起来的单进程",而家里那台连 systemd 都没有 |

**重新评估的触发条件**

- **出现第一条不可回滚、或者会长时间锁表的迁移**(重建大表、改列类型)。
  那种不该在无人值守时自动跑 —— 那时要给迁移加一个"需要人工"的标记,
  而不是关掉整个机制
- **一个库被多个进程连**(P4 之后横向扩)。互斥现在靠 Postgres 的
  advisory lock,够用;但"两个不同版本的代码同时在跑"是另一个问题,
  advisory lock 解决不了
- **自动升级真的升坏过一次。** 先查是不是那条迁移本身写错了 ——
  改默认值是最后一步,不是第一步
- **迁移多到升一次要几分钟。** 启动期那一次会让服务延迟同样久,
  那时要把启动期改成"只校验、只在凌晨升"

## ADR-031 · 同一条告警在一个窗口内只发一封

**状态**:已确认(2026-09-10,和 [ADR-030](#adr-030--库版本落后由进程自己发现并在空闲时段自己补上) 同一次事故)。

**背景**

那次事故里,同一封告警发了 **85 封**,内容一字不差。**第 85 封没有比第 1 封
多说任何东西** —— 它唯一的作用是让前面 84 封更难被看见。

而"告警变成噪音之后,真出事的那次就被忽略了"这句话,在这个仓库里已经写过
两遍:一遍在 [config.py](../lifein/config.py) 那条"配了 SMTP_HOST 就必须配全"
的理由里,一遍在 [bootstrap.py](../lifein/bootstrap.py) 那条"拿不到凭据就不建
那个适配器"的理由里。**两处都在说别让告警变吵,而系统自己没有做到。**

要紧的是这不只是"烦"。[07 §2.7](07-config.md#27-邮件兜底通道p1) 把邮件通道
称作**告警的唯一出口**,而一个被同一件事刷屏的出口,和堵住了没有区别。

**决策**

告警出口外面包一层 `ThrottledAlerter`([alerts.py](../lifein/alerts.py)):

1. **键是 `(title, detail)` 完全一致。** 差一个字就是另一条告警,照发
2. **窗口是 `ALERT_DEDUP_WINDOW_M`,默认 60 分钟。** 配 `0` 等于不去重
3. **收敛的只有出口,日志一条不少。** 被压住的那些照样写一行 ERROR,
   注明这是窗口内第几次
4. **窗口结束后的第一封带上次数**:"这段时间里同样的告警还发生了 N 次"

**理由:错合并的代价,比多发几封信高得多**

最容易想到的键是"只看标题"。否决它是因为 P4 之后
`user=A: 授权码失效` 和 `user=B: 授权码失效` 是**两个人的两件事** ——
把第二条压住,等于让一个人的故障消失。

同理否决了"把 detail 里的数字抹掉再比":uuid 里有数字,那样两个用户会被
归成一条。**宁可少收敛,不要错合并** —— 少收敛的代价是多几封信,
错合并的代价是一件事从来没有被报告过。

事故那 85 封的 `detail` 一字不差(同一个 user、同一条 SQL、同一个错),
所以这个最保守的键**对这次的形状就已经够了**。

**为什么日志不收敛**

日志在本机、不打扰任何人,而且它是排查时唯一能数出"到底发生了多少次"的
地方 —— 这次那个 85 就是从日志里数出来的。收敛日志等于把排查时最有用的
那个数字扔掉,换取一点磁盘。

**为什么是一小时,不是"每天一封"**

一小时内的重复几乎必然是同一个原因。而超过一小时它还在发,说明**没有人
处理它** —— 那时再响一次是应该的。默认值要在"别吵"和"别被忘掉"之间,
一天一封偏向了前者太多。

**为什么必须带上被压住的次数**

因为这个项目最危险的失效方式是安静([alerts.py](../lifein/alerts.py) 开头
第一句)。**一个不说自己压了多少的收敛器,就是在制造安静** ——
"一封"和"一小时内八十五封"是完全不同的两件事,而后者才说明它在恶化。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **只按标题去重** | 见上。P4 之后同一个标题下是不同人的不同故障,压住第二条等于让一个人的故障消失 |
| **把 detail 里的数字 / uuid 归一化之后再比** | 更能收敛,但会把两个用户合成一条。**错合并的代价比多发几封高** |
| **指数退避**(1、2、4、8… 分钟) | 更省信。否决理由是"下一封什么时候来"变得不可预测,而告警最需要的属性恰恰是可预期 —— 你要能回答"没收到信是不是说明它好了" |
| **落库去重**(建一张 `alerts` 表) | 进程内一个 dict 就够,而且**告警链路不该依赖数据库** —— 库本身出问题正是最需要告警的时候,这次就是。ADR-030 那条如果走库,它自己就发不出来 |
| **在 `EmailAlerter` 里直接做** | 那样 `LoggingAlerter` 和将来每一条新通道各要再写一遍。包一层任何 `Alerter` 都能用,测试里也能直接对着假时钟测 |
| **交给收件端**(邮箱的过滤规则 / 会话折叠) | 把问题挪走而不是解决:折叠是按主题做的,它会把真正不同的第 86 件事一起折进去,而那一封正是你要看见的 |
| **给告警分级,只收敛低级别的** | 现在只有一种级别,而**引入级别之后最可能发生的事是所有告警都被标成高级别** —— 那时收敛等于没做。要分级的话先要有"哪些可以晚一天看"的清单,现在没有 |

**重新评估的触发条件**

- **出现 title 相同、detail 每次都不一样的风暴**(比如 detail 里带了时间戳
  或计数)。那时才加第二层"按 title 的上限" —— 现在加等于为一个还没发生的
  形状付错合并的代价
- **多用户之后,同一个故障对着 N 个用户各发一封。** 那时键里该有 `user`,
  而不该靠窗口去挡 —— 窗口挡住的会是别人的那一封
- **有人漏掉了一条被压住的告警。** 先看窗口是不是太长,再考虑把次数放进
  标题(而不是正文)
- **告警出口不止一条**(比如加了短信)。那时收敛要在出口之前,
  否则每条通道各收敛各的

## ADR-032 · 设备端补上 P2 那两道闸门:`purpose` 与 `sender`

**状态**:已确认(2026-09-11,第一次把 App 装上真机之后)。

**背景**

2026-09-11 第一次把 App 配到真手机上:扫码连上了、通知使用权给了,
而**消费短信一条都没采到**。

第一层原因是白名单空着 —— 默认拒绝,采集器送上去的全丢。这一层是对的,
[R10](05-risks.md#r10--手机端采集器的越权读取) 要的就是它。

但把白名单填上之后,**消费短信仍然记不了账**。查下来是设备端两处
P1 时期的写法,而 P2 从来没回去动过它们:

| 在哪 | 写的是什么 | 后果 |
| --- | --- | --- |
| `Whitelist.allows()` | 硬编码 `purpose == "message"`,注释写着"银行与支付类是 P2 的事" | `purpose=transaction` 的规则**在手机上就被丢掉**,根本不上传 |
| `NotificationCollector.screen()` | 两处都传 `sender = null` | `sms_sender` 规则**永远匹配不上** —— 两端的匹配都是 `sender.startsWith(pattern)` |

**服务端那一半是齐的**:`OPEN_PURPOSES = {message, transaction}`,
`purpose == transaction` 走交易解析。而 [AGENTS §9](../AGENTS.md#p2-的实施顺序)
里 P2 第 12 片「白名单扩容到 P2:银行号段、支付类包名,打开 `purpose=transaction`
闸门」标着 ✅ —— **标 ✅ 的是服务端那一半**。

**第二条的失效方式最糟。** `admin allow-source --preset 招商` 会成功返回,
`list-sources` 会把它列出来,App 的状态页也会显示它是放行的 ——
而那条规则永远匹配不上任何东西。**它看起来配好了**,然后一个月之后
你发现招行的消费一笔都没进账,而账本上看不出少了什么
(`bank_sources.py` 开头那句"少放一个则是那家银行的消费一整个月都不入账"
说的就是这件事,只是没想到会以这种方式发生)。

**决策**

1. **设备端的 `purpose` 闸门改成集合**:`OPEN_PURPOSES = {"message",
   "transaction"}`,和服务端那份**各写各的**,不共用配置
   ([第 11 片留下的约定](../AGENTS.md#p1-的实施顺序))
2. **短信通知的 `sender` 取通知标题**,而且**只对系统默认短信应用**
   (`Telephony.Sms.getDefaultSmsPackage()`)
3. **关闸门的动作仍然只在服务端一处**:`OPEN_PURPOSES` 去掉 `transaction`
   ([07 §4](07-config.md#4-采集白名单存表用户可改) 那条退出条件的具体动作)。
   设备端放开之后,服务端那一道仍然是最终决定 —— 两道的方向不一样:
   **设备端那道决定什么离开这台手机,服务端那道决定什么入库**

**理由:为什么 `sender` 只取默认短信应用的标题**

通知标题对短信应用就是发件人,对微信是聊天名。**把所有通知的标题都当
`sender`,会让号段规则误伤** —— `"95555"` 前缀撞上一个群名虽然罕见,
但白名单是安全机制,"罕见"不是放过它的理由。

用 `getDefaultSmsPackage()` 而不是自己维护一张 OEM 短信应用包名表:
那是**系统自己的答案**,而那种表一定会漏一个牌子,漏掉的表现又是静默不采。

**它什么时候不准,要先说出来**:有些系统在通知标题里显示的是联系人名或
银行名(号码存进通讯录、或者厂商做了号码识别),那时号段前缀匹配不上。
**表现同样是静默的** —— 所以这一条写进了 [07 §4](07-config.md#4-采集白名单存表用户可改),
退路是按应用放行整个短信应用。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **加 `READ_SMS` 权限直接读短信** | [ADR-010](#adr-010--微信只做只读接入走官方通知监听) 定死只走官方通知监听**读取**。多一个短信权限换一个更准的发件人,而 [R10](05-risks.md#r10--手机端采集器的越权读取) 改判的四前提里有"采集范围可解释" —— 一个能读全部短信的权限解释不过去 |
| **硬编码一张短信应用包名表** | 国内 OEM 太多,漏一个的表现是那台手机静默不采。系统自己知道哪个是默认短信应用 |
| **从 `EXTRA_MESSAGES`(MessagingStyle)里挖发件人** | 更准。否决理由是只有一部分应用用 MessagingStyle,要多一条分支和一份回退,而标题那条的覆盖面更广。**留在触发条件里** |
| **所有通知都把标题当 `sender`** | 见上:号段规则会误伤聊天名 |
| **只开 `purpose` 闸门,不修 `sender`** | 那样要收银行短信就只能按包名放行**整个短信应用** —— 私人短信一起上报,R10 不接受 |
| **只修 `sender`,不开 `purpose` 闸门** | 号段预设的 `purpose` 恰恰是 `transaction`,不开闸门它照样在设备端被丢。**两条必须一起改**,单独任何一条都不会让消费短信入账 |
| **在服务端把 `sender` 从标题推出来** | 服务端收到的时候标题已经和正文混在一起了,而且**设备端那道过滤发生在上报之前** —— 推得再准也救不了"根本没上传"这件事 |

**重新评估的触发条件**

- **出现"通知标题不是号码"的机型。** 那时再看 MessagingStyle 那条路,
  而不是回头去维护包名表
- **03 的退出条件触发(出现错记)。** 关的是**服务端**的 `OPEN_PURPOSES` ——
  设备端要重新发版,而退出条件要的是立刻停
- **微信支付的通知想单独放行。** [06](06-data-model.md) 那条"支付通知和聊天
  通知同一个包名,系统层面分不开"还在,这次改动没有解决它,别指望
- **朋友(P4)开始自己配采集来源** → 一起看 [ADR-033](#adr-033--放行来源改成选应用预设从服务端拿)

## ADR-033 · 放行来源改成选应用,预设从服务端拿

**状态**:已确认(2026-09-11,和 [ADR-032](#adr-032--设备端补上-p2-那两道闸门purpose-与-sender) 同一次实测)。

**背景**

App 状态页"放行的来源"那一格,输入框的 label 是**"加一个包名"**,
placeholder 是 `com.tencent.mm`。

这等于要求用户先知道 `com.eg.android.AlipayGphone` 才能放行支付宝。
用户当天的原话:

> 普通用户怎么知道包名呢,他们只知道软件名呀

而 [R10 那节的改判](05-risks.md#r10--手机端采集器的越权读取)写着四个前提,
其中一条是**朋友要能自己管理采集,不是"找你帮忙"**
([data_control.py](../lifein/repos/data_control.py) 开头把这条展开过:
"'找你帮忙'和'自己能做'的差别不在功能,在**是不是要开口**")。
一个要先查包名才能用的输入框,把"自己能做"变回了"找你帮忙"。

**决策**

1. **从已安装的应用里选。** 图标 + 应用名,包名藏在背后。
   `PackageManager` 在手机本地就有这份对应关系,**不需要任何新接口**
2. **银行号段这类"不是应用"的东西走预设。** 新增
   `GET /app/collector/presets`,把 [`bank_sources.py`](../lifein/sources/bank_sources.py)
   那份目录发给 App,列表里显示的是"招商银行"而不是 `95555`
3. **原来那个包名输入框留着**,降级成高级入口 —— 装了但没有启动图标的应用
   (有些厂商的短信应用就是这样)在选择器里露不出来,那时还得能手输

**它顺带推翻了一句写在代码里的判断**

`Repository.allowSource()` 原来写着:

> P1 只放消息。加银行与支付类是 P2 的动作,**不该从手机上顺手打开**

状态页上也印着"只放消息类。银行与支付类要在服务器上单独开"。
**那句话在 P2 做完之前是对的** —— 那时服务端的 `OPEN_PURPOSES` 还没放开
`transaction`,从手机上加一条交易类规则只会得到一条永远被 `phase_not_open`
丢掉的记录,而那比不让加更让人困惑。

现在两件事都变了:P2 的闸门开了,而设备端那道也补上了
([ADR-032](#adr-032--设备端补上-p2-那两道闸门purpose-与-sender))。
再把银行来源留在"只能 SSH 上去用 CLI 加",撞的正是
[R10](05-risks.md#r10--手机端采集器的越权读取) 那四个前提里的一条。

**真正兜底的不是"手机上加不了",是这两件:默认拒绝,以及服务端那道
`OPEN_PURPOSES`。** 前者保证没被显式选中的东西一律不采,后者保证
"停下来"这个动作在服务端一处就能做到(03 的退出条件要的是立刻,
而改 App 要重新发版)。**把能力藏起来不算安全措施,它只是让人绕路。**

**理由:预设为什么走接口,而不是在 App 里再写一份**

**号段会变,而 App 改一次要重新发版**([06 §6](06-data-model.md#6-接口契约)
那句"发版之后旧版本还在手机上跑")。放服务端的话改一行,
所有设备下次打开就看见了。

**这和[铁律 11](../AGENTS.md#1-铁律) 要求的"两端各写一遍"不冲突。**
那条要的是两道**独立失效的过滤判断** —— 验证码正则、白名单匹配、签名算法,
共用配置的那一刻它就退化成一道。而预设是**一份目录**,不是判断:
它决定"界面上列出哪几个选项",决定不了任何一条通知的去留。
用户从目录里选完之后,真正过滤的仍然是两端各自那份 `matches()`。

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **在 App 里内置一份预设目录** | 号段会变,而 App 要发版。同一份东西两个地方各存一份,迟早对不上 —— 而对不上的表现是"服务端加了新银行,手机上看不见" |
| **让用户从"最近被丢弃的通知"里挑** | 最贴近直觉的做法,而且差一点就选了它。否决理由是它要求**先把没放行的通知存下来再展示** —— 那和默认拒绝是直接冲突的([R10](05-risks.md#r10--手机端采集器的越权读取)):为了让你选择放行什么,先把不该采的采了 |
| **只做应用选择器,不做预设** | 银行号段不是应用,选择器里选不出来。而[银行短信正是消费记账的主来源](#adr-012--账单采集以实时通知为主导出账单为辅) |
| **在 Web 控制台做这件事** | 浏览器列不出手机上装了哪些应用。控制台那条路留着改已有的规则,加新的要在手机上 |
| **让用户填应用名,服务端反查包名** | 服务端没有"应用名 → 包名"这张表,而且它是按设备不同的。这件事只有手机答得出来 |

**重新评估的触发条件**

- **装了几百个应用,列表长到不好找。** 这次带了搜索框;再不够就按"最近用过"
  排序,而那要 `PACKAGE_USAGE_STATS` 权限 —— 到那时先算一遍这个权限值不值
- **预设目录长到要分组。** 那时给接口加一个分类字段,不要在 App 里按名字猜
- **朋友(P4)真的开始自己配。** 那是这条决策唯一的验收场景,
  而在此之前它只是"我认为这样更好用"
- **出现一个装了、能发通知、但在选择器里露不出来的应用。** 那说明
  "有启动图标"这个筛选条件太紧,要换一个判据(而不是去掉筛选 ——
  全部列出来会有几百个系统组件)

## ADR-034 · 银行短信按**短信签名**匹配,不按发件人

**状态**:已确认(2026-09-11)。**它推翻 [ADR-032](#adr-032--设备端补上-p2-那两道闸门purpose-与-sender)
里"短信的 `sender` 取通知标题"那半条**,并把 `sms_sender` 降级成不推荐使用。

**背景:三条真实短信**

ADR-032 把"通知标题就是发件人"这件事当成可用的,只在注脚里写了它什么时候不准。
收到三条真实短信之后,那个注脚才是主体。同一台手机、同一个 `com.android.mms`:

| # | `sender`(通知标题) | 正文开头的签名 |
| :-: | --- | --- |
| 1 | `招商银行` | `【招商银行】` |
| 2 | `游戏中心` | `【游戏中心】` |
| 3 | `10693495555` | `【招商银行】` |

`sms_sender` 靠两个假设成立,**三条短信把两个都证伪了**:

**假设一「采集端拿得到发件号码」—— 半假。** 同一个短信应用,有时给号码,
有时给厂商识别出来的显示名。这个字段不是一个稳定的身份,是**系统渲染给人看
的东西** —— 而白名单是按身份配的。

**假设二「银行号码是号段前缀」—— 全假,而且这一条和显示名无关。**
真实号码是 `10693495555`:招行走 **1069 的 SP 网关**下发,`95555` 在里面是
**子串,不是前缀**。拿那 14 条预设跑一遍真实值:

```
'10693495555':  前缀匹配命中 = 无   包含匹配命中 = ['招商银行']
```

[`bank_sources.py`](../lifein/sources/bank_sources.py) 的注释写着"银行实际发
短信用的是扩展号(955550、9555501……)" —— **那是照着想象写的**。所以就算
显示名的问题不存在、就算号码每次都拿得到,**那 14 条预设照样一条都不会命中**。

> **这是 [AGENTS §9](../AGENTS.md#那两列不是一回事别把绿色当成能用) 那句话
> 第二次应验:** "真实数据比构造的用例值钱得多。前面那些用例是照着规则写的,
> 所以规则漏掉什么,用例也漏掉什么。" 三条短信,十分钟。

**决策**

1. **新增 match_type `sms_signature`**:匹配正文开头 `【…】` 里的机构名,
   **前缀匹配**
2. **银行预设从 14 条号段改成按签名**,复用目录里现成的 `label` ——
   那不是巧合,签名本来就是机构的名字
3. **两端各自从自己手里那份正文提取签名,不新增任何线上字段**
4. **`sms_sender` 不删,但降级**:预设不再产出它;文档改口径(它是"通知上
   显示的发件人",不是"发件号码");迁移把库里现存那两条号段规则**停用**

**理由:为什么签名是这里唯一稳的信号**

它由**发信方写进内容**,不受厂商显示逻辑影响,也不受 SP 网关号码影响。
三条里三条都指向正确的机构 —— 包括标题是网关号码那条。看起来华为那个显示名
正是从签名推出来的(第 3 条没推出来,就退回了原始号码),
**也就是说签名是源,显示名是它的有损副本**。

**为什么不新增一个"设备算好的签名"字段**

[铁律 11](../AGENTS.md#1-铁律) 要的是两道**独立失效**的过滤。设备把算好的
签名传上来,服务端那道就退化成"信任设备算的" —— 一道,不是两道。
两边各自从正文里抠一次,多写十行,换的是那条铁律还成立。

**为什么前缀匹配,而包名是全等**

同一家机构有多个签名(`招商银行` / `招商银行信用卡`),而预设给的是完整机构名。
这里的取舍照抄 `bank_sources.py` 自己那句话:

> 多放一个进来最多是几条营销短信(会被第 3 层判成 marketing 丢掉);
> **少放一个则是那家银行的消费一整个月都不入账,而账本上看不出少了什么。**

包名没有这个问题(它是精确标识符),所以那边仍然全等 ——
前缀会让 `com.tencent.mm` 顺带放行 `com.tencent.mm.fake`。

**代价:签名可以伪造,这是一个新的注入面**

谁都能发一条以 `【招商银行】` 开头的短信,从而被放行、被解析成一笔交易。
**接受它,但理由要写下来:**

- 白名单是 [R10](05-risks.md#r10--手机端采集器的越权读取) 的**范围控制**
  (什么离开这台手机),不是真伪控制。进来的东西一律 `trust=external`
- "这是不是一笔真消费"归四层防误判管,那是它存在的理由
- **但它确实比按号码匹配更容易被构造** —— 号码要伪造得有个通道,
  而正文写什么是发信人说了算。03 那条"出现错记就停下来"的退出条件覆盖它,
  而**那条退出条件从今天起多了一个要盯的方向**

**被否决的方案**

| 方案 | 否决理由 |
| --- | --- |
| **把号段预设从前缀改成包含匹配** | 治得了第 3 条,治不了第 1、2 条 —— 标题是显示名时根本没有号码可匹配。而且 `包含` 比 `前缀` 松得多:`95555` 会命中任何含这五位的号码 |
| **给每家银行同时配号码和名字两条 `sms_sender`** | 这是我一开始提的,**是打补丁**:把一个显示名塞进一个叫"发件号码"的字段,数据模型开始说谎,而下一个读这张表的人会以为那一行是号码 |
| **加 `READ_SMS` 直接读真实发件号** | [ADR-010](#adr-010--微信只做只读接入走官方通知监听) 定死只走通知监听。而且**就算拿到真号码也解决不了问题** —— `10693495555` 对不上任何一条号段预设,前缀假设本身才是错的 |
| **不按发件人识别,整个短信应用放行成 `transaction`,让解析器判断** | 差一点选了它,而且它更简单。否决理由是**全部短信都要离开这台手机**才能被判断,而 R10 收的正是这个。签名那道让不相干的短信根本不上传 |
| **在设备端做"像不像银行短信"的内容判断**(金额正则等) | 比签名松,而且把语义判断搬进了手机(架构 §8.1)。签名只是**取一个标识符**,不是判断内容的含义 —— 和验证码正则那道的性质不同 |
| **`sms_sender` 直接从 CHECK 里删掉** | 表里现存的行要能回答"曾经放行过谁"(06 §6.9 那条"没有删除")。删掉约束值等于让历史行非法 |

**重新评估的触发条件**

- **出现签名在正文结尾的银行短信。** 现在只认开头,因为三条真实样本都在开头。
  见到结尾的那天再扩,**不要现在就为没见过的形状写代码**
- **出现没有签名的银行短信。** 那时才需要回头看发件人那条路,
  而且要先量一遍它到底给的是什么
- **真的被伪造的 `【银行】` 短信记进过一笔账。** 那是 03 退出条件的触发,
  先停 `OPEN_PURPOSES` 再谈怎么加强
- **签名前缀误伤了一家机构**(比如 `中国银行` 命中了别的"中国银行…"署名)
  → 那时把该条预设改成更长的完整签名,而不是把全局改成全等
