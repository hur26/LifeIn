# 03 · 开发计划

**分期原则:每一期结束后都必须是"能真的用起来"的状态。**
不接受"先搭三个月基础设施再说"。每期都有明确的验收标准和**退出条件**
(即"什么情况下应该停下来修前面,而不是继续往下做")。

工作量估计按**一人全职**计,业余投入请自行乘系数。

---

## 总览

| 期 | 主题 | 验收标准 | 估计 |
| --- | --- | --- | --- |
| **P0** | 邮箱+日历 → 每日摘要 | 你自己每天真的会打开它 | 2–3 周 |
| **P1** | 记忆层 + 安卓 App + 主动触发 | 它开始"记得你",且提醒不烦人 | 6–8 周 |
| **P2** | 财务与账单 + App 账本 | 你不再逐笔记账 | 6–8 周 |
| **P3** | 审批执行 | 你敢让它代发一条真实消息 | 4–5 周 |
| **P4** | 多用户托管 + Web 控制台 | **朋友才在这一步进来** | 5–7 周 |

> P1 和 P2 的工期比最初估计各多了约 3 周,原因是[安卓 App](02-architecture.md#8-安卓-appp1-起)
> 从"后台采集器"扩成了承担查看与操作的完整客户端
> ([ADR-014](04-tech-decisions.md#adr-014--客户端做完整-app-但不接收推送))。
> 这笔时间换来的是 Web 控制台从 P3 推迟到 P4、桌面客户端整个移出规划。

---

## P0 · 自己每天会打开它

**唯一目标**:验证两件事 —— 你自己会不会每天看,以及 LLM 摘要质量够不够。
这两个答案决定后面所有事情值不值得做。

### 范围

- 数据表 schema(含 `user_id` 与凭据加密字段,见 [架构 §6](02-architecture.md#6-为多用户预留p4-前必须做到))
- 工具注册表 + 分权网关 + 审计日志(**骨架必须在 P0 到位**,后面往里填)
- **agent 注册表与契约机制**:输入类型、工具白名单、输出 schema、失败行为、
  评测集五项缺一不可([ADR-013](04-tech-decisions.md#adr-013--agent-按领域分工同进程运行))。
  P0 只有摘要和问答两个 agent,但机制要一次做对 —— 第三个 agent 进来时补,
  就得回头改前两个
- 邮箱采集(IMAP + 授权码,QQ / 163)、日历采集(企业微信日程 API)
- 事件归一化写入 `raw_events`
- 每日摘要生成(直调外部 LLM API,不套框架)
- 企业微信自建应用 + **markdown 消息**推送。
  **模板卡片推迟到 P3**:卡片必须带 `card_action` 跳转目标,而 P0 没有可跳的地方
  (App 在 P1、Web 控制台在 P4)。卡片真正不可替代的是**按钮回调**,
  那是审批的硬需求([ADR-001](04-tech-decisions.md#adr-001--推送与审批入口选企业微信)),
  和审批一起做才验证得了
- 基础对话:在企微里提问,agent 用 L1 工具回答

### 不在范围内

L2/L3 工具、记忆抽取、向量检索、账单、安卓 App、Web 界面、任何朋友相关的东西。
P0 只有服务端和企微,手机上不装任何东西。

### 验收标准

连续 14 天每天收到摘要,你主观判断"这条有用"的比例 **> 70%**。

### 退出条件(出现以下情况先停下来修,不要往 P1 走)

- 摘要质量差到你自己都不看 → 问题多半在**数据归一化**而不是 prompt,回去修归一化
- 邮箱/日历数据拉取不稳定 → 先解决可靠性,主动推送的信任建立在稳定之上
- 企微卡片推送有延迟或丢失 → 入口不可靠,后面全是空中楼阁

## P1 · 记忆层、安卓 App 与主动触发

**目标**:让它开始"记得你",并且主动说话时不招人烦。

### 范围

**记忆层**

- 实体抽取与别名归并(`entities` / `entity_aliases`)
- 事实库 `facts`,**强制携带 provenance**
- 笔记 / 待办工具接入(具体选型在本期确定)
- pgvector 向量索引,用于模糊召回

**安卓 App 首次上线**([架构 §8](02-architecture.md#8-安卓-appp1-起))

原生 Kotlin,不做 iOS([ADR-015](04-tech-decisions.md#adr-015--app-用原生-kotlin只做安卓));
**不集成任何厂商推送 SDK** —— 这条是硬约束,不是本期没做完。

采集侧:

- 安卓通知监听 + 白名单过滤 + 验证码丢弃 + HTTPS 上报
- **心跳上报与掉线告警** —— 这条不是锦上添花:采集器静默掉线时系统表现
  一切正常,只是提醒悄悄变少,不告警你半个月都发现不了
- 微信好友与群消息通知接入(**只读**,见
  [ADR-010](04-tech-decisions.md#adr-010--微信只做只读接入走官方通知监听))

查看侧(本期只做最小集,账本相关留到 P2):

- 采集器状态面板:心跳、掉线原因、白名单增删
- 记忆与实体浏览:查看、否定、纠正 `facts` 条目
- **认证机制**:采集凭据与查询凭据**分开签发**,采集端只能写不能读;
  长期凭据存 Keystore,token 服务端可单点吊销
  ([R11](05-risks.md#r11--app-直连服务端的认证面))

**基于消息的新能力**

- **群消息摘要**:对在线期间收到的群消息做摘要。注意能力边界 ——
  免打扰的群拿不到、长消息会截断、撤回和历史消息拿不到
- **日程与待办提取**:从邮件和群消息里识别"周三下午三点开会""帮我带个东西",
  经 L2 工具写入企微日程或待办,**必须可回滚**
- **定时提醒**:基于提取出的日程按时推送

**主动触发**

- 规则引擎 + 影子模式 + 频率闸门
- L2 工具首次上线(建待办、改日历),含回滚信息记录
- 邮件兜底推送通道

### 验收标准

- 能正确回答:"上次和 X 聊的是什么"、"我这周答应了谁什么事"
- 主动提醒**误报率 < 20%**(先跑一周影子模式统计,再决定是否转 active)
- 群消息摘要你主观判断"抓住了重点"的比例 **> 70%**
- 日程提取:一周内的真实日程**漏报 < 10%**,且**误报进日历的条数为 0**
  (拿不准的一律走"待确认",不直接写日历)
- 采集器掉线能在 **1 小时内**告警
- App 的采集凭据被拿走**读不到任何账本或记忆数据**(实测验证,不是设计上认为)
- 你没有关掉任何一类通知

### 退出条件

- 误报率降不到 20% 以下 → 收紧规则或退回影子模式,**不要靠调 prompt 硬压**
- 记忆里开始出现你不认可又说不清来源的条目 → provenance 链路有漏,先补
- **日程提取往日历里写了脏数据** → 立刻退回"提取为待确认"模式。
  日历被污染比没有这个功能糟得多 —— 你会不再信任日历本身
- 采集器频繁掉线且保活搞不定 → 先解决保活,不要带着一个半死的采集器往 P2 走

## P2 · 财务与账单

**目标**:消费发生的当场就入账,你不再逐笔记录。

**主通道是实时通知,不是月度账单。** 预算预警只有在超支当天发出才有意义,
月度导出天然滞后最多 30 天。因此本期以手机端转发的交易通知为记账主来源,
月度账单退居**对账与补全**角色。设计细节与两个必须正视的缺口见
[ADR-012](04-tech-decisions.md#adr-012--账单采集以实时通知为主导出账单为辅)。

**硬前提**:App 必须装在**你日常使用的那台安卓主力机**上,备用机不行。
两条物理限制堵死了备用机方案:银行短信只到 SIM 卡所在设备;
微信与支付宝个人号同一时间只能在一台手机登录。
iOS 没有等价方案 —— 若只有 iOS,本期退回月度导出模式,实时入账不成立。

### 范围

**采集与入账(服务端)**

- **实时通道(主)**:安卓端转发**短信 + App 通知** → HTTPS webhook → 立即入账。
  必须同时监听 App 通知,不能只做短信 —— 多家银行已提高短信提醒门槛,
  500 元以下的小额交易普遍不再免费发短信,而日常消费大多在这个区间
- **采集侧白名单扩容**:P1 只放行了微信,本期加入银行号段与支付类 App 包名;
  验证码类内容仍在手机端强制丢弃,服务端入库前再过一次正则
  (见 [R10](05-risks.md#r10--手机端采集器的越权读取))
- **四层防误判**:源头白名单 → 5 分钟去重窗口 → LLM 判定是否真实支出
  (显式区分待支付提醒 / 还款 / 转账 / 退款 / 到账 / 营销)→ 代码复核
  (金额必须能在原文逐字找到、分类必须在枚举内、置信度低于阈值拒绝)。
  **任何一层不过一律进"待确认",不入账也不丢弃**
- **两阶段入账**:实时通道先落金额、时间、卡号后四位;月度账单到达后按
  (金额, 时间窗, 卡号后四位) 匹配回填真实商户名与订单号 —— 实时通知里的商户
  常常只是"财付通""支付宝"这类代收机构名,不能直接拿来归类
- **覆盖率统计**:月度账单到达后,统计其中有多少笔曾在实时通道出现过

**月度对账数据源**

- 信用卡月度对账单邮件解析(PDF 带打开密码),完全自动,作金额权威源
- 支付宝 / 微信账单导出邮件的自动收取:识别导出邮件 → 解压(密码可配置)→ 解析,
  用于补全商户名与订单号(导出格式不稳定,需容错)

**归类与分析**

- 归类:**规则表 + LLM 混合** —— 高频商户走规则(便宜且稳定),
  新商户才问 LLM,结果写回规则表([ADR-008](04-tech-decisions.md#adr-008--账单归类用规则llm-混合))
- 预算设定与超支预警
- 月度分析报告(企微卡片 + 邮件长版)
- 账单增删改与组合查询(按时间 / 类别 / 关键字),在企微里对话式完成

**App 查看侧主体(本期的另一半工作量)**

- 账本浏览、月度报表、预算与超支查看
- **待确认队列** —— 防误判拦下来的账目在这里快速处理,是使用频率最高的界面
- 拍照识别小票 / 发票,补现金与纸质票据这条长尾
- 手动补一笔

### 验收标准

- 一个月账单自动归类准确率 **> 90%**
- 你连续一个月没有逐笔录入过任何一笔消费
- **实时通道覆盖率 > 80%**(月度账单中曾在实时通道出现过的笔数占比)
- **误记率 = 0**:一个月内没有任何一笔"待支付提醒""信用卡还款""退款"
  被错记成支出。这一条不设百分比阈值 —— 错记会直接摧毁对账本的信任
- 预算超支预警在**超支当天**发出,不是月底
- 手动操作只剩两类:**每月两次账单导出** + **在待确认队列里点确认**。
  不再有任何一笔是靠你打开界面从头输入的

### 退出条件

- 账单导出格式频繁变动导致解析经常挂 → 先做格式容错和失败告警,不要静默丢数据
- 归类准确率上不去 → 检查是不是规则表没有沉淀,而在反复问 LLM
- **实时通道覆盖率长期低于 80%** → 是转发规则漏了(多半是 App 通知没监听全),
  回去补规则,不要默认"就这样吧"然后退回月度模式
- **两阶段匹配出现重复入账** → 停下来修匹配键和幂等,重复的账目比没有更糟
- **出现错记(把非支出记成支出)** → 停下来补防误判层,不要靠调 prompt 硬压。
  优先把阈值调严让它进"待确认",宁可多点几下

## P3 · 审批执行

**目标**:你敢让它代你发一条真实消息。这是信任的分水岭。

本期范围比原计划窄了 —— Web 控制台推迟到 P4,专注把 L3 这条链路做扎实。

### 范围

- L3 工具首次上线(代发消息、提交表单、预约)
- 审批队列:幂等键、超时过期、人类可读预览
- 企微交互卡片回调链路(签名校验、时效校验)
- **引入状态机编排**(LangGraph 或同类)—— 审批要求流程暂停数小时后从断点恢复,
  这才是引入框架的真实理由([ADR-002](04-tech-decisions.md#adr-002--p0p2-不引入-agent-编排框架))

> Web 控制台已从本期移出、推迟到 P4;桌面客户端整个移出规划。
> 理由见 [ADR-014](04-tech-decisions.md#adr-014--客户端做完整-app-但不接收推送)。

### 验收标准

- 完成 20 次真实 L3 操作,**零重复执行、零越权**
- 审批卡片的预览文本你一眼能看懂在做什么,不需要点开细节

### 退出条件

- 出现任何一次越权或重复执行 → 停止 L3 上线,回去修网关和幂等
- 你自己不敢点"同意" → 预览做得不够清楚,或回滚机制不可信

## P4 · 多用户托管

**只有走到这里,朋友才进来。**

### 前置硬门槛(不满足则不开放)

- [ ] 完成一次安全审查,[05 风险登记](05-risks.md) 中所有 **高** 等级风险已有缓解措施
- [ ] 凭据加密从环境变量升级为 KMS 或等价方案
- [ ] 备份与恢复演练成功至少一次
- [ ] 写好隐私说明,明确告知朋友:你能看到什么、数据存在哪、如何删除

### 范围

- 用户体系与租户隔离(数据层强制 `user_id` 过滤,不靠应用层自觉)
- 凭据 KMS 管理
- 每用户配额与**成本上限**(主动扫描的开销随用户数线性增长)
- 企业微信多成员配置与"微信插件"接收链路验证
- **Web 控制台**(从 P3 推迟至此):数据导出、账号与授权管理、隐私说明页 ——
  移动端查看已由 App 覆盖,Web 只剩这些 P4 的合规必需项
- 备份、恢复、数据导出与删除
- 朋友侧的降级说明:未装 App 或使用 iOS 的朋友,记账退化为月度导出、
  无群消息摘要([产品定义 §4 降级矩阵](01-product-spec.md#4-交互形态))

### 验收标准

一位朋友连续使用两周,无数据事故、无越权、无成本失控。

## 开发节奏约定

- **一个可独立描述的改动 = 一次提交 = 一次推送。** 不攒批。
- 提交信息说清**为什么**这么改,不只是改了什么。三个月后你只会记得 why。
- 每期结束写一份复盘,把新学到的和被推翻的结论回写进
  [04 技术决策](04-tech-decisions.md)。
- 任何时候引入新依赖或新技术,先在 04 里补一条 ADR,写明**被否决的替代方案**
  和**将来重新评估的触发条件**。
